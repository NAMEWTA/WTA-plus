## New driver findings at e78d886 (standards axis)

1. **Medium, resource cleanup can report success while owned Chrome remains.** `frontend/e2e/run-inbox-real.py:95-103` returns from `stop()` whenever the runner leader has exited, without signaling its process group. A crashed Playwright runner can leave Chrome descendants in that group. `:293-297` records `process_error_*` if termination raises, but the success condition at `:330-334` never checks those errors and only probes four service ports, none of which belongs to Chrome. Thus an orphaned browser or termination error can coexist with `exit_code=0`, contrary to `frontend/e2e/inbox-real.md:16-18` and TEST-003 cleanup. Minimum fix: stop/verify the owned process group after leader exit as well, treat any process cleanup error or surviving group as failure, and add a no-Docker child-process regression for leader-exits-before-child plus failure injection.
2. **Medium, selected-test provenance can be false under a supported CLI override.** `run-inbox-real.py:115-116,155-169` accepts and hashes `--playwright-test`, but `:267-269` invokes Playwright only with `--config` and `--grep`; it never selects that file. A caller can pass a different path and produce a result labeled with its hash while another test runs. The default dedicated config currently selects the intended file, so this does not invalidate the default test run; it makes the reusable driver/report contract untrue. Minimum fix: include the validated test path as a CLI file filter and record both config/test paths, or remove the override and verify the fixed config selects the fixed test.
3. **Medium, an I/O failure during log finalization can skip container cleanup.** `run-inbox-real.py:298-307` closes and rewrites logs before `docker rm` without per-stage exception handling. A disk-full/error on `close()`, redacted log write, or `unlink()` exits `finally` before exact-ID container removal and before `result.json` is written. Minimum fix: trap and accumulate log finalization errors, always continue process/container cleanup and report writing, and fail the gate if any cleanup error remains. This is a failure-path hardening requirement, not a finding about the normal successful run.
