# 统一通知管理平台设计日志

## LOG-001 — 2026-08-31T20:47:00+08:00 — 统一通知平台目标
- **设计树节点：** D-001
- **轮次与依赖：** round 1 / 无
- **状态：** confirmed
- **问题：** 本 change 是继续提供分散的应用内发送工具，还是建设所有业务系统统一接入的通知平台？
- **事实与来源：** 用户要求公司所有业务系统只对接一个平台，由平台集中管理短信渠道、配置、供应商迁移、发送量和逐条投递记录。
- **选项：** 各业务系统分别集成供应商；只做共享 SDK；建设统一通知平台。
- **推荐：** 建设统一通知平台，统一机器接入、配置治理和投递审计。
- **结论：** 本 change 的目标是公司级统一通知管理平台，不是单个系统内新增短信配置页面。
- **原因：** 只有统一入口和统一状态才能让供应商迁移、配额、统计和审计不再分散在业务系统。
- **影响工件：** CONTEXT / ADR / Spec / Ticket
- **约束或不变量：** 统一平台必须实际拥有对外发送入口和治理状态；只有后台 CRUD 不算完成。
- **后续：** 锁定渠道范围、执行模式、应用身份、模板和路由合同。
- **替代/被替代：** 无

## LOG-002 — 2026-08-31T20:47:00+08:00 — 复用现有内核而非改造 Austin
- **设计树节点：** D-002
- **轮次与依赖：** round 1 / D-001
- **状态：** confirmed
- **问题：** 平台应 fork Austin，还是演进仓库现有通知内核？
- **事实与来源：** 用户认可基于当前工程新增模块的建议；代码已有 common-notify、SMS4J、邮件 Adapter、Redis 幂等、OSS 附件快照、投递事件和监控。永久 ADR-0006 至 ADR-0009 已固定现有内核边界。
- **选项：** fork Austin；另建新服务；复用现有内核并补控制面。
- **推荐：** 复用现有内核，避免两套渠道、日志、认证和配置体系。
- **结论：** 不改造 Austin，不重建发送内核；以 NAMEWTA 现有通知能力作为数据面底座。
- **原因：** 当前差距主要是应用、账号、模板、路由、配额、统一 API 和统计等平台控制面。
- **影响工件：** ADR / Spec / Ticket
- **约束或不变量：** 保持 common-notify 渠道无关；SMS 与 Mail 继续通过 Adapter 接入。
- **后续：** 新模块只能正向依赖现有公共能力，不得产生反向依赖。
- **替代/被替代：** 无

## LOG-005 — 2026-08-31T20:47:00+08:00 — 公司系统统一接入入口
- **设计树节点：** D-005
- **轮次与依赖：** round 1 / D-001, D-003
- **状态：** confirmed
- **问题：** 公司其他系统怎样认证并调用统一通知平台？
- **事实与来源：** 当前仓库已有显式 @OpenApi 暴露、HMAC 签名、时间窗、nonce 防重放、权限匹配、机器会话和 Redis 分布式限流；用户认可复用该入口的建议。
- **选项：** 新建第二套 appKey 协议；使用浏览器登录 Token；复用现有 OpenAPI 机器调用边界。
- **推荐：** 复用 OpenAPI 认证协议，在认证后增加通知应用授权。
- **结论：** 外部统一发送接口使用现有 OpenAPI 机器调用边界，不重新发明密钥和签名协议。
- **原因：** 降低安全实现重复，同时保留通知领域对应用、模板、渠道和配额的独立治理。
- **影响工件：** ADR / Spec / Ticket
- **约束或不变量：** OpenAPI credential、OAuth Client、Platform Client、notify_app 和 Provider Account 是不同概念。
- **后续：** 决定 notify_app 与 credential 的绑定及授权粒度。
- **替代/被替代：** 无

## LOG-007 — 2026-08-31T20:47:00+08:00 — 现有投递日志复用与迁移边界

- **轮次与依赖：** round 1 / D-003, D-004
- **状态：** confirmed
- **问题：** 新平台是否建立一套新的发送日志和监控页面？
- **事实与来源：** 当前已有 sys_notify_log、sys_notify_delivery_log、全局监控 Controller、前端列表和详情；用户认可复用这些数据的建议。
- **选项：** 平行日志体系；直接重命名并破坏兼容；复用表和合同后再迁移代码归属。

## LOG-008 — 2026-08-31T21:00:02+08:00 — 首期渠道范围
- **设计树节点：** D-008
- **轮次与依赖：** round 1 / D-001, D-002, D-004
- **状态：** confirmed
- **问题：** 首期只建设短信平台，还是同时把邮件纳入统一治理？
- **事实与来源：** 当前数据面已有 SMS4J 和 SMTP Adapter；用户对第一轮建议回复“采用全部建议”。
- **选项：** 只做短信；短信和邮件同步达到完整能力；统一模型覆盖二者但短信优先闭环。
- **推荐：** 统一模型覆盖短信和邮件，短信优先完成多供应商、路由与回执，邮件先复用现有 Adapter。
- **结论：** 首期领域模型和控制面覆盖短信、邮件；短信是完整治理主线，邮件基础治理不阻塞短信上线。
- **原因：** 避免未来为邮件重做应用、模板、配额和统计模型，同时控制首期交付面。
- **影响工件：** CONTEXT / Spec / Ticket
- **约束或不变量：** “模型覆盖”不等于两个渠道在第一期具备完全相同的 Provider 能力。
- **后续：** 分别定义短信路由回执与邮件能力验收。
- **替代/被替代：** 无

## LOG-009 — 2026-08-31T21:00:02+08:00 — 发送执行与可靠性模式
- **设计树节点：** D-009
- **轮次与依赖：** round 1 / D-001, D-004, D-005
- **状态：** confirmed
- **问题：** 平台只提供同步发送，还是同时支持可靠异步受理？
- **事实与来源：** 当前 NotifyDispatcher 同步调用 Provider；现有 Spring @Async Listener 仅作 best-effort 监控，永久 ADR-0007/0008 明确它不是 durable queue；用户采纳双模式建议。
- **选项：** 只同步；只异步；显式同步和持久化异步双模式。
- **推荐：** 验证码等低延迟场景同步，普通业务通知使用 Outbox 或 durable queue 异步投递。
- **结论：** 统一平台提供同步快速发送和可靠异步发送两种显式模式。
- **原因：** 同步保留当前调用语义，异步为削峰、恢复和最终处理提供持久状态。
- **影响工件：** ADR / Spec / Ticket
- **约束或不变量：** 异步受理成功不等于 Provider ACCEPTED；监控事件不能充当任务队列。
- **后续：** 决定 API、Outbox 状态机、重试和路由 attempt 语义。
- **替代/被替代：** 无

## LOG-011 — 2026-08-31T21:00:02+08:00 — 模板优先与原始内容权限
- **设计树节点：** D-011
- **轮次与依赖：** round 1 / D-001, D-004, D-005
- **状态：** confirmed
- **问题：** 普通业务调用是否可以任意提交正文？
- **事实与来源：** 用户目标要求供应商迁移和配置集中治理；如果业务直接提交供应商模板或任意正文，平台无法稳定审批、映射和统计；用户采纳模板优先建议。
- **选项：** 所有调用都可发原文；完全禁止原文；模板优先并提供独立高权限原文能力。
- **推荐：** 模板优先，原文发送仅向受控内部应用开放。
- **结论：** 普通统一 API 只接受逻辑模板编码和参数；原始内容发送是独立权限，不是默认能力。
- **原因：** 维持模板审批、参数校验、供应商迁移和统计的一致入口，同时保留必要的内部临时发送能力。
- **影响工件：** CONTEXT / ADR / Spec / Ticket
- **约束或不变量：** 原文权限不得绕过渠道、配额、敏感审计和目标频控。
- **后续：** 定义模板版本、参数 schema 和原文调用审计。
- **替代/被替代：** 无

## LOG-012 — 2026-08-31T21:00:02+08:00 — 供应商与路由选择权
- **设计树节点：** D-012
- **轮次与依赖：** round 1 / D-001, D-004, D-005
- **状态：** confirmed
- **问题：** 普通业务调用方是否可以直接选择 providerKey？
- **事实与来源：** 当前底层 NotifyRequest 支持 providerKey 覆盖，但公司级平台的目标是让业务与阿里云、腾讯云等供应商解耦；用户采纳平台路由建议。
- **选项：** 调用方总是指定 Provider；调用方可选覆盖；平台选择，只有运维测试可定向。
- **推荐：** 平台选择，普通调用方不接触 providerKey。
- **结论：** 业务请求表达逻辑场景和渠道，由平台选择渠道账号；providerKey 只用于受控运维测试或内部诊断。
- **原因：** 保证供应商迁移、灰度、健康路由和故障切换对业务系统透明。
- **影响工件：** CONTEXT / ADR / Spec / Ticket
- **约束或不变量：** 底层 providerKey 接缝可以保留，但不得成为普通外部 API 合同。
- **后续：** 决定路由维度、快照和故障切换条件。
- **替代/被替代：** 无

## LOG-013 — 2026-08-31T21:00:02+08:00 — 动态配置与发布方式
- **设计树节点：** D-013
- **轮次与依赖：** round 1 / D-001, D-002, D-004
- **状态：** confirmed
- **问题：** 生产渠道配置通过 YAML 重启生效，还是数据库集中管理并热发布？
- **事实与来源：** 当前 SMS4J 支持多个 YAML blend，但用户目标要求统一配置和透明迁移；仓库已有 OpenAPI 凭据加密模式可参考；用户采纳数据库动态配置建议。
- **选项：** YAML 加重启；数据库明文；数据库加密并发布运行时快照。
- **推荐：** 数据库加密保存，校验后原子发布，不回显密钥，失败保留旧快照。
- **结论：** 生产渠道账号集中持久化、加密保存并支持安全热发布；YAML 只用于本地开发或引导。
- **原因：** 允许不修改业务系统和不重启应用地迁移供应商，同时限制密钥暴露和半发布状态。

- **约束或不变量：** 运行日志、HTTP 日志和管理响应不含 secret；发布失败不得破坏当前可用配置。

- **替代/被替代：** 无

## LOG-014 — 2026-08-31T21:06:36+08:00 — 路由、灰度与故障切换
- **设计树节点：** D-014
- **轮次与依赖：** round 2 / D-008, D-009, D-012, D-013
- **状态：** confirmed
- **问题：** 平台如何选择渠道账号，并在 Provider 失败时决定是否切换？
- **事实与来源：** 用户对第二轮建议回复“采用全部”；底层当前只按 providerKey 选择 Provider，尚无平台路由或自动切换。
- **选项：** 固定默认账号；调用方指定；无条件依次重试；版本化路由与受控切换。
- **推荐：** 按应用、模板、渠道和目标区域匹配版本化规则，请求固定快照，只对明确可重试错误切换。
- **结论：** 平台拥有路由选择权；每个请求固定路由快照，每次 Provider attempt 独立记录，只有明确可重试错误进入备用路径。
- **原因：** 保证供应商迁移和灰度可审计，同时避免业务拒绝、参数错误等确定性失败被盲目重发。
- **影响工件：** CONTEXT / ADR / Spec / Ticket
- **约束或不变量：** 同一路由快照可重放解释；故障切换不能覆盖原 attempt；未知错误默认不切换。
- **后续：** Spec 定义路由优先级、错误分类、健康信号和最大 attempt。
- **替代/被替代：** 无

## LOG-015 — 2026-08-31T21:06:36+08:00 — 统一发送 API 合同
- **设计树节点：** D-015
- **轮次与依赖：** round 2 / D-008, D-009, D-010, D-011, D-012
- **状态：** confirmed
- **问题：** 同步、异步和状态查询使用什么稳定业务合同？
- **事实与来源：** 用户采纳推荐；现有 NotifyRequest 是 JVM 内部模型，直接对外暴露会泄漏 providerKey、审计策略和实现字段。
