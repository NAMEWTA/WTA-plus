课的隐含假设若反转，合格读者会把哪段走廊认错？

1. **「控制器方法名 `token` 就是 UseCase 方法名。」** 源码没有 `UseCase.token`。课误区 1。
2. **「换票会再读一遍 SSO Cookie 确认还是同一个人。」** `token()` 不调 `sessionUseCase`。身份冻在码行 `userId`。课误区 3。
3. **「`SsoTokenBo.token` 也能拿来换票。」** `TokenCommand` 五字段，无 token。反过来 revoke 不看 code。课误区 5。
4. **「revoke 等于跨 App SLO / 会删 Redis 手环。」** javadoc 与实现都否定；不调 `SsoSessionPort.delete`。课误区 2。要清手环走 L-057 `logout`。
5. **「verifier 差一个字符会把码打成已使用。」** verify 在 consume 之前；单测先失败再成功换出。课反例 1。
6. **「`findByCode` 失败和 `consume` 失败是同一件事。」** 前者没这行「授权码无效」，后者有这行但没抢到版本「授权码已使用」。课误区 4。
7. **「用 home 的 `client_id` 去换 admin 发出的码也能出票。」** 「授权码与客户端不匹配」；换错回调「授权码与回调地址不匹配」。课反例 2。
8. **「可以把认人厅自己（`sso`）当成业务 Client 签发。」** `SsoTokenExtras.bind` 拒绝。课反例 3 / 误区 6。
9. **「换票阶段还接受 PKCE `plain`。」** 换票只 `verify` 已存 S256 挑战，没有 method 字段。`requireS256` 是 L-055。课误区 7。
10. **「`grant_type=refresh_token` 是第二条合法分支。」** 唯一合法值 `authorization_code`。
11. **「换票体里的 `state` 还会再校验一次。」** `TokenCommand` 无 state；state 战场在授权请求。课图边界。
12. **「本课覆盖 `GET /authorize`，所以 (a) 整行可 covered。」** 发码是 L-055。把假设反转后，Lead 会用本行假闭合 PKCE 发码窗。
13. **「`PkceS256.verify` 失败就是矩阵 (d) fail-pkce。」** 该行备注只挂 L-055（授权时缺挑战 / 非 S256）。换票时校验失败是本窗负向，矩阵 **没有**「失败路径 换票」独行。
14. **「并发安全只靠 Java `if (consumed) throw`。」** 那是窗口期；真正互斥是 XML `consumed=0 AND version=?`。课变式 B。单测证人却是内存 CAS。
15. **「消费成功后 Client 被停用，码应仍可再换。」** `requireEnabledClient` 在 consume **之后**。失败则码已烧、票没发出。课写了「再查一遍目录」，没写成反例。
16. **「空白 revoke 在 Service 就会失败。」** 空白闸在适配器。课边界。
17. **「浏览器厅堂会打 `/sso/oauth2/revoke`。」** 磁盘上 admin/home 只打 `/token`；sso-web 只打 `/authorize`；前端零 revoke 调用方。撕票 HTTP 仍是本格门牌，不是前端格子。
18. **「`exchange` 会再调 `assertClientAccess`。」** 换票只 `buildLoginUser`。准入冻结在发码时（L-055）。
