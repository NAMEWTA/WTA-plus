## Confirmed gaps for the writer

1. **High: REDACT event-publisher failure still leaks caller-supplied request ID into an ordinary log.** `backend/wta-common/wta-common-notify/src/main/java/org/namewta/common/notify/core/NotifyDispatcher.java:292,307` logs `request.requestId()` in both `publish` and `publishDuplicate` catch blocks. `NotifyRequest.java:11-31` accepts an arbitrary caller-supplied request ID, and the new REDACT test deliberately sets it to the synthetic phone. A throwing `NotifyEventPublisher` makes that value appear in the warning log even though `NotifyDeliveryEvent` itself is sanitized. Use a fixed marker when `auditPolicy == REDACT_SENSITIVE`, retain the FULL log behavior, and assert canary absence from captured logs for both normal and duplicate publish failures. Existing `shouldNotChangeProviderResultWhenEventPublishingFails` tests only the non-sensitive path and result.
2. **Medium: REDACT event target `type` and `role` remain unclassified caller input.** `NotifyDispatcher.java:315-317,334-336` masks `NotifyTarget.value` but copies `type()`/`role()` in both request and result. `NotifyTarget.java:10` is a public record of three unrestricted strings. `validateTargets` checks type only for nonblank and adapter support; `role` is not validated (`NotifyDispatcher.java:231-243`). A caller/custom adapter can put a phone/OTP canary in `role`, and an adapter with broad support can also carry it in `type`; the serialized event then leaks it. Mask both for REDACT or enforce a closed safe vocabulary before preserving them. Add distinct type/role canaries and assert both event halves are clean.

Both findings were sent to `/root/cors_audit` and Lead while the writer was active.

## Conditional boundary needing Lead decision/evidence

An accepted `SmsNotificationReceipt.providerMessageId()` is copied unchanged by `SmsNotifyChannelAdapter.java:42-43`, persisted by `NotifyDispatchResultService.java:71-86`, and exposed in `NotificationDeliveryView.java:10-18`. A custom provider can return a synthetic phone/OTP as its message ID, defeating the absolute AC-035 management-snapshot absence assertion. The built-in provider ordinarily returns a serial, so this is a conditional untrusted-provider edge, not evidence that the built-in path leaks. Preserve the genuine ID needed for receipt correlation; either establish and test a provider-ID trust invariant or decide on a sensitive management projection. No projection change is within the current writer's declared production paths without Lead's write-set decision.

`NotifyTemplateRenderer.smsSnapshot` serializes scene code, provider template code and variable names. It excludes actual variable values, but those identifiers are not checked against a safe grammar by `NotifySendPlanner`; a configured identifier containing a sensitive canary would enter the snapshot. This does not affect the fixed CAPTCHA scene/template fixtures; if the contract covers arbitrary administrator-supplied identifiers, add an identifier-safety assertion or use a value-independent description.

### Identifier-source follow-up (read-only, 2026-09-23)

The concrete data flow narrows that conditional concern. `DispatchNotificationService.planChannel` takes `sceneCode` from the persisted intent (`NotificationApplicationRuntimeService.submit` copies `NotificationCommand.sceneCode`), then looks up a `NotifySceneBinding` by that scene/channel; the command's separately supplied `templateCode` is **not** the SMS provider template code used by the snapshot. `NotifySendPlanner.preflight` passes `sceneCode`, `binding.smsTemplateCode`, and `mapping.keySet()` to `smsSnapshot` (`DispatchNotificationService.java:226-235`; `NotifySendPlanner.java:97-122`). It sends `params.get(logical)` to the supplier as `smsParams` but never passes those values to `smsSnapshot`.

The supported configuration writer is `NotifyConfigController.saveBinding` behind `notify:config:edit`, through `NotifyConfigService.saveBinding` (`NotifyConfigController.java:130-138`; `NotifyConfigService.java:210-286`). That service allows only `NotifySceneCatalog.sceneCodes()` and mapping **keys** from that scene's declared variable names. The catalog has five literal scene codes; its variable names include `code`, `expireMinutes`, `title`, `content`, and `path`, not caller-provided values (`NotifySceneCatalog.java:15-68`). The SQL seed uses those fixed scene codes and declared mappings (`50-cde-base-dml.sql:1604+`). A notification submitter can provide arbitrary template parameter values, a business ID/phone and a command `templateCode`, but none enters these three snapshot inputs through this supported path. An arbitrary caller-supplied scene without a binding fails preflight before an SMS snapshot is made. The actual CAPTCHA, person-rebind and enterprise-transfer callers use literal scene codes.

The provider SMS template code is an administrator-managed binding identifier with a nonblank check, not a declared secret field; no source path was found that substitutes an OTP, phone, or template parameter value into it. A privileged operator or direct database mutation could deliberately store secret text there, but that possibility alone is not a T-35 data-flow defect or reason to expand the write set. **Conclusion:** no demonstrated normal-path raw-value leak from `smsSnapshot`; retain a regression test with distinct OTP/phone parameter canaries and verify they are absent from the snapshot. The earlier grammar suggestion is optional hardening, not a blocking finding on present evidence.
