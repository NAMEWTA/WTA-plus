## Required additions before AC-046 can be evidenced

1. **No late-delete-after-timeout proof.** The `delete` decorator waits up to 10 seconds on `releaseDelete`, then calls `super.delete(..., timeout)` (:268-280). The test releases the latch before awaiting the cleanup future (:320-325). This is a blocked but ultimately synchronous successful DELETE, not a caller timeout followed by a remote DELETE that completes late. If the test intentionally waits past the 5-second `properties.ioTimeout`, the decorator itself ignores that budget and only starts the real SDK request **after** release; it still does not model an in-flight remote call. Required negative: one controlled request/worker loses the caller's outcome, keeps the durable fence, later executes exactly one owned MinIO deletion, and proves no restore while unresolved, no second DELETE, and target remains readable. Do not infer that `Future.cancel` cancelled MinIO.
2. **No independent second-object progress while delete held.** Object 102 is published/restored before object 101 begins the blocked DELETE (:286-314). During the blocked object-101 DELETE, only a rejected `unpublish(101)` runs. Add a separate operation for object 102 *while* `deleteEntered` is held, require it to finish before `releaseDelete`, and verify its pointer/item and source/target bytes. This is the actual proof that per-object I/O does not serialize an entire batch.
3. **Reverse competition never reaches the shared-lock restoration path.** In the cleanup-first sequence, `service.unpublish(101)` is invoked after the cleanup reservation has already committed UNKNOWN. `findLatestRestorable` filters the item to null before `atomic.restore` (:321-323 and service :69-77). It proves the API refuses that state but does not prove a stale, eligible pre-read restoration is rechecked under the object lock after cleanup wins. Pause unpublish after it selects the eligible item/source exists but before `atomic.restore`; let cleanup reserve; then release unpublish and assert the proxied locked re-read vetoes it, with source/target/pointer intact as appropriate.
4. **Provider DELETE response loss is different from the present DB ACK fault.** After the database ACK test shows providerDeletes=0, the fixture manually calls `privateClient.delete(cleanupKey)` (:180) and then reconciles. This validates a missing-source readback, but no application `objectStore.delete` executed and lost its response. Add an owned decorator that calls `super.delete` once and then throws a controlled uncertain I/O error; assert durable UNKNOWN, same-target HEAD and one provider call; a later approved retry only HEAD/reconciles and does not send DELETE again. Preserve the existing DB commit-ACK negative separately.
5. The fixture has no explicit injected pointer-CAS/item-CAS zero-row rollback or producer crash during finalize; unit tests may cover some logic but AC's real transaction claim needs at least one two-row real MySQL failure to prove pointer+item atomicity. The current `ProxyFactory` composition also should be paired with a bean-level/static wiring check for the production `@Autowired` path; it is not a full Spring application context test.
