# 环境模式

| 模式 | 现场状态 | 允许的结果 |
|---|---|---|
| `audit` | 任意 | 只读盘点并生成报告 |
| `takeover` | 已存在 NAMEWTA 数据或服务 | 保留既有边界，只修复经过批准的差异 |
| `fresh-dev` | 独占且为空的根目录 | 初始化中间件并生成可直接开发的前后端配置 |
| `release-prod` | 独占生产目标 | 前后端版本化发布到统一入口，并记录 TLS 决策 |
| `upgrade` | 已纳管环境 | 完成备份、迁移、验证、升级和回滚点登记 |
| `rollback` | 存在兼容且验证过的备份 | 恢复指定版本及其兼容配置 |

只要存在持久化目录、Compose 项目、NAMEWTA 容器、数据库、桶或入口路由，就选择 `takeover`。只有证明既有状态可废弃并再次取得明确授权后，才可切换到 `fresh-dev`。

`fresh-dev` 应准备公共依赖与被忽略的本地配置，使开发者可以从源码启动前后端；这不代表已经满足生产要求。

`release-prod` 必须先明确 DNS、TLS、防火墙、备份、容量、凭据来源与监控责任人。除用户明确限定为局部修复外，生产发布必须同时覆盖前端和后端。

`upgrade` 与 `rollback` 必须遵循升级文档。应用代码回滚不等于数据回滚；先确认 Schema 兼容性，再决定是否恢复数据。

当前已知开发目标为 `172.16.105.9:22`，SSH 用户为 `root`，授权根目录为 `/data/namewta-data`。现场已有 NAMEWTA 部署，因此默认使用 `takeover`。同机 CDE 系统不在范围内；NAMEWTA Nacos 不暴露 `8848/9848`，统一从 `40080/nacos/` 访问。
