## Current facts that change the earlier handoff

- `NotifyNoticeUseCase.publish/retract` already carry `@DSTransactional`; `NotifyNoticeService.publish/retract` lock `notify_notice` but retract currently changes only lifecycle. `NotifyNoticePublisherService` creates a versioned `notify_notice_snapshot`, submits one `notice-published:<noticeId>:<version>` Intent, ignores the returned `NotificationReceipt`, and stores `/notify/notice?noticeId=...`. The public receipt ID is a **String**. Runtime uses the Intent ID as `notify_message.message_id` when IN_APP persists.
- `NotifyDispatchResultService.deadlineGateLocked` holds Intent→Outbox→Delivery, checks old PROCESSING provenance before deadline and unsupported-mode settlement, and is called by initial/second external gate, IN_APP begin/complete, and settle. `complete` deliberately does **not** re-run that gate: an already-entered external provider result must still be recorded. External proven-unsent requires the current claim to be from READY, the persisted `DEADLINE_UNSENT_READY` marker, zero Outbox/Delivery attempts, and no provider/accepted/delivered evidence. Historic READY/zero attempts alone is insufficient.
- T-41 `GET /notify/inbox/{messageId}` already proves the current user has a recipient relation; list is summary, detail has content. `InboxPage.vue` has session/request generation guards but only opens a row from the current page. `adminManifestRegistry.ts` has the host session port but no route-query port. Top-bar detail GET is also owner-checked; both its “查看业务” and full Inbox “查看业务” currently navigate stored paths verbatim.
- `NotifySceneCatalog.notice-published` requires `title`, `content`, **and `path`** for all channels. The seeded MAIL binding renders `${path}` and the seeded SMS mapping includes `path`. Therefore `path=null` before submit breaks valid external-only notices. `InAppNotificationService.resolveCategory` currently recognizes `/notify/notice`, not `/notify/inbox`.

## Minimal production sequence

1. **Publish, one version only.** Keep Notice row lock, allocate the next snapshot version, snapshot immutable title/content/audience, and use the existing stable Intent idempotency key. Put typed version provenance in Intent metadata while preserving `audit=NOTICE_SNAPSHOT`, for example `noticeVersion={noticeId,snapshotId,version,retracted:false}`. Pass a valid generic `templateParams.path='/notify/inbox'` to `submit`: this satisfies all channel preflight/rendering without promising a particular recipient message exists. Do not null it or change the shared scene catalog/SQL templates to make a test pass.
2. After `submit` returns, strictly parse `NotificationReceipt.notificationId()` as a positive signed-64-bit ID and verify the locked/new Intent identity (`appId=notify`, scene/template `notice-published`, `bizType=NOTICE_PUBLISHED`, `bizId=noticeId`, exact version key, metadata version). For publications containing IN_APP, conditionally update **three fields in the same publication transaction**: the new Intent `path_snapshot`, its `template_params_json.path` while preserving all other params, and the matching NoticeSnapshot `path_snapshot` to `/notify/inbox?messageId=<intentId>`. Require the intended affected row count for each conditional update and roll back all publication writes on failure. `dispatchInApp` reads `intent.pathSnapshot`; external MAIL/SMS render `template_params_json.path`, so both now use the same personal deep link. If external delivery arrives before the IN_APP relationship commits, or IN_APP ultimately fails, owner-scoped detail GET fails closed; it never falls back to management data. For MAIL/SMS-only, retain generic `/notify/inbox` in all three snapshots and never create a fictitious message detail link. Keep title/content and old version snapshot untouched. Verify that nested `NotificationApplicationUseCase.submit` participates in the same dynamic transaction through a real late-write failure test, not annotation inspection alone. Extend `InAppNotificationService.resolveCategory` to classify the exact new inbox deep-link shape as `notice`, while retaining old `/notify/notice` and workflow behavior.
3. **Retract, Notice→Intent lock order.** Under the already locked Notice, get the latest published snapshot, derive the exact version key, lock only that version's Intent by `(appId,key)` with a DAO current read, then cross-check notice ID, scene, biz type/id, key, snapshot ID/version and metadata. Persist `retracted=true` in this Intent's metadata, preserving audit/other metadata, inside the same transaction as the Notice lifecycle update. On an old Intent with metadata containing only the audit key, accept it **only** if all immutable key/business/snapshot identity checks match, then attach the version marker. Malformed/conflicting metadata, missing snapshot/Intent, or zero affected rows abort and roll back the lifecycle, **except** the two provable static DML seeds described below. Repeated retract checks the same version and is idempotent; publish V2 gets another key/Intent and cannot remove V1's marker. Do not call general `cancel`, bulk-update every `bizId`, overwrite Intent status as the fence, or lock all deliveries in the request.
   The six-SQL base DML inserts only notice IDs `1761800000000000001` and `1761800000000000002` as published static content and creates their V1 snapshots using `snapshot_id=notice_id`; it creates no Intent. A missing Intent permits lifecycle-only retract **only** for one of those exact IDs when the locked Notice is still the original PUBLISHED/ALL/IN_APP seed, the latest **and only** snapshot is V1 with matching `snapshot_id`, title/content/type and publication/create timestamps, and both exact-key and all `NOTICE_PUBLISHED` Intents for that notice are absent. Preserve the V1 snapshot. A repeat retract of this same verified seed is idempotent. Any mismatch, another snapshot/version, an Intent under a conflicting key, or any other notice with a missing Intent fails closed; it must not turn a lost publication task into a successful retract. This is not a tombstone or a global prohibition on an unrelated caller submitting its own notification. The DML's `INSERT ... SELECT` covers all PUBLISHED notices, so `snapshot_id=notice_id` alone never proves seed provenance.
4. **Worker and retry.** Read/validate the locked Intent's version fence inside `deadlineGateLocked`, after existing lease/provenance and terminal/durable IN_APP fact checks, before schedule/route/provider. If retracted: preserve ACCEPTED/DELIVERED/UNKNOWN and committed IN_APP message+relation; for a PENDING IN_APP with no durable relationship close it locally as CANCELLED/DONE without message, attempt, or push; orphan/inconsistent local facts use fixed local-inconsistency outcome. For external PENDING, only `provenExternalUnsent(...)` may become CANCELLED/DONE with a fixed safe reason; markerless/reclaimed/otherwise uncertain work becomes UNKNOWN/WAITING_RECEIPT without a new physical call. Keep T-39 expiry and T-50 unsupported precedence and live lease checks; no attempt/budget reset. In `retry`, after locking the Intent and before eligibility/requeue/wake, explicitly reject a retracted version. Duplicate same-key `submit` must never recreate or wake an old Intent; normal duplicate return remains the old receipt, and its retracted Outbox remains fenced. Other scenes and V2 remain unaffected.
5. **Already entered provider result.** Do not add a retraction check to `NotifyDispatchResultService.complete`, `writeResult`, callback, or the provider result adapter. A second gate that wins Intent lock has granted this lease execution rights; retract may commit while the mock provider is blocked. On release, the same lease still commits its real ACCEPTED/UNKNOWN/FAILED result and Attempt if its existing token/time fence remains valid. If retract wins before the second gate, the gate rejects and mock provider call count is zero. Maintain lock order and no result downgrade; status aggregation can change, but metadata fence persists.
6. **Personal deep link and old paths.** Add a host-owned route-query port to `NotifyWebRuntime` from `adminManifestRegistry.ts`; the reusable web-domain must not import Admin Router or read global location. The host supplies current query plus same-route changes and an unsubscribe. `InboxPage.vue` validates a single positive signed-64-bit decimal `messageId` (reject arrays, slash, zero and overflow), calls existing `service.inbox.detail(id)` independently of the current 20 rows, and uses its current session/detail generation to close/discard old identity or old query responses. A missing/foreign ID displays the normal owner-scoped detail failure; no management API fallback. Top-bar and full-page navigation translate **only** legacy `/notify/notice?noticeId=...` found on a detail returned for the current user's message into `/notify/inbox?messageId=<that message.messageId>`; never use the embedded `noticeId` to fetch management content or infer another version. Other business paths retain existing navigation. The Notice management retract confirmation explicitly says only not-yet-started sends are stopped; accepted/unknown/already-delivered facts cannot be recalled. No new permission is granted: normal user needs only `notify:inbox` own-detail access, not `notify:notice:query`.

## Activation cautions

The existing DML has external MAIL/SMS `path` requirements, so a null path is a deterministic regression. The old handoff's sentence “no IN_APP → null link” is superseded by a generic safe inbox landing path for external-only notices. This path does **not** claim a corresponding detail exists. Mixed-channel messages intentionally carry the personal deep link in both IN_APP and external templates; if the external message is seen first, its detail remains inaccessible until the IN_APP relation exists, and an IN_APP failure remains an ordinary owner-scoped 404/denial. The real transaction test must prove all three path fields are replaced before wake/worker sees the Intent. Historical already-retracted versions lacking a persisted per-version fence cannot be proven from current Notice lifecycle after a later republish; rollout must stop old workers and explicitly audit/fail closed on any active legacy notice tasks with ambiguous metadata, rather than infer safety from `bizId` or current lifecycle. No automatic resend of UNKNOWN is allowed.
