## Blocking finding

**P1 — a pre-provider local runtime failure is persisted as `UNKNOWN/WAITING_RECEIPT`.** `backend/wta-modules/wta-notify/src/main/java/org/namewta/notify/service/runtime/DispatchNotificationService.java:111-129` calls `planChannel` (including `NotifySendPlanner.finish` quota acquisition), constructs content/request, then enters `notifyClient.send`. Its catch at lines 168-171 unconditionally sets `UNKNOWN` and `DISPATCH_ERROR` for any `RuntimeException`. `NotifyDispatchResultService.java:86-90` converts `UNKNOWN` to `WAITING_RECEIPT`. A reachable example is `RedisNotifyQuotaAdapter.tryAcquire` throwing on Redis failure from `NotifySendPlanner.java:125-150,173-180`: no supplier call has begun, yet the task waits for a provider receipt that cannot exist. This contradicts AC-035's “本地错误无 WAITING_RECEIPT” and the revision150 pre-I/O phase contract. Existing tests cover returned quota denial and `NotifyValidationException`, but not a thrown pre-send quota/assembly failure (`DispatchNotificationServiceTest.java:195-230,243-263`; integration test's local cases use missing binding or invalid target).

Keep the phase boundary narrow for SMS: classify a generic failure before entering `NotifyClient.send` as a local FAILED with a stable nonterminal preparation error category (so existing bounded recovery can act), while retaining UNKNOWN for errors after entering the common client where provider I/O may have occurred. Known `NotifyValidationException` remains FAILED/DONE. Do not change MAIL/IN_APP or T-37's general resend logic as part of this finding. Add a throwing-quota/zero-supplier assertion and verify status/outbox in the isolated database. The previously present `providerInvocationStarted` distinction was removed in this candidate; a phase marker or equivalent scoped catch can restore the required distinction.
