# 通知内核的端口、适配器与插件实现

先给结论：这里的“插件”不是运行中上传一个 JAR 就能立即生效的热插件，而是**应用启动时，Spring 从 classpath 中发现渠道实现并组装起来的静态插件**。

整套机制由三层共同完成：

1. Java 接口规定插头形状，也就是端口。
2. Mail、SMS、system 等代码实现接口，也就是适配器。
3. Spring 自动装配收集这些实现，Registry 建立渠道路由表，也就是插件发现和注册。

## 先看全图

```text
[验证码、工作流等业务]
          |
          | 只调用 send(request)
          v
 [NotifyClient 输入端口]
          |
          v
 [NotifyDispatcher 通知内核]
          |
          +-- 校验请求
          +-- 处理幂等
          +-- 创建附件快照
          +-- 聚合发送结果
          +-- 发布监控事件
          |
          | 根据 channel 查路由表
          v
 [NotifyChannelRegistry]
          |
          +-- "mail" -> [Mail Adapter] -> [SMTP]
          |
          +-- "sms"  -> [SMS Adapter]  -> [SMS4J / 短信厂商]
          |
          +-- 未来渠道 -> [新 Adapter]  -> [新的外部系统]

通知内核还通过其他端口向外请求能力：

[NotifyDispatcher]
          |
          +-- [上下文端口] ------> [admin 读取登录人与 traceId]
          +-- [幂等存储端口] ----> [Redis 实现]
          +-- [附件快照端口] ----> [system + OSS 实现]
          +-- [日志编号端口] ----> [system 雪花 ID 实现]
          +-- [事件发布端口] ----> [Spring Event]
                                      |
                                      v
                              [system 异步监控落库]
```

最关键的依赖方向是：

```text
[通知内核] ------> [抽象接口]
                       ^
                       |
[Mail、SMS、system] ---+
```

内核不反向 import `MailBuilder`、SMS4J、`SysOssMapper`。外部实现主动遵守内核定义的接口，因此底层技术可以变化，核心流程不用跟着改。

## 一步一步看

### 第一步：业务从输入端口进入，不直接找 Mail 或 SMS

输入端口只有一个很小的接口：

```java
public interface NotifyClient {
    NotifyResult send(NotifyRequest request);
}
```

实际代码在：

`ruoyi-common/ruoyi-common-notify/.../core/NotifyClient.java`

`CaptchaController` 注入的是 `NotifyClient`，不是 `MailNotifyChannelAdapter` 或 `SmsNotifyChannelAdapter`：

```java
private final NotifyClient notifyClient;
```

发送短信验证码时，它把渠道写进请求：

```java
notifyClient.send(NotifyRequest.builder()
    .bizType("auth_captcha")
    .channel("sms")
    .providerKey("config1")
    .targets(List.of(NotifyTarget.phone(phoneNumber)))
    .content(...)
    .idempotencyKey(...)
    .build());
```

发送邮件时仍调用同一个端口，只把渠道改成 `mail`：

```text
[短信验证码] -> channel = "sms"  --+
                                      +-> [同一个 NotifyClient]
[邮件验证码] -> channel = "mail" --+
```

这说明业务选择“要做什么”，但不负责“用 SMS4J 还是 SMTP 怎样做”。

### 第二步：NotifyDispatcher 是内核，也是输入端口的默认实现

`NotifyDispatcher implements NotifyClient`。它的字段只依赖 Registry 和若干抽象端口：

```text
NotifyDispatcher
  +-- NotifyChannelRegistry
  +-- NotifyContextResolver
  +-- NotifyEventPublisher
  +-- NotifyIdempotencyCoordinator
  +-- NotifyAttachmentSnapshotService（可选）
  +-- NotifyLogIdGenerator（可选）
```

真实 `send` 方法的主线位于 `NotifyDispatcher.java:70` 附近：

```text
[收到 NotifyRequest]
          |
          v
[校验请求、去重附件 ID]
          |
          v
[Registry 按 channel 找 Adapter]
          |
          v
[校验目标类型：邮件地址或手机号]
          |
          v
[读取请求上下文]
          |
          v
[申请幂等占位]
          |
          v
[有附件时创建快照]
          |
          v
[Adapter.send(...)]
          |
          v
[校验并聚合每个目标的结果]
          |
          v
[完成幂等记录 + 发布投递事件]
          |
          v
[成功返回；失败抛出包含 NotifyResult 的异常]
```

对应的关键代码非常直接：

```java
NotifyChannelAdapter adapter = registry.require(request.channel());
validateTargets(request.targets(), adapter.supportedTargetTypes());
...
adapterResult = adapter.send(new NotifyAdapterRequest(request, context, snapshots));
...
NotifyResult result = aggregate(request, adapterResult);
publish(request, context, result, snapshotBatch);
return requireAccepted(result);
```

所以 Dispatcher 不是邮件发送器，也不是短信发送器。它像总调度台，保存所有渠道共同遵守的规则。

### 第三步：输出端口规定渠道插件必须长什么样

`NotifyChannelAdapter` 是渠道输出端口：

```java
public interface NotifyChannelAdapter {
    String channel();
    Set<String> supportedTargetTypes();
    NotifyAdapterResult send(NotifyAdapterRequest request);
}
```

三个方法分别回答：

```text
channel()                -> 你叫什么渠道？
supportedTargetTypes()   -> 你接受什么目标？
send(...)                -> 你怎样发送并返回统一结果？
```

内核只认识这份协议。它不知道实现类使用 SMTP、SMS4J、HTTP SDK，还是测试里的假对象。

### 第四步：Mail Adapter 把统一请求翻译成邮件技术

`MailNotifyChannelAdapter` 实现了输出端口：

```java
public final class MailNotifyChannelAdapter implements NotifyChannelAdapter {
    public static final String CHANNEL = "mail";
    public static final String PROVIDER = "smtp";
}
```

它声明只接受邮箱目标：

```java
return Set.of(NotifyTargetType.EMAIL);
```

收到统一请求后，它做的是“翻译”：

```text
[NotifyAdapterRequest]
          |
          +-- 邮件目标角色 -> TO / CC / BCC
          +-- 统一标题正文 -> MailNotificationMessage
          +-- OSS 附件快照 -> 本地临时文件
          |
          v
[MailNotificationSender]
          |
          v
[MailBuilder / SMTP]
          |
          v
[NotifyAdapterResult]
```

外部邮件库抛出的异常不会原样泄漏给内核。Adapter 把它翻译成统一的 `PROVIDER_ERROR` 和 `NotifyTargetResult.failed(...)`。

这正是“适配器”一词的含义：一边说统一通知语言，另一边说 SMTP 邮件语言。

### 第五步：SMS Adapter 用同一个端口翻译短信技术

`SmsNotifyChannelAdapter` 同样实现 `NotifyChannelAdapter`，但声明：

```java
channel()              -> "sms"
supportedTargetTypes() -> PHONE
```

它先根据 `providerKey` 找到具体短信 Provider，然后逐个手机号发送：

```text
[统一短信请求]
       |
       v
[ProviderResolver 按 providerKey 选择配置]
       |
       v
[SMS4J Provider Sender]
       |
       v
[每个手机号的成功或失败结果]
       |
       v
[统一 NotifyAdapterResult]
```

因此这里有两级选择：

```text
第一级：channel = sms  -> 选择 SMS Adapter
第二级：providerKey    -> SMS Adapter 内选择具体短信厂商配置
```

`channel` 是通知内核认识的渠道类型；`providerKey` 是渠道内部认识的供应商或账号配置。两者不能混成一个概念。

### 第六步：Spring Boot 怎样发现这些“插件”

每个相关 JAR 都有一个入口清单：

```text
META-INF/spring/
  org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

三个清单分别指向：

```text
[common-notify JAR] -> NotifyAutoConfiguration
[common-mail JAR]   -> MailConfig
[common-sms JAR]    -> SmsAutoConfiguration
```

启动时的完整过程是：

```text
[Maven 依赖把 JAR 放入 classpath]
                   |
                   v
[Spring Boot 读取 AutoConfiguration.imports]
                   |
                   v
[MailConfig / SmsAutoConfiguration 创建 Adapter Bean]
                   |
                   v
[NotifyAutoConfiguration 收集所有 NotifyChannelAdapter Bean]
                   |
                   v
[NotifyChannelRegistry 建立不可变 Map]
                   |
                   v
[NotifyDispatcher 被注册为 NotifyClient Bean]
```

收集插件的源码在 `NotifyAutoConfiguration.java:46` 附近：

```java
public NotifyChannelRegistry notifyChannelRegistry(
        ObjectProvider<NotifyChannelAdapter> adapters) {
    List<NotifyChannelAdapter> adapterList = adapters.orderedStream().toList();
    return new NotifyChannelRegistry(adapterList);
}
```

这里使用 `ObjectProvider` 的作用是：渠道可以是零个、一个或多个，通知内核不需要在构造函数里写死 Mail 和 SMS。

```text
错误的硬编码想法：
new Registry(mailAdapter, smsAdapter, feishuAdapter, ...)

当前实现：
Spring 容器里所有 NotifyChannelAdapter -> 自动收集
```

### 第七步：配置条件决定插件是否真正出现

Mail Adapter 不是只要 JAR 存在就一定注册。`MailConfig` 的链条是：

```text
[mail.enabled = true]
          |
          v
[创建 MailAccount]
          |
          v
[创建 MailNotificationSender]
          |
          v
[创建 MailNotifyChannelAdapter]
```

如果邮件未启用，这条 Bean 链不会成立，Registry 中也就没有 `mail`。

SMS 的 `SmsAutoConfiguration` 在模块存在时会创建 Resolver 和 Adapter。以后也可以为它增加配置条件，但当前代码没有类似 `sms.enabled` 的 Adapter 开关。

这说明插件能否使用取决于两道门：

```text
第一道门：实现模块是否在运行时 classpath？
第二道门：自动装配条件是否成立？
```

### 第八步：Registry 怎样把插件变成路由表

`NotifyChannelRegistry` 构造时遍历所有 Adapter：

```java
String channel = normalize(adapter.channel());
if (registry.putIfAbsent(channel, adapter) != null) {
    throw new IllegalStateException("重复的通知渠道 Adapter: " + channel);
}
```

最终得到类似这样的不可变 Map：

```text
{
  "mail" -> MailNotifyChannelAdapter,
  "sms"  -> SmsNotifyChannelAdapter
}
```

它还做了三项保护：

1. 渠道名不能为空。
2. 渠道名去空格并转成小写，因此 ` Mail ` 与 `mail` 视为同一个名字。
3. 两个插件声明同一个渠道时，应用启动失败，不允许随机选择。

真正发送时，`require(channel)` 查 Map。没有对应插件就抛出 `UNKNOWN_CHANNEL`：

```text
[request.channel = "feishu"]
             |
             v
[Registry 中没有 feishu]
             |
             v
[拒绝请求：UNKNOWN_CHANNEL]
```

### 第九步：为什么 `@ConditionalOnMissingBean` 很重要

通知内核为上下文、事件发布、幂等协调器和 `NotifyClient` 提供默认 Bean，但大多使用 `@ConditionalOnMissingBean`：

```text
[应用没有自定义实现] -> [使用 common-notify 默认实现]
[应用已有自定义实现] -> [默认实现退让]
```

例如 common-notify 默认返回空的 `NotifyContext`，但 admin 提供 `RequestNotifyContextResolver`，从当前登录用户读取 `userId`、`clientPk` 和 `traceId`。

这也是插件式装配的一部分：内核提供能运行的默认值，宿主应用可以替换与自身环境有关的能力。

### 第十步：system/notify 也是适配器区，不只是 Controller 和 Service

`system/notify` 没有负责 SMTP 或短信厂商调用，它实现的是依赖 system 数据和 OSS 的输出端口：

```text
[common-notify 定义端口]
          |
          +-- NotifyAttachmentSnapshotService
          +-- NotifyLogIdGenerator
          +-- NotifyDeliveryEvent
                    ^
                    |
[system/notify 提供实现]
          |
          +-- 复制 OSS 对象并登记临时附件
          +-- 使用系统雪花 ID 生成日志编号
          +-- 异步监听事件并写 sys_notify_log
```

以附件为例，`SystemNotifyAttachmentSnapshotService` 需要 `SysOssMapper`、对象存储和生命周期管理器。这些都是 system 掌握的能力，不应该让 common-notify 反向依赖 system。

投递完成后的监控链是：

```text
[Dispatcher 获得 Provider 结果]
          |
          +-- 返回同步结果
          |
          +-- 发布 NotifyDeliveryEvent
                         |
                         v
             [NotifyDeliveryEventListener]
                         |
                         v
               [monitorService.record]
```

监听器使用 `@Async` 和 `@EventListener`。监控落库失败只记录错误，不改变已经得到的 Provider 发送结果。这是“尽力记录”的旁路，不是可靠消息队列。

### 第十一步：依赖关系为何能阻止内核知道具体渠道

POM 的关键方向是：

```text
[common-mail] --depends on--> [common-notify]
[common-sms ] --depends on--> [common-notify]
[system     ] --depends on--> [common-notify]

[common-notify] --X--> [common-mail]
[common-notify] --X--> [common-sms]
[common-notify] --X--> [system]
```

所以 common-notify 可以编译接口和 Dispatcher，却不可能直接 import 后面三个模块的类。Maven 在编译期帮助守住依赖方向。

最后由可执行应用把零件放进同一个 Spring 容器：

```text
[ruoyi-admin 运行时]
  +-- 直接引入 common-mail
  +-- 直接引入 common-notify
  +-- 通过 system 获得 common-sms
  +-- 扫描 system/notify 组件
```

模块在磁盘上分开，运行时仍位于同一个 JVM。这是模块化单体中的插件组装，不是微服务远程调用。

### 第十二步：新增一个飞书渠道实际要做什么

假设要新增 `feishu`，正常路径是：

```text
[新模块依赖 common-notify]
          |
          v
[实现 NotifyChannelAdapter]
          |
          v
[channel() 返回 "feishu"]
          |
          v
[AutoConfiguration 创建 Adapter Bean]
          |
          v
[AutoConfiguration.imports 声明配置类]
          |
          v
[宿主应用引入新模块]
          |
          v
[Spring 启动时自动注册]
```

最小轮廓如下：

```java
public final class FeishuNotifyChannelAdapter implements NotifyChannelAdapter {
    public String channel() {
        return "feishu";
    }

    public Set<String> supportedTargetTypes() {
        return Set.of("feishu_user");
    }

    public NotifyAdapterResult send(NotifyAdapterRequest request) {
        // 把统一请求翻译给飞书 SDK，再翻译回统一结果。
    }
}
```

需要测试至少覆盖：

- `channel()` 和目标类型声明正确。
- 外部 Provider 成功、拒绝、抛异常时都返回正确的统一结果。
- 自动配置条件成立时 Bean 存在，不成立时 Bean 不存在。
- 与其他插件的 channel 不冲突。

不需要修改：

- `NotifyClient`
- `NotifyDispatcher.send`
- `NotifyChannelRegistry` 的路由算法
- 原有 Mail/SMS Adapter

这就是“对扩展开放、对核心修改收敛”的实际效果。

### 第十三步：它不是什么

当前实现有清楚的边界：

```text
它是：
[编译期接口约束] + [启动期 Spring 自动发现] + [发送期 Map 路由]

它不是：
[运行中上传 JAR] -> [无需重启立即加载]
```

新增或移除渠道 artifact 后，需要重新构建或调整部署依赖，并重启应用，让 Spring 重新建立 Bean 和 Registry。

它也不是消息队列式异步通知平台。`NotifyClient.send` 是同步调用；只有投递后的监控记录通过 Spring Event 异步旁路执行。

### 第十四步：失败分别发生在哪一层

```text
[启动阶段]
重复 channel -----------------> 启动失败

[请求校验阶段]
空 channel / 空目标 ----------> NotifyValidationException
未知 channel -----------------> UNKNOWN_CHANNEL
目标类型与渠道不匹配 ---------> UNSUPPORTED_TARGET_TYPE

[发送准备阶段]
附件快照未装配或创建失败 -----> 不调用 Provider
幂等冲突或正在发送 -----------> 拒绝重复执行

[Provider 阶段]
厂商拒绝或抛异常 -------------> 统一失败结果

[结果阶段]
全部成功 ---------------------> NotifyResult 返回
部分或全部失败 ---------------> NotifyDeliveryException 携带 NotifyResult

[监控旁路]
事件发布或落库失败 -----------> 记录日志，不篡改 Provider 结果
```

把失败放回所属层级，是这套结构的重要收益。业务不需要分别理解 SMTP 异常、SMS4J 异常和 system Mapper 异常。

## 术语小词典

- 插座（端口，Port）：核心规定的接口。它说明能做什么，不绑定具体技术。
- 转接头（适配器，Adapter）：实现端口，把统一语言翻译成 SMTP、SMS4J、OSS 等具体技术语言。
- 总调度台（Dispatcher）：执行所有渠道共用规则，再把请求交给选中的适配器。
- 渠道通讯录（Registry）：保存 `channel -> Adapter` 的不可变映射。
- 可替换功能件（插件，Plugin）：遵守同一扩展接口、可被宿主发现并加入系统的实现。本项目是启动期静态插件。
- 零件箱路径（classpath）：Java 应用启动时能找到的类和 JAR 集合。
- 自动组装说明（AutoConfiguration）：告诉 Spring 在什么条件下创建哪些 Bean。
- 容器里的对象（Bean）：由 Spring 创建、保存并注入给其他对象的实例。
- 等有需要再取对象（ObjectProvider）：Spring 提供的可选、多实例查找工具，这里用于收集全部渠道 Bean。
- 高层依赖接口（依赖倒置）：Dispatcher 依赖端口，Mail/SMS/system 反过来实现端口。
- 重复请求只执行一次（幂等）：相同业务操作重试时，避免再次调用 Provider。
- 当时版本副本（附件快照）：发送前复制一份附件，避免源文件后来变化或被删除。
- 尽力记录（best-effort）：监控失败不影响已经完成的外部发送，不承诺监控记录绝不丢失。
- 模块化单体：代码按模块分开，但最终在同一应用、同一 JVM 中运行。

## 你现在能复述什么

读完后，可以用下面四句话复述：

1. `NotifyClient` 是业务进入通知内核的输入端口，`NotifyChannelAdapter` 是内核调用外部渠道的输出端口。
2. Mail、SMS 和 system 依赖并实现 common-notify 的接口，common-notify 不反向依赖它们，所以依赖方向指向抽象。
3. Spring Boot 通过 `AutoConfiguration.imports` 创建 Adapter Bean，`ObjectProvider` 收集它们，Registry 再按 channel 建 Map；发送时 Dispatcher 查 Map 调用对应插件。
4. 这是启动期、classpath 内的静态插件架构。增加新渠道通常只需新增 Adapter 和自动配置，不改 Dispatcher，但部署后需要重启才能重新发现。

一句话压缩：

```text
业务给统一请求
    -> 内核处理共同规则
    -> Registry 按 channel 选插件
    -> Adapter 翻译并调用外部 Provider
    -> 内核返回统一结果并旁路记录监控
```
