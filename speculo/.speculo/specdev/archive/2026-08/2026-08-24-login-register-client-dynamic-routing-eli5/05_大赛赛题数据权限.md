# 大赛、赛题与报名数据权限

这篇图解分清两件事：

1. 当前框架中的 `sys_role.data_scope` 到底保存什么，怎样变成 SQL 条件。
2. “大赛负责人看整个大赛，赛题负责人只看负责赛题”应该怎样落地。

其中，第一部分是当前仓库已经存在的源码事实；第二部分是针对大赛业务的推荐设计，当前仓库尚无大赛、赛题和报名业务表实现。

## 先看全图

```text
第一层：能不能使用功能

[用户]
   |
   v
[当前 Client 下的角色]
   |
   v
[菜单或按钮权限码]
   |
   v
[能否调用“查看报名列表”接口]


第二层：调用成功后能看哪些报名记录

[平台大赛管理员] ----------------------> [全部大赛的报名]

[大赛 A 负责人] -> [负责关系：用户 -> 大赛 A] -> [大赛 A 的全部报名]

[赛题 A1 负责人] -> [负责关系：用户 -> 赛题 A1] -> [赛题 A1 的报名]

[普通报名用户] ------------------------> [自己的报名]
```

推荐的整体调用流：

```text
[用户请求报名列表]
          |
          v
[功能权限：有 registration:list 吗？]
          |
     +----+----+
     |         |
    没有       有
     |         |
     v         v
 [拒绝请求] [根据当前用户查负责范围]
                  |
          +-------+--------+----------------+
          |                |                |
          v                v                v
     [平台管理员]     [负责的大赛编号]   [负责的赛题编号]
          |                |                |
          +----------------+----------------+
                           |
                           v
                 [服务端生成 SQL 条件]
                           |
                           v
                 [数据库返回允许的报名]
```

最重要的结论是：

```text
角色 data_scope 字段 = 通用范围类型代码

大赛编号、赛题编号     = 业务资源范围

二者不是同一个东西，不能把赛题编号直接写进 data_scope。
```

## 一步一步看

### 第一步：`data_scope` 字段里实际写什么

当前字段位于角色表：

```text
sys_role.data_scope
```

它是一个字符串字段，但当前只允许保存 6 个代码中的一个：

```text
"1" = 全部数据权限
"2" = 自定数据权限
"3" = 本部门数据权限
"4" = 本部门及以下数据权限
"5" = 仅本人数据权限
"6" = 部门及以下或本人数据权限
```

它不保存下面这些内容：

```text
- 不保存 SQL
- 不保存 JSON
- 不保存用户编号
- 不保存大赛编号
- 不保存赛题编号
- 不保存一串允许访问的业务记录编号
```

例如数据库中：

```text
role_name = "数超大赛用户"
data_scope = "5"
```

这里只表达“这个角色使用仅本人模板”，并没有表达“本人是谁”或“本人负责哪些赛题”。当前初始化脚本中的“数超大赛用户”默认角色确实使用代码 `5`。

### 第二步：代码怎样解释这个字段

`DataScopeType` 把 6 个代码翻译成条件模板：

```text
代码 1 -> 不追加条件

代码 2 -> 部门列 IN (角色自选部门)

代码 3 -> 部门列 = 当前用户部门

代码 4 -> 部门列 IN (当前部门和全部子部门)

代码 5 -> 本人列 = 当前用户编号

代码 6 -> 部门列在范围内 OR 本人列等于当前用户编号
```

模板只知道两个抽象名字：

```text
deptName -> 哪一列代表部门

userName -> 哪一列代表本人
```

具体列名由每个 Mapper 的 `@DataPermission` 指定。例如：

```java
@DataPermission({
    @DataColumn(key = "deptName", value = "dept_id"),
    @DataColumn(key = "userName", value = "user_id")
})
```

如果角色的 `data_scope = "5"`，上面的映射最终近似产生：

```sql
user_id = 当前登录用户编号
```

因此“仅本人”并不天然代表创建人、报名人或负责人。它代表什么，取决于 Mapper 把 `userName` 映射到了哪一个数据库字段。

### 第三步：代码 2 的具体部门写在哪里

代码 `2` 表示“自定数据权限”，但勾选的部门编号也不写进 `data_scope`。它们单独保存在：

```text
sys_role_dept

role_id | dept_id
--------+--------
角色 10 | 部门 100
角色 10 | 部门 101
角色 10 | 部门 205
```

查询时，固定名字为 `sdss` 的服务根据角色编号读取这些部门：

```text
[角色编号]
     |
     v
[sys_role_dept]
     |
     v
[100, 101, 205]
     |
     v
dept_id IN (100, 101, 205)
```

所以：

```text
data_scope = "2"       只说明“使用自定部门模式”

sys_role_dept 多行记录  才说明“具体允许哪些部门”
```

`sys_role_dept` 的 `dept_id` 仍然是组织部门编号，不是一个可以随意改成赛题编号的通用资源字段。

### 第四步：登录时准备哪些材料

用户登录后，系统把数据权限需要的材料装进 `LoginUser`：

```text
[用户所属部门] --------------------> LoginUser.deptId

[当前 Client 下的角色和 dataScope] -> LoginUser.roles

[权限码对应哪些角色] -------------> LoginUser.dataScopeRoleMap
```

假设一个用户有两个角色：

```text
角色 10：报名审核员，data_scope = 3
角色 20：公告查看员，data_scope = 1
```

登录时还会形成类似的索引：

```text
competition:registration:list -> [角色 10]

system:notice:list             -> [角色 20]
```

当用户查询报名列表时，只让能授予 `competition:registration:list` 的角色参与数据范围计算。这样，“公告查看员”的全部范围不会错误地放大报名列表。

### 第五步：请求到 SQL 的完整现有链路

```text
1. Controller 权限注解
   @SaCheckPermission("competition:registration:list")
                     |
                     v
2. 先检查用户是否拥有这个功能权限
                     |
                     v
3. Mapper 方法上的 @DataPermission 声明部门列和本人列
                     |
                     v
4. 切面把注解放进当前调用上下文
                     |
                     v
5. MyBatis 拦截器读取 LoginUser 和接口权限码
                     |
                     v
6. 选出能授予当前接口权限的角色
                     |
                     v
7. 根据角色 data_scope 选择 SQL 模板
                     |
                     v
8. 把范围条件追加到原 SQL 的 WHERE
                     |
                     v
9. 数据库只返回满足条件的记录
```

例如原查询是：

```sql
SELECT *
FROM test_demo
WHERE status = '0'
```

角色范围为“仅本人”，Mapper 把本人列映射为 `user_id`，拦截后近似变成：

```sql
SELECT *
FROM test_demo
WHERE status = '0'
  AND (user_id = 9001)
```

这就是当前通用数据权限的核心实现：不是把数据全部查出来再隐藏，而是在 SQL 执行前追加条件。

### 第六步：为什么赛题负责人不能直接使用现有 1 到 6

你的规则是：

```text
大赛负责人 -> 看负责大赛下的全部报名

赛题负责人 -> 只看负责赛题下的报名
```

这里的范围轴是：

```text
competition_id 大赛编号

problem_id     赛题编号
```

当前 `DataScopeType` 模板只认识：

```text
deptName 部门列

userName 本人列
```

因此下面三种做法都不正确：

```text
错误一：把 problem_id 写进 sys_role.data_scope
原因：该字段只接受 1 到 6 的类型代码。

错误二：把赛题当作部门写进 sys_role_dept
原因：赛题不是组织部门，会污染部门树、人员归属和其他系统权限。

错误三：给赛题负责人使用“仅本人”
原因：报名记录通常由参赛者创建，赛题负责人并不是报名记录的创建人或报名人。
```

即使给 Mapper 增加：

```java
@DataColumn(key = "problemName", value = "problem_id")
```

当前 1 到 6 的任何 SQL 模板也没有引用 `problemName`，所以它不会自动产生赛题条件。

### 第七步：推荐的大赛业务数据模型

先让报名记录能够明确指出自己属于哪个大赛、哪个赛题：

```text
[competition 大赛]
competition_id
       |
       +--------------------------+
                                  |
                                  v
[competition_problem 赛题]   [registration 报名]
problem_id                   registration_id
competition_id               competition_id
       |                      problem_id
       +--------------------> applicant_user_id
```

再单独记录“谁负责什么”：

```text
[competition_manager 大赛负责人关系]
user_id | competition_id

[problem_manager 赛题负责人关系]
user_id | problem_id
```

示例数据：

```text
大赛：
A = 全国算法大赛
B = 全国建模大赛

赛题：
A1 = 路径规划题，属于大赛 A
A2 = 图像分类题，属于大赛 A
B1 = 城市预测题，属于大赛 B

负责人：
用户 100 = 大赛 A 负责人
用户 200 = 赛题 A1 负责人
用户 300 = 平台大赛管理员
```

关系表近似为：

```text
competition_manager
user_id | competition_id
100     | A

problem_manager
user_id | problem_id
200     | A1
```

这里不需要为每一个大赛、每一道赛题创建一个系统角色。角色负责表达“有哪类能力”，关系表负责表达“这项能力作用于哪些具体资源”。

### 第八步：角色和关系表怎样分工

建议至少区分这些功能身份：

```text
[平台大赛管理员角色]
可以使用：全部大赛管理、全部报名查询、导出、审核
资源范围：平台全部大赛

[大赛负责人角色]
可以使用：报名查询、导出、审核
资源范围：competition_manager 中分配给自己的大赛

[赛题负责人角色]
可以使用：报名查询、赛题审核
资源范围：problem_manager 中分配给自己的赛题

[普通大赛用户角色]
可以使用：提交报名、查看自己的报名
资源范围：registration.applicant_user_id = 当前用户编号
```

可以把它理解成两张证件：

```text
[角色证件]   说明“你有资格做报名审核”

[负责关系]   说明“你只能审核大赛 A 或赛题 A1”
```

缺少任何一张都不能访问：

```text
有功能角色，但没有负责关系 -> 返回零行

有负责关系，但没有功能权限 -> 接口直接拒绝
```

### 第九步：现实例子的最终可见结果

假设报名数据为：

```text
报名 R1 -> 大赛 A -> 赛题 A1
报名 R2 -> 大赛 A -> 赛题 A2
报名 R3 -> 大赛 B -> 赛题 B1
```

三个人查询同一个报名列表接口：

```text
用户 300：平台大赛管理员
结果 -> R1、R2、R3

用户 100：大赛 A 负责人
结果 -> R1、R2

用户 200：赛题 A1 负责人
结果 -> R1
```

对应的 SQL 思路是：

```sql
-- 平台大赛管理员
SELECT *
FROM registration;
```

```sql
-- 大赛负责人用户 100
SELECT r.*
FROM registration r
WHERE EXISTS (
    SELECT 1
    FROM competition_manager cm
    WHERE cm.user_id = 100
      AND cm.competition_id = r.competition_id
);
```

```sql
-- 赛题负责人用户 200
SELECT r.*
FROM registration r
WHERE EXISTS (
    SELECT 1
    FROM problem_manager pm
    WHERE pm.user_id = 200
      AND pm.problem_id = r.problem_id
);
```

如果一个人既是大赛 A 负责人，又是赛题 B1 负责人，查询范围取并集：

```sql
WHERE EXISTS (负责当前记录所属大赛)
   OR EXISTS (负责当前记录所属赛题)
```

他能看到 R1、R2、R3，但原因分别是：

```text
R1、R2 -> 来自大赛 A 负责人范围

R3     -> 来自赛题 B1 负责人范围
```

### 第十步：“大赛负责人看所有”有两种含义

“所有”必须先说清范围边界：

```text
含义一：看自己负责的大赛中的所有赛题和报名
        -> 使用 competition_manager 关系限制 competition_id

含义二：看平台上所有大赛、所有赛题和报名
        -> 这是平台大赛管理员，不追加大赛或赛题条件
```

不要把“大赛 A 负责人”角色的 `data_scope` 简单设置成 `1`，然后认为它只会看到大赛 A。代码 `1` 的真实含义是“不追加通用数据条件”；如果没有独立的 `competition_id` 业务过滤，他会看到整张报名表。

### 第十一步：推荐怎样接入当前项目

当前 1 到 6 是组织部门/本人范围，推荐保留它们的原用途。大赛业务先采用独立的业务范围查询：

```text
Controller
  |
  +-> 用 @SaCheckPermission 检查报名列表、导出、审核等功能权限
  |
  v
RegistrationService
  |
  +-> 从 LoginHelper 取得当前用户编号
  |
  +-> 判断是否为平台大赛管理员
  |
  +-> 查询该用户负责的大赛编号和赛题编号
  |
  +-> 构造统一 RegistrationScope
  |
  v
RegistrationMapper
  |
  +-> 把同一份范围条件用于列表、详情、导出、修改、删除
  |
  v
Database
```

这里最适合的第一版不是硬改 `sys_role.data_scope`，而是在大赛业务模块中建立统一的范围对象和查询构造器。原因是大赛、赛题和负责人关系属于大赛领域，不能让 `ruoyi-system` 反向依赖大赛业务表。

如果以后很多模块都有“项目负责人、设备负责人、数据集负责人”这种资源权限，再把它抽象成公共的资源范围插件；不要为了一个场景过早把部门权限改造成万能权限系统。

### 第十二步：所有数据入口必须使用同一范围

只限制列表是不够的。以下入口必须全部复用相同规则：

```text
- 分页列表
- 单条详情
- 导出
- 统计数量
- 审核
- 修改
- 删除
- 批量操作
```

错误示例：

```text
[列表按赛题过滤] -> 用户看不到 R2

[详情只按报名 ID 查询] -> 用户手改 URL 却能打开 R2
```

正确做法：

```text
[查询 R2 详情]
       |
       v
[报名 ID = R2 AND 当前用户负责其大赛或赛题]
       |
   +---+---+
   |       |
  命中    不命中
   |       |
   v       v
[返回]  [无权访问]
```

前端传来的 `competitionId`、`problemId` 只能是查询条件，不能作为权限证明。服务端必须自己根据当前登录用户查询负责人关系，并把“用户想查的范围”和“用户允许查的范围”取交集。

### 第十三步：一份可执行的管控清单

```text
1. 给角色分配正确的菜单和按钮权限
   -> 决定是否能调用报名查询、导出、审核接口

2. 给用户分配大赛负责人或赛题负责人角色
   -> 决定用户具备哪一类业务能力

3. 在负责人关系表中分配具体大赛或赛题
   -> 决定这项能力作用于哪些资源

4. 后端按当前用户生成资源范围
   -> 平台全部 / 大赛集合 / 赛题集合 / 本人

5. 每个读写 Mapper 都带上同一范围条件
   -> 防止列表安全但详情、导出或修改越权

6. 没有角色、没有分配、编号无效时返回零行或拒绝
   -> 失败时收紧，不默认放行

7. 测试至少覆盖三个人和三条报名
   -> 平台管理员看 3 条，大赛负责人看 2 条，赛题负责人看 1 条
```

### 第十四步：当前“数超大赛用户”的代码 5 能做什么

当前初始化脚本只创建了：

```text
competition Client
       |
       v
数超大赛用户默认角色，data_scope = "5"
       |
       v
数超大赛工作台权限 app:competition:workspace
```

仓库里尚无大赛报名 Mapper，所以代码 `5` 现在还没有自动产生“报名只能看本人”的业务 SQL。

未来如果普通参赛用户查询自己的报名，可以在报名 Mapper 中把本人列映射到报名人字段：

```text
userName -> r.applicant_user_id
```

这时默认角色的代码 `5` 才能近似产生：

```sql
r.applicant_user_id = 当前登录用户编号
```

但赛题负责人和大赛负责人仍应使用负责人关系范围，因为他们查看的报名不是他们本人提交的。

## 术语小词典

- 范围类型代码（`data_scope`）：角色上的 `1` 到 `6`，只说明使用哪一种通用部门/本人模板。
- 具体部门范围（`sys_role_dept`）：当代码为 `2` 时，记录角色实际勾选了哪些组织部门。
- 功能权限：决定用户能不能调用一个接口，例如查看或审核报名。
- 业务资源权限：决定用户能访问哪些具体大赛、赛题或报名。
- 负责人关系表：记录“哪个用户负责哪个大赛或赛题”的业务表。
- 数据归属字段：报名记录中的 `competition_id`、`problem_id` 和 `applicant_user_id`。
- 允许范围（Scope）：后端根据当前用户算出的可访问大赛集合和赛题集合。
- 范围交集：用户请求的筛选条件必须同时落在服务端允许范围内。
- 存在性判断（`EXISTS`）：数据库用来判断“是否存在一条负责人关系”的 SQL 写法。
- 失败时收紧（Fail Closed）：没有角色、没有负责人分配或规则异常时返回零行或拒绝，而不是放行全部记录。
- 横向越权：知道别人的报名编号后，通过详情、修改或导出接口访问不属于自己范围的数据。

## 你现在能复述什么

```text
问题一：data_scope 字段存什么？
答案：只存 1 到 6 的范围类型代码，不存大赛编号、赛题编号或 SQL。

问题二：代码 2 的具体范围存哪里？
答案：存 sys_role_dept，但那里保存的是组织部门，不应该拿来保存赛题。

问题三：大赛负责人怎样只看自己负责的大赛？
答案：用 competition_manager 记录用户与大赛关系，查询报名时限制 competition_id。

问题四：赛题负责人怎样只看负责赛题？
答案：用 problem_manager 记录用户与赛题关系，查询报名时限制 problem_id。

问题五：角色还有什么作用？
```
