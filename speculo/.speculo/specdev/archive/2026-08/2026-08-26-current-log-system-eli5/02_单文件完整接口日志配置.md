# 只保留 sys-console 的完整接口日志配置

## 先看全图

目标要拆成两个独立改动：

```text
[目标一：只保留一个日志文件]
              |
              v
[修改 logback-plus.xml]
  - 只写 sys-console.log
  - 每天滚动
  - 历史文件压缩为 .gz
  - 保留 60 天

[目标二：记录接口输入和输出]
              |
              v
[修改 Java Web 日志采集]
  - 现有拦截器记录请求
  - 新增响应 Advice 记录 JSON 响应
  - requestId 关联同一次调用
  - 跳过文件、流式响应和敏感字段
```

只修改 Logback XML，不能自动得到 HTTP 请求体和响应体。Logback 只负责接收 Java 代码已经发出的日志事件，并决定写到哪里。

当前 `sys-console.log` 的“完整”含义是：它接收 INFO、WARN、ERROR 三种级别。它并不表示每个接口的请求体和响应体都已经被完整采集。

## 一步一步看

### 第一步：把 Logback 收敛成一个文件

将 `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/src/main/resources/logback-plus.xml</Path>` 收敛为下面的结构：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <property name="log.path" value="./logs"/>
    <property name="console.log.pattern"
              value="%cyan(%d{yyyy-MM-dd HH:mm:ss}) %green([%thread]) %highlight(%-5level) %boldMagenta(%logger{36}%n) - %msg%n"/>
    <property name="log.pattern"
              value="%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n"/>

    <!-- 开发终端输出；它不会额外创建文件。 -->
    <appender name="console" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>${console.log.pattern}</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <!-- 唯一的文件日志。 -->
    <appender name="file_console" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${log.path}/sys-console.log</file>

        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <!-- .gz 后缀使历史日志在滚动时自动压缩。 -->
            <fileNamePattern>${log.path}/sys-console.%d{yyyy-MM-dd}.log.gz</fileNamePattern>
            <!-- 按天计算，保留最近 60 个历史周期。 -->
            <maxHistory>60</maxHistory>
            <!-- 防止 60 天内的超大请求日志无限占盘，容量按实际磁盘调整。 -->
            <totalSizeCap>20GB</totalSizeCap>
            <!-- 应用启动时也执行过期历史清理。 -->
            <cleanHistoryOnStart>true</cleanHistoryOnStart>
        </rollingPolicy>

        <encoder>
            <pattern>${log.pattern}</pattern>
            <charset>UTF-8</charset>
        </encoder>

        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>INFO</level>
        </filter>
    </appender>

    <root level="INFO">
        <appender-ref ref="console"/>
        <appender-ref ref="file_console"/>
    </root>
</configuration>
```

这份配置删除了：

- `file_info` 和 `async_info`，因此不再创建 `sys-info.log`。
- `file_error` 和 `async_error`，因此不再创建 `sys-error.log`。
- 旧的 `sys-console` 1 天历史设置。

结果是：

```text
当前正在写：sys-console.log
        |
        | 到第二天
        v
历史压缩：sys-console.2026-08-26.log.gz
        |
        | 超过 60 天或总历史超过 20GB
        v
自动清理
```

保留真正的 `console` appender，只表示开发终端仍能看到日志，不会产生第二个文件。如果生产环境连终端输出也不需要，可以再删除 `<appender-ref ref="console"/>`。

如果一天可能超过数 GB，推荐把滚动策略进一步改为 `SizeAndTimeBasedRollingPolicy`，让同一天按 100MB 或 500MB 分片；否则一天只形成一个很大的压缩包。

### 第二步：认识项目已经有的请求日志

项目现在并非完全没有接口日志：

```text
[HTTP 请求]
      |
      v
[RepeatableFilter]
  JSON 请求体缓存后可重复读取
      |
      v
[PlusWebInvokeTimeInterceptor.preHandle]
  记录 URL 和请求参数
      |
      v
[Controller]
      |
      v
[PlusWebInvokeTimeInterceptor.afterCompletion]
  记录耗时
```

实现位置：

- JSON 请求可重复读取：`<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-web/src/main/java/org/dromara/common/web/filter/RepeatableFilter.java</Path>`
- 请求体缓存包装器：`<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-web/src/main/java/org/dromara/common/web/filter/RepeatedlyRequestWrapper.java</Path>`
- 请求参数和耗时日志：`<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-web/src/main/java/org/dromara/common/web/interceptor/PlusWebInvokeTimeInterceptor.java</Path>`
- 拦截器注册：`<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-web/src/main/java/org/dromara/common/web/config/ResourcesConfig.java</Path>`

当前缺口是：

- 请求正文最多记录 4000 字符，因为 `MAX_PARAM_LOG_LENGTH=4000`。
- 只记录输入和耗时，不记录 JSON 响应正文。
- 没有给同一次请求生成统一 `requestId`。

因此不能只改 XML；还要扩展这条 Web 调用链。

### 第三步：把请求日志参数化

建议增加类型安全配置 `HttpLoggingProperties`，而不是继续使用代码中的固定常量：

```yaml
http-logging:
  enabled: true
  include-query-string: true
  include-request-body: true
  include-response-body: true
  max-body-length: 1048576
  excluded-paths:
    - /actuator/**
    - /resource/message/**
    - /resource/oss/**
    - /system/oss/**
  sensitive-fields:
    - password
    - oldPassword
    - newPassword
    - confirmPassword
    - token
    - accessToken
    - refreshToken
    - clientSecret
    - secret
```

推荐用 1 MiB 上限，而不是无限长度：

```text
[普通 JSON 请求或响应]
          |
          +-- 小于 1 MiB --> [完整记录，敏感字段脱敏]
          |
          +-- 超过 1 MiB --> [截断 + truncated=true + 原始长度]
```

如果把上限设成无限，一个返回几十万条数据的接口会同时制造大对象、超大日志字符串和磁盘写入压力。真正需要原样保存超大报文时，应写入权限受控的审计存储或对象存储，文件日志只记摘要、哈希和对象地址。

### 第四步：请求入口日志怎样改

继续使用 `PlusWebInvokeTimeInterceptor`，但调整为：

```text
preHandle:
  1. 读取客户端 X-Request-Id；没有就生成 UUID
  2. 把 requestId 放入 MDC 和 request attribute
  3. 读取 method、URI、query、JSON body
  4. 用 JSON 解析器递归删除 sensitive-fields
  5. 按 max-body-length 限制
  6. 输出一条 [HTTP_REQUEST] INFO 日志
```

建议日志保持单行 JSON，方便以后检索：

```json
{"event":"HTTP_REQUEST","requestId":"...","method":"POST","uri":"/system/user/add","query":{},"body":{"userName":"demo","password":"***"}}
```

不要记录全部请求头。只保留明确允许的字段，例如 `Content-Type`、`User-Agent` 和客户端标识；`Authorization`、Cookie、Token 一律不写原值。

请求结束时再输出状态和耗时：

```json
{"event":"HTTP_COMPLETE","requestId":"...","status":200,"costMs":38}
```

日志 pattern 可以增加 `%X{requestId}`，让普通业务日志也能与接口日志关联：

```xml
<property name="log.pattern"
          value="%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level [%X{requestId}] %logger{36} - %msg%n"/>
```

请求完成后必须在 `finally` 或 `afterCompletion` 中执行 `MDC.remove("requestId")`，否则线程复用时可能把上一请求的编号带给下一请求。

### 第五步：响应日志怎样补上

对这个仓库，优先新增一个 JSON 响应 Advice，而不是无条件缓存 Servlet 的所有响应字节：

```text
[Controller 返回对象]
          |
          v
[ResponseEnhancementAdvice]
  完成翻译、脱敏等现有增强
          |
          v
[HttpResponseLoggingAdvice]
  只处理 application/json
  读取 requestId
  JSON 序列化、敏感字段清理、长度限制
  输出 [HTTP_RESPONSE]
          |
          v
[HttpMessageConverter 写给客户端]
```

建议新增位置：

`<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-web/src/main/java/org/dromara/common/web/advice/HttpResponseLoggingAdvice.java</Path>`

响应日志示例：

```json
{"event":"HTTP_RESPONSE","requestId":"...","status":200,"body":{"code":200,"msg":"操作成功","data":{"userId":1001}}}
```

Advice 只支持 JSON 响应，明确跳过：

- `application/octet-stream` 下载。
- Excel、ZIP、PDF、图片等二进制输出。
- SSE 和其他流式响应。
- `Resource`、`byte[]`、文件上传正文。
- Actuator、静态资源和配置中的排除路径。

这是比 `ContentCachingResponseWrapper` 更适合当前仓库的第一版，因为仓库存在大量直接写 `HttpServletResponse` 的 Excel 和代码生成下载接口。无条件包装响应会先把大文件缓存在 JVM 内存中，增加内存溢出和流式响应失效风险。

如果将来必须记录“最终发送出去的精确字节”，才考虑 `ContentCachingResponseWrapper`，但只能应用于已确认的小型 JSON 路径，并且在 `finally` 中调用 `copyBodyToResponse()`；不能全局套在下载和流式接口上。

### 第六步：确保生产环境仍输出接口 INFO 日志

当前 Maven profile 中：

```text
local / dev -> org.dromara = INFO
prod        -> org.dromara = WARN
```

如果接口采集日志使用 INFO，而生产 profile 把整个 `org.dromara` 提高到 WARN，那么生产环境不会记录这些请求和响应。

在 `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/src/main/resources/application.yml</Path>` 中给日志采集类单独设置 INFO，例如：

```yaml
logging:
  level:
    org.dromara: @logging.level@
    org.dromara.common.web.interceptor.PlusWebInvokeTimeInterceptor: info
    org.dromara.common.web.advice.HttpResponseLoggingAdvice: info
    org.springframework: warn
    org.mybatis.spring.mapper: error
    org.apache.fury: warn
  config: classpath:logback-plus.xml
```

这样生产环境中的普通业务 INFO 仍可被压到 WARN，但接口请求/响应日志继续进入 `sys-console.log`。

### 第七步：`@Log` 是否还需要

建议保留：

```text
sys-console.log
  -> 程序排错、完整调用上下文、短期文件保留

sys_oper_log
  -> 谁做了什么业务动作、后台筛选、审计追责
```

它们解决的问题不同。只保留一个文件日志，不代表应删除 `@Log` 的数据库业务审计。

为了避免敏感内容重复保存，敏感接口可以这样使用：

```java
@Log(
    title = "敏感业务",
    businessType = BusinessType.UPDATE,
    isSaveRequestData = false,
    isSaveResponseData = false
)
```

这仍记录操作者、URL、方法、结果和耗时，但不把正文再次写入 `sys_oper_log`。

### 第八步：推荐的最终落地顺序

```text
1. 改 logback-plus.xml
   只保留 sys-console，60 天压缩轮转
                |
                v
2. 增加 HttpLoggingProperties
   开关、长度、排除路径、敏感字段
                |
                v
3. 改 PlusWebInvokeTimeInterceptor
   requestId、完整 JSON 请求、结构化脱敏
                |
                v
4. 新增 HttpResponseLoggingAdvice
   只记录 JSON，跳过文件和流
                |
                v
5. 给两个采集类单独配置 INFO
                |
                v
6. 测试正常、异常、敏感、超长、下载和 SSE
```

最低验收应覆盖：

- GET query、POST JSON 的输入能够记录。
- 正常响应和全局异常响应能够记录。
- 同一次调用的三条日志具有相同 `requestId`。
- 密码、Token、Cookie、Client Secret 不出现原值。
- 超长正文有明确截断标记，不悄悄丢失。
- Excel、ZIP、图片、OSS、SSE 不记录二进制正文且功能不受影响。
- 第二天产生 `.log.gz` 历史文件。
- 超过 60 天和总容量上限的历史能够清理。
- 不再产生新的 `sys-info.log` 和 `sys-error.log`。

## 术语小词典

- 日志分流配置（Logback XML）：决定日志文件名、级别、滚动和保留，不负责主动读取 HTTP 正文。
- 接口入口检查员（Interceptor）：Controller 执行前后运行，可读取请求信息、状态和耗时。
- 响应发出前检查员（ResponseBodyAdvice）：JSON 对象交给转换器前运行，适合记录普通接口返回值。
- 同一次调用编号（requestId）：把请求、响应和中间业务日志串在一起的唯一编号。
- 线程随身标签（MDC）：把 requestId 临时附加到当前线程日志上的机制。
- 敏感字段遮盖（脱敏）：把密码、Token、Secret 等替换为 `***`，而不是写入原值。
- 正文长度上限（max-body-length）：限制单条日志大小，超过时保留长度和截断标记。
- 流式响应（SSE/streaming）：数据持续发送、不能先全部缓存再一次性输出的响应。
- 每天换文件并压缩（滚动压缩）：当前文件继续写，历史文件按日期改名并变成 `.gz`。

## 你现在能复述什么

1. 只保留 `sys-console.log`、每天压缩、保留 60 天，可以通过精简 `logback-plus.xml` 完成。
2. 完整请求和响应不是 Logback 配置能力；当前项目已有请求拦截器，还需参数化它并增加 JSON 响应 Advice。
3. “完整”应定义为普通 JSON 在安全长度内完整记录，同时必须脱敏并排除下载、上传和流式响应；无限制记录所有字节不是可接受的生产方案。

```text
只想改文件名和保留天数？ -> [改 Logback XML]

还想看到请求体和响应体？ -> [必须增加或修改 Java 采集逻辑]
```
