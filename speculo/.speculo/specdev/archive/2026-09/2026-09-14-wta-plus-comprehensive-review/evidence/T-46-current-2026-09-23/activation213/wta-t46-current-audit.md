## Concrete race and affected entries

`OssStorageMigrationService.unpublish` (`:51–72`) obtains a restorable item and checks source existence **before** any object lock, then CASes `sys_oss.service` back to source and calls `store.saveItem`. `cleanup` (`:186–221`) snapshots all items/window once, then calls `objectStore.delete(sourceConfigKey, objectKey)` without locking/reloading either `sys_oss` or item. Interleaving `cleanup`'s pre-read before `unpublish`'s CAS permits external deletion of the source after that source becomes the current pointer. `rollback` (`:159–181`) has the same unlocked restore path; `process` (`:225–283`) claims an item and switches/restores the pointer via CAS without the common Object→Item lock, while a different cleanup/restore can act. `MybatisOssMigrationStore.saveItem/saveBatch` ignore `updateById` row counts, and item `version` is incremented by `claim` but not checked by later `saveItem`, so stale success/failure state can overwrite a changed item.

`SysOssMapper.selectByIdForUpdate` and `selectByIdsForUpdate` already provide object row locks; `OssLifecycleManager.cleanupExpired` already locks the object before deleting its **current** service. It should participate by that existing object lock once migration paths use the same lock, without an unrelated lifecycle rewrite. `SysOssServiceImpl` writes service only when inserting a new object; upload cleanup is for an unregistered upload ticket. The relevant external entry points are `SysOssController` publish/unpublish and `SysOssMigrationController` start/retry/rollback/cleanup. They already have backend permissions and safe `@Log`; no new endpoint or menu is needed. `OssPage.vue` already says restoring the private pointer leaves the public copy and URL in place; no claim should be made that unpublish retracts public bytes.

`findLatestRestorable` currently filters to `CLEANUP_ELIGIBLE` **before** ordering. If a newer same-object cleanup is unknown/failed, it can return an older eligible item and permit an unsafe restore. A new read must consider the latest item and any unresolved cleanup fence for that object before accepting the restorable candidate. `rollback` currently accepts a nonterminal `FAILED` item, so it too must reject an unresolved cleanup outcome. `retry()` currently excludes `FAILED` with `lastErrorStage=COMPLETED`, which is a useful existing boundary.

## Minimal safe serialization and unknown-delete fence

For every pointer-changing/restore/cleanup decision, enter a Spring-proxied public `@DSTransactional` **single-object** boundary, lock the `sys_oss` row first, then the matching migration item row, then re-read current service, key, item stage/status/version, cleanup eligibility/window and target/source existence as needed. Reject an item whose `objectKey`/ossId/source/target no longer matches the locked object. Use exact-one conditional writes with expected version/status for the item and the existing service CAS; zero rows means conflict/rollback, not a successful request. Do not hold the whole batch's rows/locks while one object is copied, probed or deleted. A private same-class method or self-invocation would not activate `@DSTransactional`; use an actually proxied service boundary or project-supported transaction template, with real proxy tests.

The existing `FAILED + lastErrorStage=COMPLETED + fixed errorMessage` fields can encode `CLEANUP_OUTCOME_UNKNOWN` without a new table or global state machine, **but current code does not use them as a durable fence**. Before issuing a source DELETE, commit an Object→Item guarded state transition to this conservative code; if that commit is unacknowledged, confirm it by readback or do not issue DELETE. Then perform bounded external I/O; after a definitive result, acquire Object→Item locks again, re-read and conditionally mark `COMPLETED`. If the DELETE or final DB commit is uncertain, leave the precommitted fence. Every `unpublish`, `rollback`, `process` pointer switch and later cleanup retry must reject or conservatively reconcile this fence; an older eligible item may not bypass it. A crash before issuing DELETE leaves a conservative manual/retry case, which is safer than restoring a source that may be deleted later. A 200/timeout/exception from an external provider alone cannot prove whether bytes were deleted. On controlled retry, confirm current pointer/target and source existence under the fence before any further delete; never restore the source until the late-delete possibility is resolved. If source is absent and target/current item still agree, idempotent completion may be recorded. If not provable, retain the fixed unknown code for operator review. External deletion cannot be rolled back by the DB transaction.

Holding only a DB row lock across external DELETE is insufficient if the call times out or commit acknowledgement is lost: releasing the lock would let a restore occur while the provider may still delete later. The precommitted fence is the minimal crash-persistent answer within the existing item state. The two short transactions also avoid pretending that a long provider request is a short transaction. The batch may iterate items, but each item must own its own transaction/fence; a blocked item must not lock another object's row.

## Strict timeout gap and exact possible scope expansion

`DefaultOssMigrationObjectStore.delete` calls `OssFactory.instance(service).delete(key)`. `wta-common-oss/.../client/AbstractOssClientImpl.bucketDelete` calls `s3AsyncClient.deleteObject(...).join()`; `DefaultOssClientImpl` configures Netty connection 60 s / connection acquisition 30 s but no visible total API-call timeout. An outer `Future.get(timeout)` is **not** proof that underlying DELETE stopped; it can finish after the DB lock is released. The durable item fence makes such a late effect safe for the current pointer, but it does not satisfy an operational total-call/cancellation guarantee or reclaim an orphaned call.

If the required strict call deadline is implemented at the common OSS client, pre-register the exact public `backend/wta-common/wta-common-oss/src/main/java/org/namewta/common/oss/client/OssClient.java` and implementation `.../AbstractOssClientImpl.java`, plus `.../DefaultOssClientImpl.java` only if SDK client-level configuration is actually needed. Prefer a per-operation SDK-enforced total timeout/cancellation with a bounded delete method; verify its behavior against the local SDK and real MinIO before promising that no late DELETE occurs. Synchronize common OSS tests/consumers if the public method changes. The already authorized `migration/` root covers its adapter/interface/result/fixed error code; `SysOssMapper.java` and `SysOssMapper.xml` cover object locks/CAS. If the durable fence is the chosen safety mechanism, still record that timeout is UNKNOWN and restoration remains blocked; do not claim outer-thread timeout cancels S3.

## Required real verification, not covered by the old test

The existing `OssStorageMigrationIntegrationTest` uses a single `SqlSession` opened with auto-commit and verifies a sequential two-bucket flow. It does **not** prove two independent JDBC transactions, actual `@DSTransactional` proxying, blocking lock order, timeout, rollback after external I/O, or lost commit acknowledgement. Add its scenarios under the Ticket's existing Admin `oss/migration/` test root, using two physical MySQL connections/threads, observed connection IDs and bounded lock waits; a `CountDownLatch`-controlled `OssMigrationObjectStore` or verifier should pause at the exact boundary. Do not accept mere thread scheduling as proof of a row lock.

1. **Restore first:** A locks Object→Item and pauses before commit; B cleanup attempts Object lock and demonstrably blocks. After A commits pointer=source/item=ROLLED_BACK, B re-reads and rejects with zero provider DELETE calls. MinIO HEAD of source remains successful; public target copy remains readable.
2. **Cleanup first:** A persists the unknown-delete fence, then pauses before/at external DELETE; B unpublish and batch rollback, including an older eligible item, must refuse restoration. After A's definitive delete/finalize, source is absent, target exists, pointer remains target and item is `COMPLETED`. With a second independent object, prove A's block did not hold that object's row/batch transaction.
3. **Failure/uncertainty:** inject item update rowcount 0, service CAS 0, DB rollback and commit-ack loss; if pre-delete fence is unconfirmed there must be zero DELETE. Inject delayed/timeout DELETE that succeeds after caller uncertainty: fixed UNKNOWN fence persists, restores reject even after DB lock release, and a controlled retry/readback converges only after source/target/pointer checks. Assert no claimed success on missing item row, no blind second delete, and no current-source loss. Check interrupted/timeout resources are bounded and cleaned.
4. Run the relevant migration unit/integration consumers with fresh positive zero-skip XML against owned MySQL/Redis/MinIO and a fixed clean source/JAR; retain before/after object HEAD/GET, row states/versions and exact cleanup. Existing T-44's single sequential MinIO pass cannot substitute for this competition matrix.

The Ticket's present migration directory, `SysOssMapper`/XML, Admin migration tests and optional `OssPage.vue` cover the main product work. The common OSS timeout paths above are the only likely production write-set expansion; controller/HTTP/SQL schema changes are not required by the accepted minimal design. The proposed fence is a design finding for Lead/writer review, not a claim that T-46 is implemented or verified.
