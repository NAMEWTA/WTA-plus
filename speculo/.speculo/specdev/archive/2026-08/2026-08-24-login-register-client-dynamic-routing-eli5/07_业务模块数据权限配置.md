# 业务子模块的数据权限配置

这篇图解回答：

1. 每个业务子模块的数据权限是不是都要从头定制？
2. `ruoyi-tokenhub` 应不应该复制一套角色表？
3. Client、角色、菜单权限和业务资源范围分别在哪里配置？
4. 固定角色和可配置角色分别需要哪些业务表？

当前仓库尚不存在 `ruoyi-tokenhub` 目录或 Maven 模块。下面的 TokenHub 目录、类和 `th_*` 表均为建议方案；当前已存在的是 `competition` Client、“数超大赛用户”默认角色和工作台菜单初始化。

## 先看全图

推荐把权限拆成三层：

```text
第一层：从哪个应用入口登录

[sys_client]
competition Client
登录域、访问路径、默认角色、Token 配置
             |
             v
第二层：能使用哪些功能

[sys_role] -> [sys_role_menu] -> [sys_menu]
当前 Client 的角色               TokenHub 菜单和按钮权限码
             |
             v
第三层：能操作哪些业务资源

[TokenHub 范围策略] -> [TokenHub 资源授权关系]
全部/本人/负责大赛/负责赛题   用户具体负责哪些大赛或赛题
             |
             v
[TokenHub 查询统一追加业务 WHERE]
```

模块所有权如下：

```text
[ruoyi-system 拥有]
sys_client
sys_role
sys_menu
sys_role_menu
sys_user_role
登录会话 LoginUser
         |
         | 当前用户编号、当前 Client、当前 Client 下的角色和权限
         v
[ruoyi-tokenhub 拥有]
大赛、赛题、报名
大赛负责人、赛题负责人
TokenHub 范围解析与 SQL 条件
```

最重要的结论：

```text
不要在每个业务模块复制一套 sys_role。

角色继续由 system 统一管理；
业务模块只保存“角色或用户怎样作用于本模块资源”的扩展信息。
```

## 一步一步看

### 第一步：哪些能力是所有模块共用的

不同业务模块不需要重新开发下面这些基础能力：

```text
- 用户登录和 Token
- 当前登录用户编号
- 当前 Client 上下文
- 角色分配
- 菜单和按钮权限
- Controller 的功能权限检查
- MyBatis 查询基础设施
- 超级管理员识别
```

这些已经由 `ruoyi-system`、`ruoyi-api` 和 `ruoyi-common-*` 提供。

业务模块真正不同的是：

```text
TokenHub：大赛、赛题、报名

工作流：流程、任务、办理人

数据采集：数据集、采集任务、设备

AI：知识库、会话、模型资源
```

所以每个模块都要定义自己的“业务资源怎样归属”，但不需要复制整套认证和角色系统。

可以把它理解为：

```text
[公共门禁系统] -> 每栋楼共用刷卡规则

[业务资源规则] -> 每栋楼自己定义房间和可进入区域
```

### 第二步：Client 的真实作用

当前 `Client` 主要定义一个登录和权限上下文：

```text
sys_client
  |
  +-> 使用哪个登录域
  +-> 是否允许注册
  +-> 默认角色
  +-> 允许访问路径
  +-> Token 有效期
```

角色和菜单都带 `client_id`：

```text
[competition Client]
       |
       +-> [数超大赛用户角色]
       +-> [TokenHub 大赛负责人角色]
       +-> [TokenHub 赛题负责人角色]
       +-> [TokenHub 平台管理员角色]
       |
       +-> [大赛工作台菜单]
       +-> [报名列表权限]
       +-> [报名审核权限]
       +-> [报名导出权限]
```

登录查询角色时，系统使用：

```text
user_id + 当前 client_id
```

只加载角色表中属于当前 Client 的角色。默认角色还会按 Client 自动合并到登录会话，不要求写入 `sys_user_role`。

因此，同一个用户进入两个 Client 时可以得到两套不同角色：

```text
[用户 100]
    |
    +-> 登录管理后台 Client -> 系统管理员角色
    |
    +-> 登录 competition Client -> 大赛负责人角色
```

但必须避免一个常见误解：

```text
Client != 租户
Client != 自动的数据隔离字段
Client != 大赛编号
```

Client 只保证当前会话使用当前 Client 的角色和菜单。某行报名属于哪个大赛，仍由 TokenHub 的 `competition_id` 决定。

只有业务明确规定“不同 Client 的数据永远互不共享”时，才应在业务表中增加并校验业务意义上的 `client_id`。不要因为系统有 Client 就机械地给所有业务数据按 Client 分区。

### 第三步：角色和功能权限继续放在 system

TokenHub 不需要创建下面这种重复表：

```text
错误方向：
th_role
th_role_menu
th_user_role
```

复制后会产生两套角色真相：

```text
system 认为用户有角色 A

TokenHub 又认为用户有角色 B

登录、菜单、按钮、接口和数据范围很容易互相不一致
```

正确方向是继续使用：

```text
sys_role      -> 角色名称、roleKey、client_id
sys_menu      -> 页面和按钮权限码、client_id
sys_role_menu -> 角色能使用哪些功能
sys_user_role -> 用户显式拥有哪些角色
```

TokenHub 角色配置示例：

```text
角色：tokenhub_participant
Client：competition
权限：报名提交、查看本人报名

角色：tokenhub_competition_manager
Client：competition
权限：报名列表、报名审核、报名导出

角色：tokenhub_problem_manager
Client：competition
权限：报名列表、赛题审核

角色：tokenhub_platform_admin
Client：competition
权限：TokenHub 全部管理功能
```

这里的角色回答：

```text
“有没有资格执行这类操作？”
```

它还没有回答：

```text
“具体可以操作大赛 A 还是大赛 B？”
```

### 第四步：`sys_role.data_scope` 在 TokenHub 中怎样处理

不要把 TokenHub 的范围模式写成：

```text
data_scope = "COMPETITION"
data_scope = "PROBLEM"
data_scope = "A1,A2,A3"
```

当前字段只接受通用代码 `1` 到 `6`，用于全部、部门和本人模板。

TokenHub 有两类权限可以直接复用：

```text
普通参赛者只看本人报名
-> 可复用代码 5，但 Mapper 必须把 userName 映射到 applicant_user_id

平台管理员看全部 TokenHub 数据
-> 可使用代码 1，但前提是真正允许查看平台全部数据
```

下面两类不能靠现有字段表达：

```text
大赛负责人 -> 负责的大赛集合

赛题负责人 -> 负责的赛题集合
```

这些需要 TokenHub 自己的业务范围。

如果 TokenHub 统一使用独立业务范围解析器，`sys_role.data_scope` 不再是 TokenHub 资源范围的权威。它仍可以控制该角色访问其他使用通用部门/本人注解的接口。

特别注意：

```text
data_scope = 1 的意思是“不追加通用部门/本人过滤”，
不是“只看分配给自己的全部大赛”。
```

所以 TokenHub 查询必须先带上自己的业务范围；不能把安全寄托在这个字段上。

### 第五步：固定角色方案不需要角色扩展表

如果 TokenHub 的角色种类固定，并且不会让管理员自由组合范围模式，可以直接约定：

```text
tokenhub_platform_admin      -> ALL
tokenhub_competition_manager -> ASSIGNED_COMPETITION
tokenhub_problem_manager     -> ASSIGNED_PROBLEM
tokenhub_participant         -> SELF
```

然后只建立具体负责人关系：

```text
th_competition_manager
----------------------
user_id
competition_id
status

th_problem_manager
------------------
user_id
problem_id
status
```

TokenHub 根据当前会话中的 `roleKey` 选择范围模式：

```text
[当前角色集合]
       |
       +-> 有 platform_admin -> 全部
       |
       +-> 有 competition_manager -> 查负责的大赛
       |
       +-> 有 problem_manager -> 查负责的赛题
       |
       +-> 有 participant -> 查本人报名
```

优点：

```text
- 表少
- 规则直观
- 第一版容易审查和测试
```

缺点：

```text
- 范围模式与固定 roleKey 绑定
- 管理员不能新建任意角色并选择 TokenHub 范围模式
```

如果 TokenHub 只有这四类稳定身份，这是更适合第一版的方案。

### 第六步：动态配置方案才需要角色扩展表

如果你希望管理员可以这样操作：

```text
1. 在 system 中新建一个 competition Client 角色
2. 勾选 TokenHub 菜单和按钮权限
3. 再选择该角色的数据模式：全部 / 本人 / 负责大赛 / 负责赛题
```

那么可以在 TokenHub 模块创建角色范围扩展表：

```text
th_role_scope_policy
--------------------
role_id       对应 sys_role.role_id
scope_mode    ALL / SELF / ASSIGNED_COMPETITION / ASSIGNED_PROBLEM
status        是否启用
```

这张表不是第二套角色表。它只补充 TokenHub 专属信息：

```text
[sys_role]
角色名称、Client、roleKey、功能权限
      |
      | role_id
      v
[th_role_scope_policy]
这个角色在 TokenHub 中使用哪种资源范围
```

具体资源仍需另一组关系：

```text
th_competition_grant
--------------------
user_id
role_id
competition_id
status

th_problem_grant
----------------
user_id
role_id
problem_id
status
```

把 `role_id` 一起保存，可以表达：

```text
用户 100 通过“大赛负责人角色”获得大赛 A

用户 100 通过“赛题协作角色”获得赛题 B1
```

当用户失去对应角色时，即使授权关系尚未清理，运行时也必须因为当前会话没有该角色而拒绝使用这条授权。

### 第七步：固定方案和动态方案怎样选择

```text
角色种类固定、范围语义稳定
          |
          v
使用固定 roleKey + 两张负责人关系表


需要管理员自由创建角色并选择 TokenHub 范围模式
          |
          v
增加 th_role_scope_policy + 带 role_id 的资源授权表
```

不要一开始就创建万能表，除非已经有明确需求。一个过度抽象的表可能长成：

```text
principal_type
principal_id
resource_type
resource_id
action_type
condition_json
```

它很灵活，但数据库外键、查询优化、表单校验和语义审查都会变难。

TokenHub 第一版更推荐显式表：

```text
th_competition_manager 或 th_competition_grant

th_problem_manager 或 th_problem_grant
```

### 第八步：推荐的 TokenHub 模块结构

建议模块位于：

```text
ruoyi-vue-plus-namewta/
  ruoyi-modules/
    ruoyi-tokenhub/
      pom.xml
      src/main/java/org/dromara/tokenhub/
        controller/
        domain/
          entity/
          bo/
          vo/
        mapper/
        service/
        security/
          TokenHubDataScope.java
          TokenHubDataScopeService.java
          TokenHubScopeMode.java
```

职责示例：

```text
TokenHubScopeMode
-> 定义 ALL、SELF、ASSIGNED_COMPETITION、ASSIGNED_PROBLEM

TokenHubDataScope
-> 保存本次请求算出的 all、self、competitionIds、problemIds

TokenHubDataScopeService
-> 根据 LoginUser.roles 和授权关系表生成范围

RegistrationMapper
-> 把范围应用到报名列表、详情、导出、更新和删除
```

Maven 依赖方向应是：

```text
ruoyi-tokenhub
  +-> ruoyi-api
  +-> 需要的 ruoyi-common-mybatis / web / security / log 等
  -X-> ruoyi-system
```

业务模块不能注入 system 的 `ISys*`、Mapper 或 domain。当前登录身份直接使用公开的 `LoginUser` 和 `LoginHelper`；需要 system 能力时只走 `ruoyi-api` 的公开接口。

当前 `RoleService` 公开面只支持按 ID 查询角色名称，没有提供角色详情或 Client 校验。如果未来要做完全动态的 TokenHub 角色范围配置页，并由 TokenHub 后端校验目标角色 Client，需要新增一个窄的 `ruoyi-api` 合同，不能让 TokenHub 直接依赖 `ruoyi-system`。

### 第九步：运行时怎样计算 TokenHub 范围

以动态配置方案为例：

```text
[LoginUser]
userId = 100
clientPk = competition Client
roles = [角色 20, 角色 30]
          |
          v
[只读取当前会话中的角色 ID]
          |
          v
[th_role_scope_policy]
角色 20 -> ASSIGNED_COMPETITION
角色 30 -> ASSIGNED_PROBLEM
          |
          v
[查询仍有效的资源授权]
角色 20 + 用户 100 -> 大赛 A、B
角色 30 + 用户 100 -> 赛题 C1
          |
          v
[生成 TokenHubDataScope]
all = false
self = false
competitionIds = [A, B]
problemIds = [C1]
```

报名查询追加的逻辑近似为：

```sql
WHERE registration.competition_id IN (A, B)
   OR registration.problem_id IN (C1)
```

如果还有普通参赛者角色，需要看到自己的报名：

```sql
WHERE registration.competition_id IN (A, B)
   OR registration.problem_id IN (C1)
   OR registration.applicant_user_id = 100
```

如果没有匹配策略或没有任何授权：

```sql
WHERE 1 = 0
```

必须失败时收紧，不能把空范围理解成全部范围。

### 第十步：配置界面应该分别放在哪里

建议拆成两个管理入口：

```text
[系统角色管理]
归属：ruoyi-system
负责：
- 选择 Client
- 创建角色
- 分配 TokenHub 菜单和按钮权限
- 给用户分配角色

[TokenHub 权限范围管理]
归属：ruoyi-tokenhub
负责：
- 固定方案下分配大赛负责人、赛题负责人
- 动态方案下配置角色 scope_mode
- 给用户和角色分配具体大赛或赛题
```

不要把具体大赛、赛题列表塞进 system 的角色页面，除非通过明确的扩展接口嵌入。system 不应该知道 TokenHub 的业务表结构。

### 第十一步：一套完整的配置顺序

以大赛负责人为例：

```text
1. sys_client
   确认 competition Client 已启用并绑定正确登录域
               |
               v
2. sys_menu
   为 competition Client 创建：
   tokenhub:registration:list
   tokenhub:registration:export
   tokenhub:registration:review
               |
               v
3. sys_role + sys_role_menu
   创建 tokenhub_competition_manager
   分配上述菜单和按钮权限
               |
               v
4. sys_user_role
   给用户 100 分配该角色
               |
               v
5. TokenHub 负责人关系
   用户 100 -> 大赛 A、B
               |
               v
6. 运行时
   功能权限允许调用接口
   TokenHub 范围只允许 A、B
```

赛题负责人同理，只把第 5 步换成：

```text
用户 200 -> 赛题 A1、A2
```

### 第十二步：管理后台 Client 和大赛 Client 如何共用业务数据

可能存在两个入口：

```text
[管理后台 Client]
运营人员管理全部大赛

[competition Client]
参赛者和大赛负责人处理比赛业务
```

两边的角色和菜单分别属于各自 Client：

```text
管理后台角色 -> client_id = 管理后台 Client

大赛端角色   -> client_id = competition Client
```

但 TokenHub 的大赛、赛题和报名可以是同一套业务数据。TokenHub 范围服务根据当前 `LoginUser.clientPk` 和当前会话角色计算范围，而不是假定数据表只属于某一个 Client。

如果同一个人需要从两个 Client 访问相同大赛：

```text
- 两个 Client 分别给他合适的功能角色
- TokenHub 资源授权可以复用同一用户与大赛关系
- 每次请求只使用当前 Client 会话中的角色策略
```

### 第十三步：每个模块需要定制到什么程度

每个模块不用定制整个权限系统，只需要实现三个业务适配点：

```text
1. Scope Model
   本模块有哪些范围：全部、本人、负责大赛、负责赛题

2. Scope Resolver
   当前用户和当前角色能得到哪些资源 ID

3. Scope Enforcement
   列表、详情、导出、统计、更新、删除怎样使用这些 ID
```

其余继续复用：

```text
Client、登录、角色、菜单、按钮权限、LoginUser、Controller 权限检查
```

当第二、第三个业务模块都出现相同模式后，可以提取一个公共 SPI：

```text
[公共资源权限编排]
      |
      +-> TokenHubScopeResolver
      +-> CollectionScopeResolver
      +-> AiScopeResolver
```

但具体的 SQL 列和资源关系仍由各模块负责。公共层不能假设所有模块都有 `competition_id` 或 `problem_id`。

### 第十四步：安全门禁

TokenHub 的范围必须用于所有读写入口：

```text
- 列表
- 详情
- 导出
- 统计
- 审核
- 修改
- 删除
- 批量操作
```

每次请求必须同时满足：

```text
[当前 Client 的角色拥有接口权限]
                    AND
[当前角色策略允许访问目标业务资源]
```

不能只检查其中一个：

```text
只有角色权限 -> 知道报名 ID 后可能横向越权

只有资源授权 -> 没有审核资格的人也可能调用审核接口
```

前端提交的 `clientId`、`roleId`、`competitionId` 和 `problemId` 都不能直接作为授权证明。服务端必须使用登录会话中的 `clientPk`、角色集合和数据库中的有效授权关系重新计算。

### 第十五步：推荐给 TokenHub 的第一版

在当前需求下，建议从固定角色方案开始：

```text
system 中：
- competition Client
- tokenhub_participant
- tokenhub_competition_manager
- tokenhub_problem_manager
- tokenhub_platform_admin
- TokenHub 菜单和按钮权限

TokenHub 中：
- th_competition_manager(user_id, competition_id)
- th_problem_manager(user_id, problem_id)
- TokenHubDataScopeService
- 所有报名读写入口共用范围
```

暂时不创建 `th_role_scope_policy`。当你确认业务管理员需要自由新建角色并选择 TokenHub 数据模式时，再增加该扩展表和相应的 `ruoyi-api` 角色查询合同。

这条演进路线避免第一版过度设计，同时保留未来动态配置能力。

## 术语小词典

- Client 上下文：当前从哪个应用入口登录，以及该入口使用哪些角色和菜单；不是天然租户。
- 中心角色：由 `sys_role` 统一保存并通过 `sys_user_role` 分配的系统角色。
- 功能权限：决定能不能调用列表、导出、审核等接口。
- 业务资源范围：决定可以访问哪些大赛、赛题或报名。
- 角色扩展表：只保存某个业务模块附加给角色的范围策略，不复制角色名称、菜单和用户关系。
- 范围模式（Scope Mode）：ALL、SELF、ASSIGNED_COMPETITION、ASSIGNED_PROBLEM 等 TokenHub 规则类型。
- 资源授权关系：用户通过某角色具体获得哪些大赛或赛题。
- 范围解析器（Scope Resolver）：把当前用户、当前 Client 角色和授权关系转换成允许的资源编号集合。
- 范围执行（Scope Enforcement）：把允许范围放进列表、详情、更新和删除的 SQL 条件。
- 固定角色方案：代码约定稳定 roleKey 对应哪种业务范围，不需要角色扩展表。
- 动态配置方案：管理员可以给任意角色选择业务范围模式，需要 `th_role_scope_policy`。
- SPI：公共层定义接口，各业务模块提供自己的范围解析实现。

## 你现在能复述什么

```text
问题一：每个业务模块都要复制角色表吗？
答案：不要。sys_role、sys_menu、sys_user_role 继续由 system 统一管理。

问题二：每个模块是否完全不用定制？
答案：仍需定义自己的资源范围、范围解析器和 SQL 约束，但复用公共登录和功能权限。

问题三：TokenHub 需要角色子表吗？
答案：固定四类角色时不需要；需要任意角色动态选择 TokenHub 范围时才建 th_role_scope_policy。

问题四：具体大赛和赛题授权存哪里？
答案：存 TokenHub 自己的负责人或 grant 关系表，不存 sys_role.data_scope 或 sys_role_dept。

问题五：Client 控制什么？
答案：控制当前会话加载哪套角色和菜单，不自动决定报名属于哪个大赛。

问题六：第一版推荐什么？
答案：固定 TokenHub 角色 + 大赛负责人表 + 赛题负责人表 + 统一 TokenHubDataScopeService。
```
