## Finding

`NotifyAutoConfiguration.java:30` is bare `@AutoConfiguration`, while its store factory at `:53-56` requires `@ConditionalOnBean(RedissonClient.class)`. The installed backend uses Spring Boot **4.1.0** and Redisson starter **4.6.1**. That starter JAR (`9aa05dcfd1a7f9b7799ef881cd504c86e9ff5b975cdc1e45dd8be61facddf401`) imports `org.redisson.spring.starter.RedissonAutoConfigurationV4`, whose source declares `@Bean RedissonClient redisson()`. Its V2 auto-configuration is also listed but targets Boot 2.7–3.5; V4 targets Boot 4. The project has no other production `@Bean RedissonClient` or `@Bean NotifyIdempotencyStore` found in the scoped source search.

Boot 4.1's local `AutoConfigurationSorter` initially sorts by fully qualified class name, then order and before/after edges. Without an explicit edge, `org.namewta...NotifyAutoConfiguration` precedes `org.redisson...RedissonAutoConfigurationV4`. Boot's local `ConditionalOnBean` Javadoc says it only sees definitions processed *so far* and requires an auto-configuration using it to run after the producer. Thus the Notify store method can be skipped permanently even though Redisson is registered later. `NotifyIdempotencyCoordinator` is still created using `store.getIfAvailable()` and holds null; a keyed `NotifyDispatcher.send` then fails at `begin()` before attachment snapshot or SMTP.

The fixed 797 run `/tmp/wta-t42/runs/abfb2b395dbba64a/result.json` had 20 methods, 6 pass/14 fail, source before/after clean, cleanup errors `[]`. Its failed MAIL rows were `UNKNOWN`/`DISPATCH_ERROR` with no copy. This run did **not** test store presence and by itself did not identify the exception cause. In the later fixed 912 run `/tmp/wta-t42/runs/4ec41b94501b8931/result.json`, the newly added `@BeforeAll` `idempotencyStore.getIfAvailable()` assertion failed: fresh XML records one lifecycle failure and zero test bodies; source before/after clean and cleanup errors `[]`. That is direct evidence the complete application lacks the production store in that run. It supports the ordering cause together with the actual import/annotation evidence; no other Redis failure is needed to explain the missing bean.

## Minimal product correction and red/green test

Change only the declaration to `@AutoConfiguration(afterName = "org.redisson.spring.starter.RedissonAutoConfigurationV4")`. The string form keeps the Redisson starter configuration class out of this module's compile-time API. Keep `@ConditionalOnBean(RedissonClient.class)` and `@ConditionalOnMissingBean(NotifyIdempotencyStore.class)`; they preserve the no-Redis fail-closed behavior and user-supplied store override. The currently supported backend is Boot 4.1; no V2 edge is needed for its runtime.

Add a test to `NotifyIdempotencyAutoConfigurationUnitTest` that imports the **real pair** with `AutoConfigurations.of(NotifyAutoConfiguration.class, RedissonAutoConfigurationV4.class)`. Use a test-only `BeanFactoryPostProcessor` that runs after configuration parsing, confirms the actual `redisson` bean definition exists, replaces that definition with a mocked `RedissonClient` singleton, and marks unrelated definitions lazy. This avoids network connection while leaving `@ConditionalOnBean`'s original ordering decision intact. Assert that the context has a `NotifyIdempotencyStore` definition, obtaining it yields `RedisNotifyIdempotencyStore`, and the `NotifyIdempotencyCoordinator` holds that same store (for example via test-only field inspection). Do not invoke a Redis operation on the mock. The fixed 797 source should fail at the missing store; adding the `afterName` edge should pass. Keep the existing no-Redisson test, which must still fail closed for a keyed request. The existing `.withUserConfiguration(RedissonConfiguration.class)` positive test is insufficient for this bug: its user bean definition is registered before auto-configurations and masks their relative order.

Then rerun the 912-style complete-application `@BeforeAll` store assertion on isolated owned MySQL/Redis/MinIO before interpreting MAIL scenario results. Store presence closes this particular bootstrap defect; the 20 MAIL methods still need their own fresh XML and full cleanup evidence. Do not mark the 797 or 912 failed runs as accepted.
