# 基础字段与数据权限边界

这篇图解回答两个确认问题：

1. 当前数据权限能不能直接满足“大赛负责人、赛题负责人”的要求？
2. `create_by`、`create_dept`、岗位和用户分别在数据权限中扮演什么角色？

## 先看全图

```text
[业务表中的归属字段]
create_dept / dept_id / create_by / user_id
               |
               | 只是提供“这行数据属于谁”的事实
               v
[Mapper 上的 @DataPermission]
声明部门规则和本人规则分别使用哪一列
               |
               v
[角色的 data_scope]
选择全部 / 自定部门 / 本部门 / 部门以下 / 本人
               |
               v
[登录用户的 userId、deptId 和角色]
提供当前是谁、属于哪个部门、使用哪种范围
               |
               v
[MyBatis 数据权限拦截器]
把上述材料组合成 WHERE 条件
               |
               v
[数据库只返回允许的数据]
```

四个条件缺少任何一个，都不能得到完整的自动数据权限：

```text
只有基础字段          -> 数据可归属，但没有自动过滤

只有 @DataPermission  -> 没有正确列或角色范围，也算不出条件

只有 data_scope       -> 不知道具体 SQL 应该使用哪一列

只有前端隐藏          -> 服务端数据仍可能被直接访问
```

最准确的一句话是：

```text
当前框架原生支持“组织部门范围 + 本人范围”，
不原生支持“任意业务资源范围”，也不原生支持“按岗位成员范围”。
```

## 一步一步看

### 第一步：你的理解哪些部分是正确的

`BaseEntity` 确实定义并自动填充这些字段：

```text
create_dept -> 创建这条记录时，创建人所属的部门

create_by   -> 创建这条记录的用户编号

create_time -> 创建时间

update_by   -> 最后更新人

update_time -> 最后更新时间
```

因此，大多数继承 `BaseEntity` 的业务实体可以保存：

```text
[这条数据由谁创建]

[创建时属于哪个部门]
```

这正是通用“本部门”“本部门及以下”“仅本人”权限能够落地的重要数据基础。

例如：

```text
业务记录 501
create_dept = 研发部 100
create_by   = 用户 9001
```

如果当前用户属于研发部，角色范围是本部门，系统可以用：

```sql
create_dept = 100
```

如果角色范围是仅本人，系统可以用：

```sql
create_by = 9001
```

### 第二步：基础字段存在不等于数据权限自动生效

系统不会看见 `create_dept` 字段后自动猜测所有查询都要过滤。Mapper 还要明确声明：

```java
@DataPermission({
    @DataColumn(key = "deptName", value = "create_dept"),
    @DataColumn(key = "userName", value = "create_by")
})
```

这段声明的意思是：

```text
部门范围 -> 使用当前 SQL 中的 create_dept 列

本人范围 -> 使用当前 SQL 中的 create_by 列
```

另一张表可能不应该使用审计字段，而要使用业务归属字段：

```java
@DataPermission({
    @DataColumn(key = "deptName", value = "owner_dept_id"),
    @DataColumn(key = "userName", value = "owner_user_id")
})
```

所以 `@DataPermission` 不要求必须使用基础字段；它要求开发者选择符合业务语义的真实列。

判断是否真的受控，不能只看表结构：

```text
[表有 create_by/create_dept]
             |
             v
[查询它的 Mapper 方法有 @DataPermission 吗？]
             |
        +----+----+
        |         |
       没有       有
        |         |
        v         v
 [不会自动过滤] [继续检查列映射是否正确]
```

### 第三步：当前原生支持的是部门级和本人级

当前 `DataScopeType` 的 6 种代码可以归纳为三类：

```text
全部范围
  1 = 不追加过滤

部门范围
  2 = 角色自选部门
  3 = 当前部门
  4 = 当前部门及以下

本人和混合范围
  5 = 当前用户
  6 = 部门及以下或当前用户
```

它们依赖的数据是：

```text
当前用户的 deptId
当前用户的 userId
角色自选的 sys_role_dept
Mapper 映射的 deptName 和 userName 列
```

当前模板没有读取：

```text
LoginUser.posts
岗位编号
大赛编号
赛题编号
项目编号
设备编号
```

因此最准确的说法是“部门级和本人级”，不是“部门、岗位、用户级”。

### 第四步：岗位为什么看起来也有数据权限

岗位表 `sys_post` 自己有：

```text
dept_id   -> 这个岗位属于哪个部门
create_by -> 这个岗位记录由谁创建
```

岗位列表 Mapper 配置的是：

```text
deptName -> dept_id
userName -> create_by
```

所以管理员查看岗位列表时，可以受到部门或创建人范围限制：

```text
[当前用户属于研发部]
          |
          v
[角色范围是本部门]
          |
          v
[岗位查询追加 dept_id = 研发部]
          |
          v
[只能管理研发部的岗位记录]
```

这叫“岗位记录被部门数据权限控制”，不是“根据当前用户担任的岗位计算数据权限”。

两个概念必须分开：

```text
已经实现：岗位记录有 dept_id，因此可以按部门过滤岗位列表

没有实现：用户担任岗位 P，因此自动看见所有标记为岗位 P 的业务数据
```

`LoginUser.posts` 虽然在登录时已经装入会话，但当前 `DataScopeType` 没有使用它生成 SQL。

### 第五步：基础字段适合解决哪些问题

如果业务规则恰好是下面这些，现有体系通常够用：

```text
规则一：只能看自己创建的数据
       -> userName 映射 create_by

规则二：只能看自己所属部门创建的数据
       -> deptName 映射 create_dept

规则三：只能看业务数据明确归属部门的数据
       -> deptName 映射 owner_dept_id 或 dept_id

规则四：只能看业务数据明确归属本人的数据
       -> userName 映射 owner_user_id 或 applicant_user_id
```

这里有一个重要区别：

```text
create_by = 谁创建了记录

owner_user_id = 记录在业务上属于谁
```

二者有时相同，有时完全不同。

例如报名可能由工作人员代录：

```text
create_by         = 工作人员 100
applicant_user_id = 参赛者 9001
```

如果“普通用户只能看自己的报名”，应该映射 `applicant_user_id`，不能机械地映射 `create_by`。

同理：

```text
create_dept   = 创建操作发生时工作人员所属部门

owner_dept_id = 这条业务数据真正归属的部门
```

数据权限必须选择符合业务语义的字段，而不是因为基础字段天然存在就一律使用它。

### 第六步：为什么大赛和赛题仍需要额外定制

你的规则使用的是两种新的业务归属：

```text
报名属于哪个大赛  -> competition_id

报名属于哪个赛题  -> problem_id
```

负责人范围来自：

```text
用户负责哪些大赛 -> competition_manager

用户负责哪些赛题 -> problem_manager
```

它们既不是创建部门，也不是创建人：

```text
[赛题负责人]
    |
    | 没有创建参赛者的报名
    | 也不一定和参赛者属于同一个部门
    v
[仍然需要看到负责赛题下的报名]
```

所以，仅靠现有 `create_by/create_dept + data_scope 1..6` 无法表达该规则。

需要额外定制，但“定制”不一定等于修改公共数据权限核心。推荐第一步是在大赛业务模块内增加：

```text
1. 大赛负责人关系表
2. 赛题负责人关系表
3. 统一的报名业务范围对象
4. 列表、详情、导出、修改、删除共用的范围查询条件
```

这比把赛题伪装成部门，或者把赛题编号塞入 `data_scope` 更符合真实业务边界。

### 第七步：哪些场景可以不定制

只有当你的业务规则真的等价于部门或本人时，现有体系才能直接复用。

例如：

```text
情况 A：每个赛题严格归属于一个组织部门，
        赛题负责人就是该部门的所有管理员，
        并且未来永远按部门授权。

这时可以把报名的 deptName 映射到赛题归属部门字段。
```

但如果：

```text
- 一个部门负责多个赛题，但不同人分别负责不同赛题
- 一个人跨部门负责多个赛题
- 负责人会临时调整
- 同一赛题有多个负责人
```

部门权限就无法准确表达，应该使用业务负责人关系。

同样，如果“大赛负责人”真的是平台级管理员，要看所有大赛，现有代码 `data_scope = 1` 可以表达“不追加通用过滤”。但如果他只负责大赛 A，仍然必须增加 `competition_id` 范围，不能只用代码 `1`。

### 第八步：最终判断公式

```text
现有体系直接满足：
数据可见范围 = 全部 / 角色自选部门 / 当前部门 / 子部门 / 当前用户

需要业务定制：
数据可见范围 = 负责的大赛 / 负责的赛题 / 负责的项目 / 负责的设备等
```

再把实现条件写完整：

```text
[表中有正确的归属字段]
          +
[Mapper 使用 @DataPermission 映射正确列]
          +
[角色配置正确 data_scope]
          +
[登录上下文有 userId、deptId 和角色]
          +
[查询经过 MyBatis 数据权限拦截器]
          =
[通用部门/本人数据权限真正生效]
```

## 术语小词典

- 审计字段：记录谁在什么时候创建或修改数据，例如 `create_by`、`create_dept`。
- 业务归属字段：表达数据在业务上真正属于谁，例如 `applicant_user_id`、`competition_id`、`problem_id`。
- 基础实体（`BaseEntity`）：为实体统一提供创建部门、创建人和时间等字段的父类。
- 列映射（`@DataColumn`）：告诉数据权限模板，当前 SQL 的部门列和本人列分别是哪一列。
- 数据范围（`data_scope`）：选择全部、部门或本人等通用过滤类型的代码。
- 岗位记录权限：限制谁能查看或管理岗位表中的记录。
- 岗位成员权限：根据当前用户担任的岗位计算业务数据范围；当前模板没有实现。
- 业务资源权限：按大赛、赛题、项目或设备等具体业务对象进行授权。
- 额外定制：在业务模块中增加资源关系和查询条件；不一定要修改公共权限框架。

## 你现在能复述什么

```text
问题一：当前体系能直接满足赛题负责人范围吗？
答案：不能。它原生只支持全部、部门和本人范围，需要增加赛题负责人业务范围。

问题二：BaseEntity 的基础字段有帮助吗？
答案：有。它们提供创建人和创建部门事实，是通用过滤的重要数据基础。

问题三：只要表里有 create_by/create_dept 就会自动过滤吗？
答案：不会。Mapper 还必须用 @DataPermission 正确映射列，并经过拦截器。

问题四：当前支持岗位级数据权限吗？
答案：不支持按用户岗位计算业务范围；只支持按部门/创建人过滤岗位表记录。

问题五：大赛业务应该怎样做？
答案：角色控制功能，负责人关系控制具体大赛或赛题，服务端查询统一追加业务范围。
```
