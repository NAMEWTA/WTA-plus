# T45 proposed `OssAccessDiagnostic` model — bounded safety review

Read-only review of fixed product `fc50c1e1227d42a46f8e25b3e19949baeccb89e0` and proposed record: `verification/reason/expectedAccessPolicy/checkedAt + List<Fact(subject, observation, source, scope, observedAt)>`. No repo edit, build, or service. The model is usable with two small clarifications and one recommended extra fixed code; no general IAM evaluator or compatibility bridge is needed under the accepted direct cutover.

## Minimum refinements

1. Add a **fixed, non-sensitive per-Fact basis/reason enum** (or equivalent) for `NO_SUCH_POLICY`, `POLICY_UNREADABLE`, `ACL_UNREADABLE`, `TIMEOUT`, `REDIRECT`, `NOT_EVALUATED`, `UNSUPPORTED`. `UNKNOWN` alone is insufficient to distinguish a known absent bucket-policy document from unreadable 403, or to preserve simultaneous independent partial failures; one top-level `reason` cannot describe all facts. Do not include HTTP URL, object key, raw policy, Provider message, credential, or mutable map. A `NoSuchBucketPolicy` 404 is known document absence, but is **not** observed denial of anonymous object read/write. Policy/ACL 403 is UNKNOWN for the content/conclusion, never an empty policy/grant list. A generic S3 404 must not be treated as `NoSuchBucketPolicy` without the specific error code.
2. Define `subject` as a **claim about anonymous action**, not whether the application could call `GetBucketPolicy`/`GetBucketAcl`. `POLICY_READ/WRITE` are applicable parsed policy claims; `ACL_READ` on the **bucket ACL** is bucket listing, not object GET; `ACL_WRITE` on the bucket ACL is a bucket-scoped modification hazard, not proof that an anonymous PUT happened. AWS documents bucket ACL READ as ListBucket and WRITE as object creation; WRITE_ACP is a distinct ability to change the bucket ACL. If UI/API says “object write,” split out `ACL_WRITE_ACP` as one extra subject; otherwise label `ACL_WRITE` broadly and safely as “bucket/ACL modification grant,” with no inferred successful PUT. [AWS S3 ACL permission table](https://docs.aws.amazon.com/AmazonS3/latest/userguide/acl-overview.html).
3. `Scope.BUCKET` must mean an actually recognized whole-bucket claim, and `Scope.OBJECT` must mean the one synthetic diagnostic object. With only these two scope values, prefix-limited or otherwise partially scoped statements are UNKNOWN rather than falsely promoted to BUCKET. Keep the object key implicit; do not expose it in the public Fact or VO. Make the fact list immutable (`List.copyOf`), bounded/deterministic and null-validated; take `observedAt` when each observation completes, not reuse the method-start `checkedAt` for all probes.

## Evaluation rules that prevent false safety claims

- For each understood Principal/Action/Resource combination, an applicable explicit `Deny` overrides a matching `Allow`; no Allow and unreadable/complex policy are **not** proof of effective denial. `Condition`, `Not*`, unsupported principals/actions, ambiguous resource wildcards, invalid JSON, and unknown Provider semantics stay UNKNOWN for that source/scope. A recognizable unconditional broad write Allow can raise a **scoped policy hazard**; it is not evidence that a PUT/DELETE was performed or accepted. If a broad Allow is limited by an applicable Deny, do not call the denied scope ALLOWED. [AWS IAM explicit-deny precedence](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html).
- Bucket ACL is not object ACL. The current code obtains `getBucketAcl`; its READ/FULL_CONTROL grant cannot prove the canary's object GET. An ACL WRITE/WRITE_ACP warning is bucket-scoped; absence of AllUsers grants cannot establish actual anonymous write DENIED because another applicable policy or object ACL may exist. No diagnostic anonymous PUT/DELETE/ACL mutation.
- Anonymous HEAD and Range GET are **separate object-scoped facts**. 2xx is ALLOWED for that request/object/time; 401/403 is observed DENIED for that request/object/time; 404, 3xx, timeout and 5xx are UNKNOWN. Disable redirect following or reject a redirect before classifying a later response: the current `HttpClient.Redirect.NORMAL` can otherwise make a different target's 2xx look like this object's direct read. If HEAD succeeds but GET fails, keep HEAD ALLOWED and GET UNKNOWN. If GET succeeds but HEAD fails, retain both; neither policy nor global bucket status is inferred from the partial pair. A true 404 may mean a missing object rather than authorization denial.
- Current `anonymousRead` sends both calls in one try and catches `InterruptedException` after the pair; on second-call failure it discards the first result. Capture each fact independently. On interruption restore the interrupt flag, stop further network steps, mark unfinished facts UNKNOWN with fixed `INTERRUPTED` basis, and preserve completed facts. Do not retry after interruption or swallow it as a verified policy result. For ordinary one-step timeout/5xx, continue only independent bounded probes if safe within the existing per-step limits; preserve completed facts and stable failure codes.
- `Verification`/top-level `Reason` must be a conservative summary of these facts. `VERIFIED` cannot mean entire bucket or write safety when only a canary was read; PRIVATE plus policy/ACL unreadable cannot assert `anonymousWriteDenied=true` or READY on that basis. A definite `MISMATCH` needs understood, applicable contrary evidence within its stated scope. The T44 business and core-health paths remain independent of this optional diagnosis.

## Projection and tests

`OssStorageReadinessService` may use a private `Evaluation(entry, facts)` so `diagnoseOne` can return safe facts while background registry keeps its existing public `OssStorageReadinessEntry` constructor. This is smaller than changing every registry/health caller. `OssStorageDiagnosticVo` should project only enum subject/observation/source/scope/fixed basis/time plus the existing status/reason/checkedAt; its UI must say “observed this object” and “policy/ACL unknown” rather than “bucket safe.” No raw policy/key/URL/provider text. The existing `POST /resource/oss/config/diagnose/{ossConfigId}` and permission remain, with no new route.

Required focused tests: Policy 403 versus genuine NoSuchBucketPolicy 404; ACL 403; PUBLIC canary GET 2xx under unreadable policy; PRIVATE canary 403 with write UNKNOWN; bucket ACL READ only (no object-read inference); AllUsers WRITE versus WRITE_ACP; exact object/whole-bucket versus unrelated/prefix resource; conditional Allow; explicit applicable Deny plus Allow; malformed policy; HEAD success + GET timeout/interrupt and vice versa; 3xx/404/5xx/timeout; no anonymous mutation; no raw provider data. An owned low-privilege MinIO run must execute the 403 paths with zero skips. The T44 privileged MinIO run is not this proof.
