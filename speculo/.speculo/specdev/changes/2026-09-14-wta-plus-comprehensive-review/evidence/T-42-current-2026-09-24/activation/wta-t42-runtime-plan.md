## Why a new full-context test is required

`NotifyAtomicResultIntegrationTest` uses real MyBatis, dynamic transactions and Redis, but constructs `DispatchNotificationService` with a mocked `NotifyClient`. Existing attachment tests supply a recording snapshot SPI. Neither proves production snapshot adapter discovery or an async worker's durable original actor. `MailConfig.mailNotificationSender()` is conditional on a missing `MailNotificationSender`, so a single `@SpringBootTest(classes = {NamewtaApplication.class, ...})` opt-in test can contribute **only** a recording `MailNotificationSender` through test configuration while retaining the production `NotifyClient`, `MailNotifyChannelAdapter`, `NotifyAttachmentSnapshotService`, System OSS implementation, Notify DAOs and worker/use-case beans. The test must assert those bean identities/counts explicitly and fail if an upstream bean is a Mockito substitute. The recording sender may inspect subject/body and opened attachment bytes in memory, but must never connect to SMTP or print mail contents.

Proposed source contract to confirm with the writer: `org.namewta.test.notify.NotifyMailAttachmentIntegrationTest`, `@EnabledIfSystemProperty(named="notify.mail.attachment.integration", matches="true")`, one fresh Surefire XML at `backend/wta-admin/target/surefire-reports/TEST-org.namewta.test.notify.NotifyMailAttachmentIntegrationTest.xml`. Confirm the real FQCN, opt-in flag, method names, Mail sender test bean wiring, MinIO property names and password entrypoint from landed source before freezing any executable driver. If full `@SpringBootTest` cannot start because an unrelated outbound integration is mandatory, pin its isolated configuration to owned loopback or disable that integration without replacing the Notify/OSS path under test; record the exact bean or connection failure rather than silently switching to manual assembly.

## Assertions to put in the real test, not infer from the runner

* **Bean boundary:** complete application context contains exactly one production snapshot adapter, one production NotifyClient/MAIL adapter, production System OSS port and relation DAO; only the physical `MailNotificationSender` is a test bean. No `sys_notify_log` table is created or queried.
* **No-attachment positive:** a `demo-mail` body-only command succeeds through planner → persisted intent/outbox → worker → MAIL adapter → recording sender with no dummy `path`. The source/snapshot OSS port call counters are zero at submit and worker phases, and owned MinIO request-count proxy has zero delta from a baseline taken **after** application startup. The production bean remains installed while instrumenting it. Notice/workflow scenes still require their own path.
* **Owned attachment positive:** real A and Client X authorization produces durable immutable actor/Client-PK and ordered source relation facts in Notify Intent/relationship rows. Worker uses those persisted facts, copies source objects to private snapshot objects through production System OSS, and sender reads exact expected bytes in order. `sys_oss_ref` rows point to actual relationship primary keys; source and snapshot references, object state and owner are checked with read-only SQL and owned MinIO object checks, not just adapter invocation count.
* **Failure and isolation:** B user, another Client, absent/deleting source, and changed source fail closed before mail/extra intent or snapshot; already committed source references retain the queued source until worker decision. Fault after first physical copy and before the second, DB relation/ref write rollback or unknown commit, and materialization failure cause zero SMTP calls and no unowned replica. Snapshot compensation is proved by remote absence or a durable enumerable recovery fact; a database rollback alone is insufficient. Duplicate submit including duplicate-key race and worker retry keep the same actor/ordered source facts and bounded snapshot count; provider-unknown state cannot be treated as safe resend.

The opt-in test should query real DAO/SQL to validate actor and reference state, and use controlled barriers/two connections where the race or rollback assertion needs it. Test-only writer hooks may inject failure at a narrow interface while delegating all other calls to production implementations. Do not seed or inspect unrelated production data.
