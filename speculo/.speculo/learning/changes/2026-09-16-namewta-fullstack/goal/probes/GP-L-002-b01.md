# Probe GP-L-002 / b01

审问对象是已写成的 `L-002-backend-assembly.md` 与工作树，不是学习者。声称覆盖格子：`C:wta-admin`、`C:wta-api`、`C:wta-modules`、`C:wta-common`。对照 OBJ-02：画出后端依赖方向（组装者组装；业务走 api 与最小 common；common 不反向依赖业务）。

## Q1 澄清

L-002 把四个容器一次性标成已讲。工作树与课文本对「格子里到底有什么」并不重合，先把范围钉死：

1. `C:wta-admin`：课说插座板 = `NamewtaApplication` + 「少量接线（启动类、登录 HTTP）」，并把 `AuthController` / `SysLoginService` 明确推到后续切片。矩阵备注却是「AuthController + 模块组装」。本课声称覆盖的是 **Maven 组装图**，还是 **admin 源码树（21 个 `org.namewta.web.*`）**？`AdminSsoIdentityService`（实现 `SsoIdentityService` 且注入 `SysUserMapper`）算不算本课必须点名的组装职责？
2. `C:wta-api`：课反复举 `UserService`、`NotificationApplicationService`、`LoginUser`。源码是 **65** 个类型，分包为 `system` / `notify` / `profile` / `sso` / `third` / `workflow`。本课覆盖的是「api 是一个 jar、只依赖 core/json/spring-core」这条定义，还是整张合同目录？
3. `C:wta-modules`：课给出九个房间与依赖姿态，并把 layered/classic 交给 L-003。矩阵备注却写「layered/classic 登记表」。本课格子是 **房间名册 + POM 箭头**，还是必须交出模式登记表？
4. `C:wta-common`：课把主路径枢纽收成 notify / mybatis / satoken / openapi 四件门口，迁移段又写「不要把 26 个 jar 一次性写进 POM」。`wta-common/pom.xml` 的 `<modules>` 实际是 **29** 项（`packaging=pom` 的 bom + **28** 个能力 jar，含 `nacos` 与 `richtext`）。本课格子是「四件门口 + 禁止反向依赖」，还是整个工具间清单？
5. 三套「通知」名词是否被当成同一个盒子：`wta-api` 的 `org.namewta.notify.api.NotificationApplicationService`、`wta-modules/wta-notify` 控制面、`wta-common-notify` 的 `NotifyDispatcher` / `NotifyChannelAdapter`？

## Q2 证据

课的机制链（§因果 1–10）哪些能在工作树直接复现，哪些只被点名？

- **能复现的组装箭头。** `backend/pom.xml` reactor 五块：`wta-admin` / `wta-common` / `wta-extend` / `wta-modules` / `wta-api`。`wta-admin/pom.xml` 常驻：`wta-api`、`wta-system`、`wta-third`、`wta-notify`、`wta-sso` + 直接 common（doc / social / mail / notify / nacos / mcp / openapi）。`bundle-full` `activeByDefault` 另插 job / ai / demo / workflow / profile-person / profile-enterprise；`bundle-core` 只另插两份档案。根 README「架构一览」树确实省略 `wta-extend`。
- **能复现的跨房间合同。** `NotifyNoticePublisherService` 同时持有 `UserService` 与 `NotificationApplicationService`，按受众调用 `selectNotificationUsers` / `selectUsersByUserTypeIds` 再 `submit`。`NotifyRecipientDirectoryService` 只持有 `UserService`。`SysUserServiceImpl implements ISysUserService, UserService`。`wta-notify/pom.xml` 无 `wta-system`。`wta-job/pom.xml` 只有 `wta-common-json` + `wta-common-job`。业务 POM 之间互不声明对方 artifact。
- **能复现的 common → api，而不是 common → 业务。** `wta-common-satoken` 与 `wta-common-mybatis` 依赖 `wta-api`；`LoginHelper` / `InjectionMetaObjectHandler` / `PlusDataPermissionHandler` 引用 `org.namewta.system.api.model.LoginUser`。全仓 `wta-common-*/pom.xml` 无 `wta-system` / `wta-demo` 等业务 artifact。`DictService` 在 `wta-common-core`；`SysDictTypeServiceImpl implements ISysDictTypeService, DictService`。OpenAPI SPI 实现在 system：`SystemOpenApiAuthorizationResolver`、`SystemOpenApiCredentialResolver`。
- **课没画但源码有的组装边。** `AuthController` 除 `ISysClientService` 与 `NotificationApplicationService` 外，还注入 `ISysSocialService`、`PasswordPolicyService`、`SsoProperties`；`ISysClientService` 位于 `org.namewta.system.service`，**不在** `wta-api`。`AuthController` 还 import `LoginHelper`、`@ApiEncrypt`，而 admin POM **没有**声明 `wta-common-satoken` / `wta-common-encrypt`——它们经 `wta-system` 传递进编译 classpath。`AdminSsoIdentityService implements SsoIdentityService` 且字段注入 `SysUserMapper`。`NamewtaApplication` 仅 `@SpringBootApplication`（默认扫 `org.namewta`），没有显式 `scanBasePackages`。
- **枢纽门口与 POM 不完全同构。** 四件枢纽里，admin 直接声明的只有 notify 与 openapi；mybatis / satoken 不在 admin POM。`wta-common-notify/pom.xml` 显式依赖 `wta-common-nacos` + core + redis，**不**依赖 `wta-api`。另有 `translation` / `log` / `push` 也依赖 `wta-api`，课只写「若干 common（如 satoken、mybatis）」。

合格读者若只背课里的「常驻插座」列表，能否解释 `AuthController` 为什么能编译 `LoginHelper`？若不能，本课的证据链在 admin 格子上断在哪一层——POM 声明，还是组装后的传递 classpath？

## Q3 假设与反例

课的正例/反例是否把合法形状和违规形状分干净？

1. **正例 4 把两种 SPI 揉成一句。** `UserNameTranslationImpl` 住在 `wta-common-translation`（common 自己的实现，POM 依赖 `wta-api`），调用 `UserService`；真正「接口在 common、实现在业务」的是 `DictService` → `SysDictTypeServiceImpl`。读者会不会把「common 里的类调用 api」误判成「业务填 SPI」？
2. **「26 个 jar」。** 工作树是 28 个能力 jar + 1 个 bom。数字来自过期 Skill 摘要，不是 `wta-common/pom.xml`。课自己要求「以工作树为准」，这条有没有打自己的脸？
3. **「禁止业务互挖 Mapper」vs 主机。** `wta-notify` 确实不能碰 `SysUserMapper`；`wta-admin` 的 `AdminSsoIdentityService` **可以**。课从未写「组装者可以 import 被插模块的 Mapper」。读者会不会把反例 2 推广成「全仓谁都不能碰 `SysUserMapper`」，从而把合法主机接线判成违规？
4. **「api 合同」vs 模块内部接口。** 课说 admin 可注入 `ISysClientService`。该类型不是公开合同。读者会不会把 `org.namewta.system.service.*` 与 `org.namewta.system.api.*` 当成同一层？
5. **bundle-core。** 课正确写出档案仍在、job/ai/demo/workflow 不在。若读者以为 core = 「只剩 system」或「只剩 api+system+直接 common」（部分 Skill 仍这么写），课的变式 C 是否足够挡住这条过期假设？
6. **三套 notify。** 业务注入 `NotificationApplicationService`（api）≠ 直接 new 渠道 SDK ≠ 调用 `NotifyDispatcher`（common-notify）。变式 B 把 api 与 common-notify 渠道 SPI 并提。读者会不会以为 `wta-common-notify` 就是 `wta-api` 的 notify 包？

读完后仍说不出的最小集合：主机可看见实现（含 Mapper）；邻居只能走 api；common 可依赖 api 稳定类型；数字 26 不可当作库存。

## Q4 视角

架构边缺了哪一条？不是再讲登录流程（那是 L-006 / L-011），而是 OBJ-02 的箭头图还少哪些合法边。

| 缺边 | 源码位置 | 为何影响四个格子 |
| --- | --- | --- |
| 组装者实现 api SPI | `wta-admin/.../AdminSsoIdentityService implements SsoIdentityService`；全仓仅此一处实现 | admin 不是纯「插头」。api 合同的实现可以落在 **主机**，不一定落在 `wta-modules/*`。缺这条，api/admin 两个格子的「谁填合同」不完整。 |
| 主机 → 被插模块内部类型 | 同上注入 `SysUserMapper`；`AuthController` → `ISysClientService` / `SysClientVo` | 与「邻居禁止 Mapper」成对。图上只有「admin → 模块 jar」，没有「主机可深用、邻居不可」。 |
| POM 直接依赖 ≠ Java import 集合 | admin POM 无 satoken/encrypt；`AuthController` 使用 `LoginHelper`、`@ApiEncrypt` | 只背 admin `<dependencies>` 会认为 satoken 不是主路径，或认为 admin 源码违规。 |
| api 分包地图 | `wta-api/src/main/java/org/namewta/{system,notify,profile,sso,third,workflow}/api` | 容器「跨模块 Java 合同」在 Relational 档至少要能指包，而不是三个类名。 |
| common → api 的完整名单 | satoken、mybatis、**translation、log、push** | 「若干如 satoken/mybatis」留下「只有这两个可以」的误读。 |
| 枢纽 notify → 被 defer 的 nacos | `wta-common-notify/pom.xml` 依赖 `wta-common-nacos` | 主路径门口踩在矩阵已 `deferred(optional-overlay)` 的叶子上。课未标这条边。 |
| 扫描边界 | `@SpringBootApplication` 默认 `org.namewta.**`；extend 是另一 JVM | 图把 extend 旁置，但没说「若误把 extend 当 jar 插进 admin，扫描会把另一进程的启动类煮进来」。 |

数据流边：课画了编译期箭头，没有把 **Maven profile → admin 运行时 classpath → Spring 扫描 → 接口与实现在同一 JVM 接上** 写成一条短链。`NotifyNoticePublisherService` 的 `UserService` 在编译期是 api 类型、运行期是 `SysUserServiceImpl`，这条「编译合同 / 运行实现」边只在正例 2 用一句话带过。
