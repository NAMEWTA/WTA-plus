# 升级与回滚

## 升级

1. 分配不可变 Release ID，并记录源 Git Tag、目标 Git Tag、父仓库及两个子模块修订。
2. 读取上一份报告、活动清单和 Schema 状态。
3. 分类应用、配置、Schema、OSS 策略、Nacos 与前端路由变化。
4. 备份配置、数据库、对象存储元数据与当前版本，并验证备份可读。
5. 构建、传输并校验新版本到暂存目录。
6. 数据库有变化时，根据源/目标 Git Tag 的六份 MySQL 基座差异生成临时升级 SQL；在隔离副本评审、演练后，只执行批准的向前迁移，优先使用 expand-and-contract。禁止在已有库重放完整基座。
7. 按 server1 -> server2 逐个滚动；每个实例先检查 restart/log 快速失败，再验证直连业务语义和连续成功窗口。
8. 校验前端 context/API/asset 后原子切换，等待 LB 连续成功；运行完整登录语义并观察日志和指标。
9. 提升版本并在 `temp/relase/` 生成私密报告，包含 Tag、基座差异摘要、备份位置、校验结果和精确回滚命令。

## 回滚

1. 指定回滚目标 Git Tag，并证明其清单、配置和数据库兼容。
2. 停止继续提升，保留失败日志/状态并通知运维责任人。
3. Schema 向后兼容时先回滚应用和配置。
4. 只有明确授权且存在验证过的时间点备份时，才恢复数据库或对象数据。
5. 逐个重启后端，再恢复前端。
6. 重跑全部门禁并生成回滚报告。

每个实例的上一镜像、配置摘要和 image ID 都是独立回滚目标。server1 候选失败时恢复 server1，server2 不推进；前端切换失败时恢复旧静态目录，不连带回滚已经验证稳定的后端，除非合同不兼容。

禁止 `docker compose down -v`。根因证据保存前不得删除失败版本、旧镜像或 rollback 目录；清理需要独立授权。签名 OSS、登录、Nacos/OpenAPI 一致性或入口仍失败时，不得宣称回滚成功。
