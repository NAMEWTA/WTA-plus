## Verdict and exact meaning of the retry clause

**No hard contract conflict.** Ticket lines 81–85 require one-object Object→Item locking, bounded I/O and short transactions; lines 84 and 99 require safe convergence when the source DELETE succeeded but final DB commit failed or its acknowledgement was lost. A precommitted `FAILED + lastErrorStage=COMPLETED + fixed CLEANUP_OUTCOME_UNKNOWN` migration-item marker can serve as the durable veto using existing columns. It grants *one* external DELETE after the marker commit is proven, and blocks all restoration while the provider outcome is uncertain. A later retry that conclusively sees the source absent and target/current pointer valid can **finalize only the item**, without another DELETE. This is the ticket's successful-delete/failed-commit convergence. A source still present, an ambiguous HEAD, or an invalid target is not proof the first DELETE cannot arrive later: keep UNKNOWN and refuse both a second DELETE and source restoration. That branch needs bounded re-probe/operator handling and must not be reported as successful cleanup. The ticket does not require pretending every timeout is automatically retryable.

Holding a DB lock across DELETE does not solve the late-completion case; after timeout the lock is released while the remote operation may still finish. Use the object lock to **commit the right to delete** in a short transaction, and the durable marker to preserve that decision across the external call and a crash. This is one-object coordination on the current item, not a new distributed state platform, table, or schema. Mixed old/new migration workers cannot safely coexist because the old implementation ignores the marker; quiesce them for the direct cutover.

## Minimal state transitions

1. For a `CLEANUP_ELIGIBLE` item after its window and explicit approval, a proxied short `@DSTransactional` method locks `sys_oss` first, then the item, re-reads latest same-object item/fences and verifies ACTIVE/current service=`targetConfigKey`, object key and source/target identities, item version/status/window. An exact-one version/status CAS writes `status=FAILED`, `lastErrorStage=COMPLETED`, `errorMessage=CLEANUP_OUTCOME_UNKNOWN`, `version+1`, while leaving the object on target. It commits independently. An unacknowledged reservation commit permits DELETE only after an independent bounded DB readback proves this exact marker/version and identity; otherwise zero DELETE.
2. Outside all DB transactions, issue **one** source DELETE through a validated per-operation total timeout. A normal provider response is useful evidence, but a timeout/exception is not evidence of nonexecution. If DELETE is uncertain, leave the marker. If it appears definitive, a second short Object→Item transaction checks the same marker/version/object/target and writes `COMPLETED`, stage/cleanedTime, cleared error fields with exact-one CAS. After an unacknowledged final commit, independent readback may find either `COMPLETED` (already converged) or the marker (requires reconciliation); a rolled-back commit leaves the marker. Do not rewrite uncertainty as ordinary `CLEANUP_FAILED` or send another DELETE.
3. Controlled retry of this exact marker performs bounded source and target HEAD **outside the lock**. Only a conclusive source `OBJECT_NOT_FOUND`, a valid target matching the saved target identity (at least stored size/ETag where reliable, otherwise the existing bounded content verification), and an unchanged current object pointer/ACTIVE/key/config and item marker/version qualify. Reacquire Object→Item locks, revalidate all DB facts and CAS the item to `COMPLETED` without provider DELETE; refresh the batch after that commit. Source present/HEAD timeout/403/5xx/config drift, target absent/mismatch, or CAS conflict leaves the marker and reports a bounded, reviewable UNKNOWN. `DefaultOssMigrationObjectStore.head` currently maps only `OBJECT_NOT_FOUND` to empty and throws other S3 errors; preserve that fail-closed distinction. Do not interpret arbitrary false/exception as absence, nor accept a 404 from a drifted or unverified bucket as proof about the original source.
4. `unpublish`, batch `rollback`, `process` pointer switch and automatic access-failure restore must reject any unresolved same-object delete marker under the same lock. `findLatestRestorable` currently filters `CLEANUP_ELIGIBLE` before sorting (`MybatisOssMigrationStore:101–109`), so it can bypass a newer UNKNOWN; consider latest item/fence **before** choosing a restorable item. `retry` currently skips `FAILED/COMPLETED` (`OssStorageMigrationService:147–155`), while `cleanup` allows it (`:191–218`): route this fixed marker to reconciliation, never to normal `process` or the existing direct-delete loop. Reject stale item and pointer writes by exact-one row count/version, not `saveItem`'s ignored `updateById` count (`MybatisOssMigrationStore:80–88`). Existing Object→Item locked operations should remain per object; batch iteration must not hold every row while one object waits for OSS.

## Bounded common OSS seam, limited scope

`DefaultOssMigrationObjectStore.exists` calls `headObject().join()` (`:64–65`, common `AbstractOssClientImpl:755–770`), and `delete` calls `deleteObject().join()` (`:69–70`, common `:745–752`). Both need **migration-only** explicit `Duration` overloads through `OssClient` and `AbstractOssClientImpl` for source/target confirmation and source DELETE; validate positive finite budgets and propagate timeout as UNKNOWN. Keep the existing ordinary upload, HEAD and DELETE contracts unchanged. The per-request SDK total-call/attempt timeout plus bounded future cancellation should bound application waiting, but it is not proof that the remote request was cancelled before execution; the durable marker is still mandatory. `OssStorageMigrationProperties` needs one or two narrowly validated per-object budgets, and migration adapter/service/tests need the overloads. Register both common production paths before writing, apply Java public API compatibility review, and add only a default-client path if local SDK tests show it necessary. The existing copy/verify remains outside DB transactions; no full OSS timeout platform is implied.

## Required focused proof

- Two **physical MySQL connections** and controlled latches show restore-first blocks cleanup on the object row, then cleanup re-reads the source pointer and emits zero DELETE; cleanup-first persists the marker before the sole DELETE, and unpublish/rollback/process (including an older restorable item) reject restoration. Confirm DB connection IDs/lock wait, not merely thread scheduling. A second object progresses while the first provider call is delayed.
- Reservation CAS zero rows or precommit rollback/ACK unknown with unproven readback ⇒ zero DELETE. DELETE succeeds but final item transaction rolls back/ACK is unknown ⇒ persisted marker, source absent, target valid and pointer target; later exact-marker retry performs **zero additional DELETE** and converges `COMPLETED`. Repeat the retry to prove idempotence. Inject source-present timeout followed by late DELETE: first retry remains UNKNOWN with zero DELETE/restore, later conclusive absent retry finalizes. Include 403/5xx/timeout HEAD, missing/mismatched target, config/pointer/version drift, item CAS zero rows and batch recount.
- Owned MinIO HEAD/GET confirms the source/target bytes and current pointer for both race orders; real MySQL + MinIO test result must have fresh positive zero-skip XML. Focused common OSS test checks `Duration` reaches both HEAD and DELETE requests and timeout returns within budget while a late provider operation cannot trigger restoration. Do not claim that a test proves exact remote cancellation. Preserve clean-source/JAR, resources and cleanup evidence.

Current code does **not** satisfy this yet: `OssStorageMigrationService:51–70` restores after pre-read without shared lock, `:184–219` directly deletes from a stale batch list, `:159–181` rollback can restore a FAILED item, and `:222–276` switches/restores independently. Existing sequential `OssStorageMigrationIntegrationTest` does not prove the competition or commit-loss behavior. The report recommends the minimal implementation/verification contract only.
