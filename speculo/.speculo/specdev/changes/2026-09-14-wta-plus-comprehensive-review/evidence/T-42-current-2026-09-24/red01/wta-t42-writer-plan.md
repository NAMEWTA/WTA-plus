## 无环职责、事务和状态

1. `wta-notify` 仍是 `notify_intent`/`notify_intent_attachment` owner。其安全入口适配器从受信 `LoginHelper.getLoginUser()` 取 `userId`、`clientPk`（`LoginUser` 已含两者），传给 UseCase/Service；附件非空而任一缺失即拒绝，HTTP body/metadata 中同名值忽略。Intent 用不可变 `submit_user_id/submit_client_pk` 保存原 actor；无附件允许空值。Notify 只注入 `wta-api` 的 `OssService`，绝不注入 System Mapper/ServiceImpl。System `SysOssServiceImpl` 只处理自己的 OSS 行锁、授权、私有副本和物化，不读 Notify Mapper/Entity；System 不反向依赖 Notify。common SPI 只接类型化 Intent owner 和附件描述。
2. 新表 `notify_intent_attachment` 以真实 `intent_attachment_id` 为 PK，至少保存 `intent_id`、`position`、`source_oss_id`、原 service/元数据摘要、确定性 `snapshot_key`、可空 `snapshot_oss_id`、受控 `copy_state`、copy owner/fence 与版本；唯一 `(intent_id,position)`、`(intent_id,source_oss_id)`、`snapshot_key`。保留 `version/create_dept/create_time/create_by/update_time/update_by/del_flag` 七字段、中文注释、Notify DAO→Mapper 边界。提交的同一个 **`@DSTransactional`** 事务内：写 Intent→各关系行→经 System 锁内授权并绑定 `sys_oss_ref(ref_type='notify_intent_attachment', ref_id=真实关系 PK)`→Recipient/Delivery/Outbox。所有来源引用先持久提交，worker 才能开始；排队期间临时对象清理不能删除来源。不存在的/待删除的/不同 user 或 Client 的源在任何 Intent/Outbox 持久提交前失败。多对象按 OSS ID 稳定加锁，关系展示顺序仍按 `position`。
3. worker 依现有 Intent→Outbox→Delivery 锁序/lease fence，短事务锁 Intent+附件关系预留一次复制权并持久化确定性对象 key；退出事务后才做 MinIO I/O。System 重新按**持久 actor**和原 service 核源，再复制到独立 PRIVATE 存储，记录真实 `sys_oss` 对象及文件名、大小、类型、字节校验；Notify 在短事务里以 relation CAS 写 `snapshot_oss_id/READY`、把 `sys_oss_ref` 从源安全迁到副本（必要时暂保留源直到确认），然后 common MAIL adapter 只物化已确认的私有快照。私有源可选其**同一经数据库核实仍为 PRIVATE 的配置**；PUBLIC_READ 源必须选数据库当前唯一合法 PRIVATE 默认配置，不能把当前默认或 readiness 缓存不加检查地认作私有。若私有目标不存在/不唯一，明确本地失败且不调用 MAIL。reservation 按 T46 的 Config→Object→Item 顺序锁住源/目标配置，在同一短事务固化来源 `service`、目标真实 `service`/配置身份/key，且为目标创建有真实关系 ref 的**未就绪 `sys_oss` 元数据**，使现有配置引用计数从预约提交起禁止物理身份改写；远端 copy 期间不持 DB 锁。该目标状态必须有不同于现有“待删除” `PENDING` 的明确不可下载值，System 所有访问/引用入口只允许 ACTIVE，绝不让旧 `bind` 将未就绪或待删对象升级为可用。仅字节校验及关系 CAS 提交成功才将目标置 ACTIVE。相同配置可用受控服务端 copy；跨配置/桶须有界流式下载→上传（已验证的源长度上限、时限、try-with-resources、字节数/摘要核对，无泄密临时文件），不假设 `copyObject` 支持跨 client。绝不因来源为已授权 PUBLIC 而任意拒绝，但目标始终 PRIVATE。`NotifyRequest` 增类型化 `attachmentIntentId`；Dispatch 从持久 Intent/有序关系构造它，生产 adapter 对照 ID、actor、关系与 delivery 归属，不能信任调用方随填的 request/context。无附件时在提交和 dispatch 两处短路，System OSS 元数据、客户端创建、复制、物化均零调用。
4. `SOURCE_HELD → COPYING → SNAPSHOT_READY` 是同一关系的最小持久阶段，另有 `COPY_UNKNOWN/RELEASE_PENDING` 用于不确定副作用和安全回收。复制 key 从真实关系 PK 固定派生；重复 worker 复用 READY 的**同一**对象和有序资源，不能按 delivery 重新复制。复制开始前持久 reservation；只在明确未调用远端时可安全重置。第一件成功、第二件失败时，SMTP 零调用；每个已生成副本要么有可查询 relation/key/ref，要么经有记录的补偿删除。复制或 DB 提交 ACK 不明时保留 `COPY_UNKNOWN`、源引用和可能的副本，后续仅按该 key/真实字节与持久行核对，不盲写新 key、删除、重发。失联的迟到 copy 不能覆盖新 owner；未知仍未知直至有充分事实。`NotifyDispatcher` 的即时 cleanup 改为通知持久 owner 的安全 release 请求，不能由单 delivery 决定删除共享副本；全部相关 delivery 已明确未发、无活 lease 才能在锁内解除引用并由可追踪清理收尾。ACCEPTED/UNKNOWN 保留资源供核对，结果事务与 T37/T39/T40 fence 不回退。
5. 提交幂等两个出口都要先比对 `(appId,key)` 既有 Intent 的原 user+Client 和**有序规范化 source ID 序列**，并核授权事实；事实不同固定冲突，不能返回他人的旧 receipt。第一处是 `findDuplicate` 早返回，第二处是 Intent 唯一键插入冲突回读（需要当前锁定读，避免 RR 旧快照）；同事实只返回原 receipt，不写新的 Intent、引用或快照。缓存/Dispatcher 幂等命中也须先核持久附件 owner；Redis 命中不是关系齐备证据。提交 ACK 失联后按同一唯一键/关系回读，不二次生成来源绑定。
