The new `OssClient` default-bucket HEAD/DELETE Duration methods and `AbstractOssClientImpl:2012–2049` use request `apiCallTimeout` and `apiCallAttemptTimeout` plus the existing bounded `await` (`:1431–1444`). On local timeout/interruption `await` cancels the future; on interruption it restores the thread flag. The methods allocate no new pool or unmanaged closeable. `toStorageException` preserves 404 vs provider error, so the migration adapter can distinguish an absent object from 403/timeout. This is a sound direction; cancellation is still not proof the remote DELETE did not execute, as the interface Javadoc says. Two implementation hazards need a precise check before candidate:

1. `OssMigrationObjectStore`'s new `exists(..., Duration)` and `delete(..., Duration)` are **default** methods that silently delegate to the old unbounded operations. The production `DefaultOssMigrationObjectStore` overrides both, but a test or later alternate implementation can satisfy the port while defeating the strict timeout contract. Prefer abstract required methods (updating current fakes) or a fail-closed default. This is contract integrity, not a request to refactor ordinary OSS operations.
2. `MybatisOssMigrationStore.saveItem` now checks `updateById` row count but still has no version/status predicate. It cannot protect an UNKNOWN reservation from a stale `fail(item)` or progress write. The new mapper `updateState` has good `version + status + del_flag` CAS, and `claim` now excludes FAILED at COMPLETED stage. The final orchestrator must route **every** item mutation that can race the reservation through locked read and `updateState`; leave `saveItem` only for genuinely isolated cases or narrow it. SQL CAS alone does not close a remaining generic saveItem caller.
