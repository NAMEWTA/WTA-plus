## 1. 实现摘要

新增独立权限 `system:user:temporaryPassword` 的 POST 签发 API。服务端以 T-03 策略生成合规值，仅在本次 `no-store` 响应中返回明文；Redis 按 userId 保存 BCrypt 校验值并设置 60 秒 TTL，重新签发覆盖旧值。password grant 保持永久 BCrypt 优先，仅在永久密码失败时验证临时值；Client/userType 准入完成后再执行 Lua compare-and-delete，唯一赢家进入既有普通 Token 流程。

`SysLoginService` 将账号/锁定判断、一次失败计数和成功清理拆成明确接缝，永久与临时值共同构成一次 grant 判定。临时签发业务审计通过事件 enrich 只落目标 userId 与 TTL，关闭原始 request/response 入库。

## 6. 双轴审查

### Lead Candidate E2E

- **环境：** clean candidate JAR；Spring Boot `18086`；MySQL `8.4.11` / `specdev_t04` / `3308`；Redis `6399`。仅为本机直接 JSON HTTP 设置 `api-decrypt.enabled=false`，验证码、controller、service、BCrypt、Client 准入、数据库、Redis 与 Token 均使用真实实现。
- **权限负向：** 普通测试用户签发自身临时密码返回 403，目标 Redis key 不存在。
- **签发/覆盖：** 连续两次签发均返回 60 与 `Cache-Control: no-store`；Redis TTL 均为 60，旧值登录失败且新值仍存在，DB 永久 hash 指纹保持。
- **组合判定：** 普通错误密码仅增加一次失败计数且不消费；正确永久密码成功、清除计数且不消费临时值。
- **Client 顺序：** 仅具 sys_user 域的测试用户在 app Client 被拒绝，凭据仍存在；随后在 pc Client 登录成功并消费。
- **并发/过期：** 双并发恰好一成功；人工缩短一次性测试 key 的 TTL 后，过期登录与普通错误登录返回相同通用错误。
- **普通会话：** 永久与临时登录响应使用相同 Client 时长，profile 身份一致；Redis 与返回对象均无临时会话标记。
- **审计：** 多条成功签发记录的 `oper_param` 均只含目标 userId 与 TTL，`json_result`、`error_msg` 为空。

真实 E2E 通过 API 绕过前端权限指令和表单校验，直接核对 Redis key、TTL、数据库 hash、失败计数、Client 准入、Token profile 与审计记录。测试输出和本 Evidence 不保存凭据、Token 或 Redis hash。
