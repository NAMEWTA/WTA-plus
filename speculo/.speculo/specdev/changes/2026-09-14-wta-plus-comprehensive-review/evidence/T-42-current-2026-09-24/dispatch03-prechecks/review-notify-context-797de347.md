# NotifyContextConfiguration no-request fix — fixed-source independent review

Source: clean `797de3470258b4e77e6c32d6f28184d0d279de31`, tree `48ad9ba0c8d7b3851359494e0cbfa3191c9f327f`. This review read only the fixed source, relevant caller/security paths, and retained test summaries; it ran no build or service and changed no repository file.

**Code verdict: no blocking correctness or authorization finding in the narrow production change.** `backend/wta-admin/src/main/java/org/namewta/web/config/NotifyContextConfiguration.java:19-23` now checks the active Sa-Token context before calling the unchanged `LoginHelper.getLoginUser()`. Sa-Token 1.45's thread-local implementation defines `isValid()` as the presence of a current context box; without one it returns false without reading a servlet request. With a valid request it delegates to precisely the previous login-user call. A valid but unauthenticated request still yields `null` through `LoginHelper`'s existing `NotLoginException` handling. Unexpected errors in a valid request are not swallowed; the new conditional does not catch them. The registered production Servlet filter covers REQUEST/ASYNC/ERROR dispatch, and the older Spring context implementation also uses a web-context validity check.

The empty return affects the common-notify `NotifyContext` audit/provider context, not the persisted attachment identity. `RequestNotifyContextResolver.resolve()` maps a null login user to null user/Client. `NotifyDispatcher.resolveContext()` accepts that context and snapshots/events use it. Attachment submission separately calls `SessionNotifyAttachmentActorAdapter.current()` from `NotificationApplicationRuntimeService.attachmentActor()`, requires positive user/Client IDs for any nonempty attachment list, and persists both into `NotifyIntent`; the worker snapshot adapter reserves/copies using that stored Intent actor and does not infer identity from the background audit context. `NotificationController.submit` retains `@SaCheckPermission("notify:notification:submit")`. No change was made to those production paths, the security filter, or the public API.

The full-context Mail test logs in before submission and exercises the independent attachment actor, but does not explicitly assert the configured resolver's value while its request context is valid. Add a single actual-Bean assertion under a valid Sa-Token request context for both user ID and Client PK (and restore thread-local/global context in `finally`), preferably in that existing test file or at the existing full-context login fixture. This is a targeted verification gap, not evidence of a current production bypass and not a reason to alter the Mail/attachment contract.
