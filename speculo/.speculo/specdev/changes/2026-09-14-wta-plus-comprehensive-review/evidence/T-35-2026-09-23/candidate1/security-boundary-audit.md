## Immediate boundary findings

1. **High — actual ordinary HTTP log contains CAPTCHA recipient phone.** `CaptchaController.java:62-73` accepts `GET /resource/sms/code?phoneNumber=...` and constructs a sensitive command. `SysLogFilter.java:178-185,306` records all request parameters unless `LogSanitizer.isSensitiveName` says otherwise. `LogSanitizer.java:21-52` does not classify `phoneNumber`/`phone` as sensitive and only masks ordinary `code` on OAuth paths. Thus the unmodified `SysLogFilter` emits the exact phone in its `HTTP_REQUEST.parameters` on this reachable route. Editing only Dispatch/runtime/planner/resultService/SMS adapter cannot close this. Before claiming AC-035 ordinary-log safety, Lead must register a narrow write set for `backend/wta-common/wta-common-json/src/main/java/org/namewta/common/json/utils/LogSanitizer.java` and its test (or an equivalent logging-policy owner). Use path-aware coverage, not a global `code` mask that hides unrelated business status fields. Also test `NotificationController.java:25-29` `@Log` on POST `/notify/notification`: a sensitive `NotificationCommand` body can contain `templateParams.code`, `recipientIds` phone and `bizId` phone; `LogAspect` serializes request data through the same sanitizer. Current CAPTCHA GET itself has no `@Log`, but the HTTP filter alone suffices for the phone leak.
2. **High contract gap — REDACT flag does not sanitize common delivery event.** `CaptchaController.java:73` and `PersonRebindNotificationService.java:154` put `audit=REDACT_SENSITIVE` in `NotificationCommand.metadata`. `NotificationApplicationRuntimeService.java:58-71` persists metadata alongside potentially sensitive `bizId`, `templateParamsJson` and recipient snapshot. `DispatchNotificationService.java:106-116` builds `NotifyRequest` without `auditPolicy`, so `NotifyRequest.java:30,51` defaults to `FULL`. Even after wiring the flag, `NotifyDispatcher.java:286,299` publishes `NotifyDeliveryEvent` with the original full request/result; the event record holds phone targets and OTP-bearing template params, and for CAPTCHA `bizId` can be the phone. No production listener of this event was found by repo-wide Java search, so this is **not proof of a currently emitted log line**; it is an unredacted event object and an explicit conflict with T-35 revision150's event-clean requirement. The authorized paths can set the policy but cannot make the adapter receive real OTP while the common Dispatcher publishes a sanitized event copy. If event object must be clean, Lead must first extend the exact write set to `wta-common-notify/.../core/NotifyDispatcher.java` plus its unit tests (and, if required, the event contract). Redact both request and result targets, `bizId`, content params and any free-form metadata for sensitive events; preserve actual adapter input and default FULL behavior. Do not merely assert `auditPolicy == REDACT_SENSITIVE` while event fields still expose canaries.
3. **Medium — provider-supplied error text can cross into persistent and management surfaces.** `SmsNotifyChannelAdapter.java:45-49` copies arbitrary `SmsNotificationReceipt.errorCode/errorMessage`; `DispatchNotificationService.java:121-133` forwards them, and `NotifyDispatchResultService.java:71-89` stores them in Delivery, Attempt and Outbox. `NotificationDeliveryView.java:10-18` exposes `errorCode` and `providerMessageId` to the management endpoint. Built-in `Sms4jNotificationProviderResolver.java:48-49` currently emits a fixed rejection code/message and extracts a provider serial rather than phone, so no built-in raw-text management leak is proven. The public provider port permits custom/error values, however; a fake provider can place a phone/OTP canary in `errorCode`, and the current adapter will expose it through `NotificationDeliveryView`. Within the authorized SMS adapter/resultService, store a stable local error category and generic text rather than arbitrary provider message; preserve genuine opaque message ID for receipt correlation, but avoid using untrusted ID as display proof without a canary test. Do not put error payload or target into Evidence.

## Existing safe/intentional data paths

- `NotificationApplicationRuntimeService.java:60,95-110` intentionally persists template variables (including OTP) and physical phone in private business tables so the worker can send. AC-035 forbids ordinary logs, management snapshots and Evidence; it does not authorize dropping required dispatch data. `intent.contentSnapshot` currently defaults to template code when no `content` is provided, so CAPTCHA's stored logical snapshot is not the OTP by default.
- `NotificationApplicationRuntimeService.java:143-155` returns `NotificationSnapshot` of status, user ID, channel and provider ID, not template params or target. `NotificationMonitorController.java:35-53` maps delivery entities through `NotificationDeliveryView`, which omits `targetValue`, `targetSnapshotJson`, `contentSnapshot` and `errorMessage`. These existing projections should stay narrow. `providerMessageId` and `errorCode` remain conditional untrusted inputs as above.
- An SMS logical `NotifyTemplateContent.contentSnapshot` can be a stable non-empty description based on scene/template and variable **names**. Never concatenate OTP, phone, arbitrary variable values or an enumerable short-value hash into it. Keep actual SMS template code/params in provider fields; `NotifyDispatcher.java:127-131` must continue rejecting blank template snapshots.

## Failure phase and retry classification

- **Before provider I/O:** `NotifySendPlanner.plan` returns deterministic binding/account/template/required-variable failures before adapter call, but `finish` acquires quota; any new pure template/mapping/snapshot validation should happen before quota acquisition. `NotifyDispatcher.validateRequest` throws `NotifyValidationException(CONTENT_SNAPSHOT_REQUIRED)` for empty SMS snapshots (`NotifyDispatcher.java:127-131`). Provider resolution can throw `NotifyValidationException(UNKNOWN_PROVIDER)` before `SmsNotifyChannelAdapter` enters its per-target try. Current `DispatchNotificationService.java:135-139` maps these known local exceptions to `UNKNOWN`, causing `NotifyDispatchResultService.java:86-97` to select `WAITING_RECEIPT`. Catch determinable validation errors separately and persist `FAILED`; ensure `configFailure` at `NotifyDispatchResultService.java:152-155` recognizes exact new local codes so Outbox becomes `DONE`, not `READY` or `WAITING_RECEIPT`. Keep error text fixed and non-sensitive.
- **After provider call begins:** `SmsNotifyChannelAdapter.java:39-54` currently catches any RuntimeException from `sender().send` and returns `PROVIDER_ERROR` as `FAILED`; common `NotifyDispatcher.java:105-109,257-282` likewise synthesizes failed result for an adapter exception. A request may already have been accepted when the response is lost. AC-035 requires a conservative UNKNOWN persistent outcome for that ambiguity. The authorized Dispatch/SMS adapter can classify `PROVIDER_ERROR` separately from explicit provider rejection, but current common idempotency completion/event may still carry FAILED. Do not label a post-I/O failure as safe to resend or claim T-37 idempotency fixed; any requirement for fully consistent common-event/idempotency UNKNOWN is an additional exact write-set/contract decision for Lead.
- **Explicit rejection:** keep a known negative provider response distinct from exception/response loss. It can be FAILED and eligible for the existing policy, but T-37 owns actual re-invocation, duplicate suppression and Redis failure repair. Do not expand this T-35 fix into a general resend rewrite.

## Public callers and event consumers (follow-up inventory)

Production `NotificationCommand` constructors at the fixed baseline are in `wta-admin` `AuthController` and `CaptchaController`; `wta-demo` `SmsController`, `MailSendController`, `WebSocketController`; `wta-notify` `NotifyNoticePublisherService`, `NotifyTestSendService`; `wta-profile` `EnterpriseTransferService` and `PersonRebindNotificationService`; and `wta-workflow` `FlwCommonServiceImpl`. In addition, `wta-notify` `NotificationController.submit` accepts the public command directly from an authenticated admin POST. These callers share the `NotificationApplicationService` API but have distinct data sensitivity; `CaptchaController` and `PersonRebindNotificationService` explicitly set metadata `audit=REDACT_SENSITIVE`, while others should retain their existing audit behavior unless their own content warrants it. Only `DispatchNotificationService` invokes the lower-level `NotifyClient.send` in production.

For `NotifyDeliveryEvent`, a repo-wide production-Java symbol search found its record declaration, `NotifyDispatcher` publish/duplicate-publish sites, `NotifyEventPublisher`, and `NotifyAutoConfiguration` forwarding to Spring `ApplicationEventPublisher`; it found **no production listener or adapter consuming this event**. Unit tests capture it through test publishers. Thus a current event object can contain secrets but no built-in event-log sink is proven. A future subscriber, test failure display, debug serializer, or instrumentation would expose them unless the published sensitive event is a safe copy.

The safe-copy boundary for `REDACT_SENSITIVE` needs to cover both halves of the event, while leaving the real `NotifyAdapterRequest` unchanged:

| Event portion | Sensitive or untrusted fields | Safe-copy assertion |
|---|---|---|
| `NotifyRequest` | `bizId` (CAPTCHA caller uses phone), every `targets[].value`, content subject/text/rich body/template `params` and `contentSnapshot`, `idempotencyKey` (may encode target in public callers), arbitrary `metadata` values and potentially caller-supplied `requestId` | Neither serialized event nor any accessible request field contains phone/OTP canary. Retain only safe typed classification such as channel, target type/count, audit policy and known-safe status/opaque internal IDs; use fixed redaction markers or omit fields. Never retain a short-value digest of OTP/phone. |
| `NotifyResult` | Every `deliveries[].target.value`, provider-returned `errorCode`, `errorMessage`, and `providerMessageId` (opaque but untrusted until validated), plus free-form `providerKey` if treated as public audit output | A sensitive event exposes status/count/duration and safe error category only; no original target or provider free text. Keep actual provider message ID in the internal return/persistence path for receipt correlation, but do not copy an unvetted value into the audit event. |
| Other event fields | `originalRequestId` may be caller-derived; `NotifyContext.traceId` can be request-supplied; typed `userId/clientPk`, log ID, attachment IDs and timestamp are usually safe technical metadata | Include context in a synthetic-canary event assertion or explicitly constrain the guarantee to Request+Result. Avoid a full-record `toString()` in logs/Evidence while any field is unclassified. |

Concrete tests for the T-35 writer: capture a sensitive event with distinct synthetic phone and OTP canaries and assert absence from **every Request and Result field plus serialized event**, including the duplicate-publish path; assert the Adapter received the original phone/OTP/template mapping once. A default `FULL` non-sensitive event should retain its established fields. For HTTP logging, exercise `GET /resource/sms/code?phoneNumber=<synthetic>` and a sensitive `POST /notify/notification` body with `templateParams.code`, `bizId` and `recipientIds`; assert canaries absent from both SysLog HTTP event and `@Log` operation event while ordinary numeric `code` on unrelated routes remains visible. This requires path-aware/command-aware policy rather than adding `code` to the global sensitive-name set.
