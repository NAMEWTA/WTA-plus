# T46 minimal implementation seams — read-only design input

Product facts are from fixed `11c6e9e6f74e218b8d75bb9d41a2c5c384e51b40` (T45 worktree remains writer-owned); this refines `/tmp/wta-t46-current-audit.md` and Ticket 46/AC-046. No repository edit, build, test, service or production operation was performed. The accepted scope is one object at a time, Object→Item locking, existing migration item status fields, and no new distributed state machine or schema.

## Smallest viable ownership and methods

1. Keep `OssStorageMigrationService` as the batch/IO orchestrator. Add **one** proxied migration-local Spring service, for example `OssMigrationLockedOperations` under the already declared `.../oss/migration/` root, with public `@DSTransactional` methods called from the orchestrator: `unpublishOne(ossId)`, `rollbackOne(itemId)`, `switchPointerAfterVerifiedCopy(itemId)`, `restoreAfterFailedAccessCheck(itemId)`, `reserveCleanup(itemId, now)`, and `completeCleanup(itemId, reservationVersion, outcome)`. Each starts by locking `sys_oss` via existing `SysOssMapper.selectByIdForUpdate`, then locks/reloads the relevant item; never call one annotated method via same-class self-invocation. `exists`, copy/verify, access verification, and DELETE stay outside these short DB transactions. The pair of short cleanup transactions surrounds only one object; the batch loop never holds all rows while an object is probed/deleted. Existing `OssLifecycleManager.cleanupExpired` already locks the object, so it participates without a new lifecycle primitive.
2. Extend `OssMigrationStore`/`MybatisOssMigrationStore` with `findObjectForUpdate(ossId)`, `findItemForUpdate(itemId)`, `findLatestItemForObject(ossId)` **without early status filter**, `hasUnresolvedCleanupFence(ossId)` and `updateItemIfVersionAndStatus(...) -> boolean`. The current `findLatestRestorable` filters to `CLEANUP_ELIGIBLE` before ordering and can bypass a newer/older unresolved delete. A single object-row lock serializes participating writers, while a version/status CAS and exact-one count prevent stale item updates from being reported successful. Keep the existing `compareAndSetService` (exact-one) in the same transaction as the matching item CAS. Do not treat `saveItem`'s ignored `updateById` count as a fence. `SysOssMigrationItemMapper` needs select-for-update and CAS SQL; `SysOssMapper.java/XML` already supply the object lock and service CAS and need changing only if their exact conditions prove insufficient. `saveBatch`/aggregate refresh can follow the one-item commit, but must not turn a failed item/pointer transaction into a claimed successful response.
3. Use the existing item columns, not a new state: before DELETE, `reserveCleanup` rechecks locked current service/ACTIVE object, item identity and source/target/key, eligibility time, latest restorable position, and **absence of any unresolved cleanup fence for that object**. It commits `status=FAILED`, `lastErrorStage=COMPLETED`, fixed `errorMessage=CLEANUP_OUTCOME_UNKNOWN`, `version+1` (add the fixed enum/error code in `OssMigrationError`), and leaves pointer on target. Only after the reservation commit is *known* may the orchestrator issue one bounded external DELETE. If the DB commit ACK is lost, perform a bounded independent readback of the exact item/version/marker; if not proven, issue zero DELETE. `completeCleanup` relocks Object→Item, checks reservation version and pointer/identity, then marks `COMPLETED` after a definite result; zero affected rows rolls back and leaves the fence. A DELETE timeout, network failure, ambiguous provider result, or final DB ACK loss leaves the persistent UNKNOWN fence. Never auto-clear it from `retry`, `rollback`, `unpublish`, `process`, or a second `cleanup` call. A controlled later reconciliation may HEAD source/target and check current pointer under the same lock, but cannot blindly reissue DELETE or restore while a late DELETE remains possible.
4. The `FAILED/COMPLETED/UNKNOWN` reservation is consistent with the approved contract precisely because it is a **durable veto**, not proof that deletion ran. Existing `retry()` already excludes FAILED at COMPLETED; `rollback()` currently accepts nonterminal FAILED and must explicitly veto this marker. `unpublish()` must read latest item plus any unresolved fence under the lock, not the currently status-filtered `findLatestRestorable`. `process()` and its failed-access automatic restore must veto any unresolved fence before switching the pointer. For all pointer changes, object and item updates must commit together or roll back together; no external I/O is placed inside that transaction. Mixed old/new migration writers during rollout would bypass this protocol, so use an atomic worker/service cutover or quiesce old migration operations.

## The one likely common write-set expansion: bounded DELETE

Current `DefaultOssMigrationObjectStore.delete` calls `OssFactory.instance(service).delete(key)`; `AbstractOssClientImpl.bucketDelete` uses `s3AsyncClient.deleteObject(...).join()` with no total call budget. A minimal public common method is `OssClient.delete(String key, Duration timeout)` (or a clearly named bounded equivalent), implemented in `AbstractOssClientImpl` by the same default-bucket DELETE with per-request SDK override. Only `OssMigrationObjectStore.delete`/`DefaultOssMigrationObjectStore.delete` need the bounded overload and `OssStorageMigrationProperties` needs a validated per-object `deleteTimeout`; keep ordinary OSS delete unchanged. Pre-register exact extra paths `backend/wta-common/wta-common-oss/src/main/java/org/namewta/common/oss/client/OssClient.java` and `.../AbstractOssClientImpl.java`; `DefaultOssClientImpl.java` is unnecessary unless actual SDK configuration testing shows otherwise. Bind public API compatibility and update common consumers/tests.

Local SDK 2.48.1 fact: `DeleteObjectRequest.Builder.overrideConfiguration(Consumer<AwsRequestOverrideConfiguration.Builder>)` and `RequestOverrideConfiguration.Builder.apiCallTimeout(Duration)` / `apiCallAttemptTimeout(Duration)` exist (`javap` on installed jars). Prefer that request-level total + attempt budget and cancellation of the returned future to an outer `Future.get()` alone. The SDK's own local source explicitly says abort after timeout is **not strictly prompt** and may lag several seconds. Therefore a configured timeout limits ordinary waiting but cannot prove a remote DELETE will never complete late. The precommitted UNKNOWN fence remains mandatory after timeout. Do not describe either SDK timeout or interrupt as an exactly timed external cancellation. Validate that a delayed owned MinIO request leaves the application free to process a second object without losing its source.

## Exact verification additions

Under existing `backend/wta-admin/src/test/java/org/namewta/test/oss/migration/`, extend `OssStorageMigrationServiceUnitTest` for all pointer/marker CAS zero-row, latest-item/fence rejection, no DELETE before proven commit, no blind second DELETE, and fixed error code; extend `OssStorageMigrationIntegrationTest` with two physical MySQL sessions and a blocking `OssMigrationObjectStore`. Prove the second connection is actually blocked on the same `sys_oss` row (connection IDs, lock wait/timeout), not merely paused by thread scheduling. Test both orders: restore commits first → cleanup re-read refuses with zero DELETE; cleanup reservation commits first → unpublish/rollback/process restoration refuse before and after external timeout. Include an older eligible item and one unrelated object that still progresses. Inject service/item CAS failures and transaction rollback; assert pointer+item remain atomic. Inject lost reservation/finalization ACK and late successful DELETE; assert UNKNOWN remains, current pointer stays target, and only inspected reconciliation can mark final state. Use owned MinIO HEAD/GET to prove source/target bytes and pointer claims, with zero-skip fresh XML.

For the common overload, add a focused OSS client unit test capturing DeleteObject request override timeout and one owned MinIO delayed-response test for the *application's bounded return/fence behavior*; do not claim strict remote cancellation. Existing `OssStorageMigrationIntegrationTest`'s sequential single-session flow cannot substitute for this concurrency evidence. `SysOssMigrationController` routes/permissions and schema need no expansion for this minimal design. Any new common paths require Ticket write-set registration before implementation.
