## Backend contract

- **Atomic version fence and lock order.** `NotifyNoticeUseCase.java:25-31` puts publish/retract in `@DSTransactional`. Retraction takes the Notice lock, finds the latest version, then locks that version's Intent (`NotifyNoticeService.java:121-147`; `NotifyNotificationDao.java:99-116`). The marker binds app, scene, business ID, idempotency key, snapshot and version; malformed/old unverified notice metadata cannot authorize a new dispatch (`NotifyNoticeVersionFence.java:24-47,59-98`). Metadata-only update requires exactly one row and preserves current aggregate status. Re-publication uses a new version/idempotency key (`NotifyNoticePublisherService.java:45-77`). The missing-Intent exception is restricted to the two verified six-SQL static V1 seeds, with no same-business Intent (`NotifyNoticeService.java:150-171`); it is not a generic success path.
- **Execution-grant boundary.** Worker calls `deadlineGate` before routing and again immediately before `notifyClient.send` (`DispatchNotificationService.java:69-124`). The result service takes Intent→Outbox→Delivery locks, validates live owner/token with database time, then distinguishes a proven new READY external task from a reclaimed/unknown task (`NotifyDispatchResultService.java:28-80,119-170`). A retract before external execution grant closes only the proven unsent task: claimed from READY, durable `DEADLINE_UNSENT_READY`, both attempt counts zero and no provider/accept/delivered fact. Legacy or reclaimed external work goes UNKNOWN/WAITING_RECEIPT rather than being falsely cancelled (`:135-170,226-236`). IN_APP persisted relation/message facts take precedence; inconsistent local facts terminate without external resend (`:192-249`). Manual retry rejects RETRACTED and UNVERIFIED versions before opening target tasks (`NotificationApplicationRuntimeService.java:179-218`).
- **Actual post-grant results survive retract.** Provider I/O is outside the result transaction (`DispatchNotificationService.java:45-48,120-124`); completion writes the actual Delivery/Attempt/Outbox result and provider message ID under the current owner fence (`NotifyDispatchResultService.java:313-367`). Retraction changes the version marker, not a previously accepted/delivered result or historical message. A delayed result after the second gate is deliberately not described as recallable. The old-owner and rollback paths remain covered by the A4 real-DB matrix.
- **Published content and owned link.** Publication inserts a frozen snapshot, validates the receipt and exact Intent/version, and for IN_APP atomically rewrites Snapshot.pathSnapshot, Intent.pathSnapshot and templateParams.path to `/notify/inbox?messageId=<receipt intent ID>`; each write must affect one row (`NotifyNoticePublisherService.java:45-90`). `InAppNotificationService.java:35-72` persists the message under that same Intent ID with frozen content and recipient relation. External-only publication retains the generic `/notify/inbox` path. A late write conflict rolls back the publication transaction. The inbox GETs derive the current user from `LoginHelper`, and detail performs a user-relation JOIN before projecting content (`NotifyInboxController.java:20-35`, `NotifyNotificationDao.java:258-280`); no management permission is needed for one's own detail, and mutation permissions remain separate.
