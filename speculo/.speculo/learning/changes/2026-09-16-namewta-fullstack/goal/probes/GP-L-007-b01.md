## Q3 假设与反例

- objective_id: OBJ-07
- bloom_level: evaluate
- socratic_move: assumptions
- expected_evidence: `createOssUploadClient` 258–259 行 `requireClientId` 在工厂体顶；`services.ts` 37 行在 44 行之前；`domain-notify/src/transport.ts` 无 recipients；`NotifyUserDirectory` 在 `web-domains/notify/src/runtime.ts`；`workflow/src/index.ts` 337 行 `createUserQueryPort`；`notificationDirectory.usersByIds` 无空数组短路；`adminManifestRegistry.ts` `resolveAttachments` 用 `systemService.resources.oss.listByIds`
- difficulty: high

课的隐含假设：合格读者能把「本文件互不 import」说成胶水层事实，不会把厨房内部的 `domain → domain`、也不会把 registry 里后接的 OSS 线，算进这张插座板的虚线。工作树反例：

1. **空 `VITE_APP_CLIENT_ID` 不是局部 OSS 故障。** 课：adapter 构造期抛 `OSS upload clientId is required`，是接线失败。源码：`requireClientId` 在 `createOssUploadClient` **返回对象之前**执行（`client.ts` 258–259）。该调用在 `services.ts` 37 行，**早于** 44 行的 `createIdentityAccessService`。模块求值抛错则登录单例根本不会被绑定。读者可能把「接线失败」说成「还能登录、只是不能传文件」。
2. **`notificationDirectory` 不是对 domain 方法的转发。** 课已写「不是工厂返回值」。更强的磁盘事实：`domain-notify` 无 `recipients` 模块、`createNotificationService` 无 search。App 自己打 `/notify/recipients/*`，只从 notify **借类型** `NotifyUserCandidatePage`。端口形状在 web-domain。读者可能把组合点说成「实现了 notify domain 已有的目录工厂」。
3. **`usersByIds` 没有对空关键字那条短路。** `ids.join(',')` 为空仍 GET。课只把空输入边界写在 `searchUsers`。读者可能把「目录组合层短路」推广成两条方法。
4. **workflow 的用户口是第五条厨房内虚线，不是本板漏画。** `createWorkflowDefinitionService` 内部 `users: createUserQueryPort(http)`。课边界已写。合格读者仍可能指着 `workflowService.users` 说「厅堂把 system 传给了 workflow」。
5. **本文件接完胶水 ≠ 厅堂不再交叉 OSS。** registry 的 workflow runtime `resolveAttachments` 再调 `systemService.resources.oss.listByIds`；`Editor/index.vue` 同时拿 `ossUploadClient` 与 `systemService`。这是消费点新接的线，不在 `services.ts` 四条虚线图上。

问：读完后，读者会不会把空 ClientId 说成「OSS 单独挂了」？会不会把 `notificationDirectory` 说成 `createNotificationService` 或 domain-notify 的方法？会不会把 `workflowService.users` 画进本课虚线？
