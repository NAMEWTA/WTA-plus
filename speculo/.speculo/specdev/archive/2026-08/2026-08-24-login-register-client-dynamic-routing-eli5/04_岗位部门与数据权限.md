# 岗位、部门与数据权限

这篇图解回答 4 个问题：

1. 部门有什么用？
2. 岗位有什么用？
3. 岗位、部门、角色有什么区别？
4. 数据权限怎样从角色配置变成数据库的过滤条件？

## 先看全图

```text
                         [一个用户]
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
         [所属部门]        [担任岗位]       [拥有角色]
          在哪里工作        做什么工作       能做什么操作
              |               |               |
              |               |               +-> [菜单和按钮权限]
              |               |               |
              |               |               +-> [数据范围]
              |               |                    能看哪些行
              |               |
              |               +-> [按岗位找人]
              |                    例如找“研发经理”
              |
              +-> [组织树和数据归属]
                   例如总部 -> 研发部 -> 测试组


[用户发起查询]
       |
       v
[接口检查：能不能使用这个功能]
       |
       v
[Mapper 声明：哪一列代表部门，哪一列代表创建人]
       |
       v
[数据权限拦截器读取当前角色的数据范围]
       |
       v
[在原 SQL 后面追加 WHERE 过滤条件]
       |
       v
[数据库只返回允许看见的行]
```

先记住一句话：

```text
部门 = 人和数据属于哪里

岗位 = 人在部门里做什么工作

角色 = 人能使用哪些功能，并能看多大范围的数据
```

岗位和角色都可以给人分类，但用途不同：

```text
[研发经理岗位] -> 用来表达职务、查找这类工作人员

[系统管理员角色] -> 用来授予菜单、按钮和数据范围
```

在当前代码中，岗位本身不会直接授予菜单权限或数据范围。

## 一步一步看

### 第一步：部门是一棵组织树

部门不是一张平铺名单。每个部门可以有上级部门，因而组成一棵树：

```text
[总公司]
    |
    +-> [研发中心]
    |       |
    |       +-> [后端组]
    |       |
    |       +-> [前端组]
    |
    +-> [市场中心]
```

部门表 `sys_dept` 保存：

```text
部门编号 + 上级部门 + 祖先路径 + 部门名称
         + 负责人 + 状态 + 联系方式
```

用户表 `sys_user` 中有一个 `dept_id`：

```text
[用户小王] --dept_id--> [后端组]
```

所以当前模型中，一个用户有一个直接所属部门。部门主要有四类用途：

```text
1. 组织展示：组成公司或机构的上下级树

2. 人员归属：按部门查找用户和部门负责人

3. 数据归属：业务数据用 dept_id 或 create_dept 标记归属部门

4. 范围展开：把“本部门及以下”展开为当前部门和所有子部门编号
```

例如当前用户属于“研发中心”，角色的数据范围是“本部门及以下”：

```text
[研发中心]
    |
    +-> [后端组]
    +-> [前端组]

允许的部门编号 = 研发中心 + 后端组 + 前端组
```

源码中的 `SysDeptMapper.selectDeptAndChildById` 会根据祖先路径找到子部门，再把当前部门自己也放进结果。

### 第二步：岗位是部门里的工作位置

岗位表 `sys_post` 保存：

```text
岗位编号 + 所属部门 + 岗位编码 + 岗位名称
         + 岗位类别 + 排序 + 状态
```

例如：

```text
[研发中心]
    |
    +-> [研发经理]
    +-> [Java 工程师]
    +-> [测试工程师]
```

用户和岗位之间不是“一人只能有一个岗位”。它们通过关系表 `sys_user_post` 连接：

```text
                       +-> [Java 工程师]
[用户小王] -> [用户岗位关系]
                       +-> [项目负责人]
```

因此，一个用户可以关联多个岗位，一个岗位也可以关联多个用户。

岗位主要用于：

```text
1. 记录职务：说明一个人在组织里承担什么工作

2. 人员分组：按岗位编号找到一批用户

3. 业务选人：例如工作流把“某岗位的人”选为候选办理人

4. 登录上下文：登录时把当前用户的岗位列表放进 LoginUser.posts
```

岗位记录自身也有 `dept_id`，所以岗位管理列表和岗位分配会受到部门数据范围限制。给用户绑定岗位前，系统会用带数据权限的查询确认这些岗位都在操作者可访问范围内；否则返回“没有权限访问岗位的数据”。

但是要分清：

```text
[岗位属于某部门] -> 这个岗位记录可以按部门范围过滤

[用户拥有某岗位] -X-> 岗位自动授予菜单或数据权限
```

第二条在当前代码中不成立。

### 第三步：角色才是权限规则的主要载体

一个角色同时回答两个问题：

```text
[菜单和按钮权限] -> 能不能进入页面、调用某个接口、执行某个操作？

[数据范围]       -> 操作已经允许后，能够接触哪些数据行？
```

角色的数据范围字段是 `sys_role.data_scope`。管理端提供 6 种选择：

```text
1  全部数据权限
   -> 不追加部门或本人过滤

2  自定数据权限
   -> 只允许角色在部门树中勾选的部门

3  本部门数据权限
   -> 只允许当前登录用户所属部门

4  本部门及以下数据权限
   -> 允许当前部门和所有子部门

5  仅本人数据权限
   -> 只允许“本人列”等于当前用户编号

6  部门及以下或本人数据权限
   -> 满足部门范围，或者属于本人
```

只有“自定数据权限”需要额外勾选部门。保存时形成：

```text
[角色] -> [sys_role_dept 角色部门关系] -> [一个或多个允许部门]
```

所以 `sys_role_dept` 不是“用户属于哪个部门”，而是“这个角色在自定范围模式下允许访问哪些部门”。

### 第四步：登录时准备数据权限材料

登录成功后，`SysLoginService.buildLoginUser` 会组装当前会话：

```text
[sys_user.dept_id] -----------------------> [LoginUser.deptId]

[当前 Client 下的角色和 dataScope] -------> [LoginUser.roles]

[权限码 -> 能授予它的角色编号] ----------> [LoginUser.dataScopeRoleMap]

[用户岗位关系 -> 岗位列表] --------------> [LoginUser.posts]
```

这里的“当前 Client”很重要。部门和岗位实体本身没有 `clientId` 字段，但登录时装入会话的角色按当前 Client 收敛。因此，同一个用户进入不同 Client 时，可以因为角色不同而得到不同的数据范围。

`dataScopeRoleMap` 可以理解为一张索引卡：

```text
system:user:list -> [部门管理员角色 12, 审计员角色 18]

system:post:list -> [部门管理员角色 12]
```

它防止一个没有授予当前功能的角色，仅仅因为数据范围很大，就把本次查询范围意外放宽。

### 第五步：接口先检查“能不能做”

假设用户打开用户管理列表：

```text
[浏览器请求用户列表]
          |
          v
[@SaCheckPermission("system:user:list")]
          |
     +----+----+
     |         |
     v         v
[没有权限]  [拥有权限]
  拒绝请求       |
                v
          [继续查询数据库]
```

这叫功能权限。它控制的是“门能不能打开”，还没有决定打开门后能看见多少行数据。

### 第六步：Mapper 声明业务表中的两把尺子

需要行级过滤的 Mapper 方法使用 `@DataPermission`。例如用户列表声明：

```java
@DataPermission({
    @DataColumn(key = "deptName", value = "dept_id"),
    @DataColumn(key = "userName", value = "create_by")
})
```

日常语言可以这样读：

```text
计算部门范围时，请使用这条 SQL 的 dept_id 列

计算本人范围时，请使用这条 SQL 的 create_by 列
```

为什么不把列名写死在公共组件里？因为不同查询可能使用不同表名和别名：

```text
普通查询可能写 dept_id

多表查询可能必须写 d.dept_id

另一张业务表可能用 create_dept 表示部门归属
```

Mapper 最了解本条 SQL，因而由 Mapper 告诉拦截器应该使用哪一列。

这里还有一个容易误会的边界：在上述用户 Mapper 中，“仅本人”比较的是 `create_by = 当前用户编号`，意思是“本人创建的记录”，不等于“用户表的 user_id 就是本人”。换到其他 Mapper 时，含义取决于该 Mapper 给 `userName` 映射的真实列。

### 第七步：拦截器把范围翻译成 SQL

调用带注解的 Mapper 后，完整调用流是：

```text
[Mapper 上的 @DataPermission]
              |
              v
[切面把注解放进当前调用上下文]
              |
              v
[MyBatis 数据权限拦截器拦住 SQL]
              |
              +-> 读取当前登录用户和接口权限
              |
              +-> 只选出能授予本接口权限的角色
              |
              +-> 读取每个角色的 dataScope
              |
              +-> 使用 DataScopeType 模板生成条件
              |
              +-> 需要部门编号时调用 sdss 服务展开
              |
              v
[把条件用括号追加到原 WHERE 后面]
              |
              v
[数据库执行最终 SQL]
```

`sdss` 是数据权限服务 `SysDataScopeServiceImpl` 的固定名字。它做两件事：

```text
自定范围
[角色编号] -> [sys_role_dept] -> [逗号分隔的允许部门编号]

部门及以下
[当前部门编号] -> [部门树] -> [当前部门和全部子部门编号]
```

没有配置出有效部门时返回 `-1`，使条件匹配不到正常部门，而不是错误地放行全部数据。

### 第八步：看一个具体 SQL 例子

假设：

```text
当前用户编号 = 9001
当前用户部门 = 研发中心 100
研发中心的子部门 = 后端组 101、前端组 102
当前角色数据范围 = 本部门及以下
```

业务原本只想查询正常用户：

```sql
SELECT *
FROM sys_user
WHERE status = '0'
```

数据权限拦截器会追加部门范围，效果近似为：

```sql
SELECT *
FROM sys_user
WHERE status = '0'
  AND (dept_id IN (100, 101, 102))
```

数据库外的其他部门记录没有先查出再隐藏，而是在 SQL 阶段就不会返回。

如果查询同时有两个能授予本接口权限的角色：

```text
[角色 A：本部门] OR [角色 B：仅本人]
```

查询条件默认按“或”组合，看到的是两个允许范围的并集。只要其中一个有效角色是“全部数据”，查询就不再追加范围过滤。

更新和删除默认使用“且”组合，必须同时满足参与计算的范围，控制会比查询更严格。

### 第九步：什么情况会放行、拒绝或根本不处理

```text
[超级管理员]
       |
       +-> 直接跳过数据过滤

[普通用户 + 有匹配角色]
       |
       +-> 按角色 dataScope 追加 SQL

[接口有权限约束，但没有角色可参与数据范围计算]
       |
       +-> 追加 1 = 0，返回零行

[角色范围需要某列，但 Mapper 没有提供这列]
       |
       +-> 使用 1 = 0 兜底，不扩大权限

[Mapper 方法没有 @DataPermission]
       |
       +-> 拦截器不为它自动追加数据范围
```

最后一种最重要：数据权限不是“系统里配置了角色范围，所有 SQL 就天然安全”。只有明确接入 `@DataPermission`、并正确映射部门列或本人列的 Mapper 查询，才会得到这层自动过滤。

## 术语小词典

- 组织树（部门树）：像家谱一样记录部门的上下级关系，用来表达“本部门”和“本部门以下”。
- 工作位置（岗位）：人在某个部门里承担的职务，可用于按岗位找人；专业名字是岗位（Post）。
- 权限套餐（角色）：把菜单、按钮和数据范围打包后授予用户；专业名字是角色（Role）。
- 能不能做（功能权限）：决定能否调用某个功能，例如 `system:user:list`。
- 能看多少（数据权限）：功能已经允许后，继续限制数据库可以返回或修改哪些行。
- 行级过滤：不隐藏整张表，只根据规则过滤其中的记录；专业名字是 Row-Level Data Filtering。
- 方法标签（注解）：贴在 Mapper 方法上的说明牌；这里的专业名字是 `@DataPermission`。
- SQL 守门员（拦截器）：数据库执行 SQL 前检查并改写 SQL 的组件；这里是 `PlusDataPermissionInterceptor`。
- 条件模板（数据范围类型）：把 1 到 6 的范围代码翻译成 SQL 条件；专业名字是 `DataScopeType`。
- 部门展开服务：把角色自选部门或“当前部门及以下”变成部门编号列表；Spring Bean 名是 `sdss`。
- 查询条件（WHERE）：告诉数据库只挑出满足条件的行。
- 失败时收紧（Fail Closed）：资料缺失或规则无法匹配时返回零行，而不是放行全部数据。

## 你现在能复述什么

```text
问题一：部门有什么用？
答案：表达组织上下级、用户归属、数据归属，并为“部门及以下”提供范围。

问题二：岗位有什么用？
答案：表达部门内的职务，用于人员分组、按岗位找人和工作流选人。

问题三：谁决定权限？
答案：角色决定功能权限和数据范围；岗位本身不直接授权。

问题四：数据权限怎样落地？
答案：角色 dataScope + 当前接口允许的角色 + Mapper 列映射
      -> MyBatis 拦截器追加 WHERE
      -> 数据库只返回或修改允许范围内的行。
```
