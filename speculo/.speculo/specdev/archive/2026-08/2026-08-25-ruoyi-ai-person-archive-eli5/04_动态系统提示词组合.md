# 动态系统提示词怎样组合

## 先给结论

`ruoyi-snailai-server` 独立运行并不妨碍动态提示词。推荐把提示词分成两部分：

```text
[SnailAI Server 保存的固定底稿]
                +
[ruoyi-ai 每次请求生成的动态上下文]
                =
[本次真正发给模型的系统提示词]
```

固定底稿写角色、长期规则和输出格式；动态部分放当前操作者、当前分析对象、授权范围和本次查询得到的小量业务事实。

第一版不必修改 `ruoyi-snailai-server`。让聊天先经过受 RuoYi 登录保护的 `ruoyi-ai`，利用 SnailAI 已有的 `sid` 在“发出聊天请求”和“Agent Client 收到 gRPC 请求”之间关联动态上下文即可。

## 先看全图

```text
[用户在 RuoYi 页面输入“分析张三”]
                 |
                 v
[ruoyi-ai 聊天入口]
  1. 读取当前登录用户和 clientPk
  2. 校验张三档案访问权限
  3. 生成随机 sid
  4. 临时保存 sid -> 授权上下文
                 |
                 | OpenAPI chat，携带 sid
                 v
[独立的 SnailAI Server]
  1. 读取 Agent 固定提示词
  2. 读取绑定的 Skill
  3. 原样分发 sid
                 |
                 | gRPC
                 v
[ruoyi-admin 中的 ruoyi-ai]
  1. 自定义 PromptFactory 按 sid 取上下文
  2. 组合固定提示词 + 动态上下文
  3. 交给模型执行
                 |
                 v
[模型基于本次授权数据回答]
```

两个程序仍然各做各的事：

```text
ruoyi-snailai-server                  ruoyi-admin / ruoyi-ai
--------------------                 -----------------------
保存 Agent 固定指令                   认识 RuoYi 登录用户
保存和绑定 Skill                      认识 clientPk 和业务权限
管理模型、会话、聊天                   查询个人档案
把请求分发给 Agent Client              生成每次不同的业务上下文
```

## 一步一步看

### 第一步：把提示词拆成四层

不要维护一整块不断拼接的巨大字符串。把来源和可信程度分开：

```text
第一层：固定角色
“你是个人档案分析助手……”
来源：SnailAI Agent 配置
                 |
                 v
第二层：固定业务规则
“同名先消歧，事实与推断分开……”
来源：Agent 指令或版本化模板
                 |
                 v
第三层：Skill 使用说明
“先调用 search，再调用 get_context……”
来源：SnailAI 绑定的 Skill，框架自动追加
                 |
                 v
第四层：本次动态上下文
“当前 clientPk、允许的分析范围、personId、授权业务事实……”
来源：ruoyi-ai 每次请求生成
```

最终组合规则建议固定为：

```text
finalSystemPrompt =
    serverBasePrompt
    + stableBusinessPolicy
    + skillPrompt
    + authorizedRuntimeContext
```

用户输入的“帮我分析张三”仍然是用户消息，不要冒充系统提示词。数据库中的自由文本也不要直接当系统指令；只能作为被引用的业务数据，并限制字段和长度。

### 第二步：让 ruoyi-ai 成为聊天网关

新增一个受 RuoYi 登录保护的业务聊天入口，而不是让业务页面直接调用 SnailAI Server：

```text
ruoyi-modules/ruoyi-ai/src/main/java/org/dromara/ai/
|
+-- controller/
|   +-- PersonArchiveAiChatController.java
|
+-- service/
|   +-- PersonArchiveAiChatService.java
|   +-- AiPromptContextService.java
|
+-- prompt/
|   +-- DynamicPromptFactory.java
|   +-- SystemPromptComposer.java
|   +-- PersonArchivePromptContextProvider.java
|
+-- domain/
    +-- AiPromptContext.java
```

入口流程：

```text
POST /ai/person-archive/chat
        |
        +-- LoginHelper 取得 userId 和 clientPk
        +-- Service 校验 personId 是否可见
        +-- 查询经过白名单裁剪的分析上下文
        +-- 生成不可猜测的随机 sid
        +-- Redis 临时保存 sid 对应上下文
        +-- 调用 OpenApiChatClient.chatStream
        v
返回 SSE 流式回答
```

这个 POST 接口需要项目规定的权限注解和 `@Log`。由于消息和档案上下文可能敏感，日志不能保存完整请求正文。

### 第三步：用 sid 关联两边

SnailAI 1.1.1 的 `OpenApiChatRequest` 和 `ChatDispatchRequest` 都已经有 `sid`。它原本用于区分同一会话中的并发提交，也可以作为短期上下文的关联键。

```text
ruoyi-ai 发请求前：

sid = 随机值

Redis:
ai:prompt-context:{sid}
    -> userId
    -> clientPk
    -> agentId
    -> conversationId
    -> personId
    -> allowedPurpose
    -> 已裁剪的业务事实
    -> expiresAt

有效期：例如 1 到 5 分钟
```

保存时必须满足：

- `sid` 由后端生成，不接受前端自选。
- 同时绑定 `agentId` 和 `conversationId`，取出时逐项核对。
- 过期即拒绝，不回退为全局权限。
- 只保存生成提示词所需的数据，不保存登录 Token。
- 根据重试合同决定“一次消费”还是“短期内幂等读取”，不能无限期复用。

`ruoyi-ai` 当前没有直接依赖 Redis 模块；真正实现时应在它的 POM 中显式增加所需的 `ruoyi-common-redis` 依赖，不依赖其他模块偶然传递进来的 Jar。

### 第四步：替换 PromptFactory

SnailAI Agent Executor 的默认 `PromptFactory` 是 `@ConditionalOnMissingBean`。因此宿主应用可以在 `ruoyi-ai` 中声明自己的 `PromptFactory` Bean，默认实现就不会创建。

推荐结构：

```java
@Configuration
public class AiPromptConfiguration {

    @Bean
    public PromptFactory promptFactory(SystemPromptComposer composer,
                                       AiPromptContextService contextService) {
        return new DynamicPromptFactory(composer, contextService);
    }
}
```

动态工厂的职责：

```java
public Prompt build(ChatDispatchRequest request) {
    Long agentId = request.getAgentConfig().getAgentId();
    if (!composer.supports(agentId)) {
        return defaultPromptFactory.build(request);
    }

    AiPromptContext context = contextService.requireValid(
        request.getSid(),
        agentId,
        request.getConversationId()
    );

    String composed = composer.compose(
        request.getSystemPrompt(),
        context
    );

    ChatDispatchRequest decorated = copyWithSystemPrompt(request, composed);
    return defaultPromptFactory.build(decorated);
}
```

这里的 `supports(agentId)` 是明确配置的 Agent allowlist。自定义 `PromptFactory` 是整个 Agent Client 共用的 Bean，非个人档案 Agent 必须原样委托默认工厂，不能强制它们也携带业务 `sid`。allowlist 应通过类型安全配置加载并在启动时校验。

`copyWithSystemPrompt` 要复制请求，不建议修改原对象后再恢复。继续委托 `DefaultPromptFactory`，可以保留 SnailAI 现有的历史消息、用户消息和媒体附件处理。

`request.getSystemPrompt()` 必须保留，因为它已经包含 Server 组装的基础内容；Skill Resolver 也会在执行前把可用 Skill 说明追加进去。动态工厂只追加自己的命名区块，不能覆盖前面的内容。

### 第五步：组合器只接收结构化数据

建议最终提示词长这样：

```text
[BASE_AGENT_POLICY]
这里保留 SnailAI Server 下发的 Agent 固定指令和 Skill 说明。

[RUNTIME_ACCESS_SCOPE]
- 当前客户端主键：1001
- 当前分析用途：PERSON_ARCHIVE_REVIEW
- 允许字段：基本信息、教育经历、任职经历
- 禁止字段：证件号码、私人联系方式

[CURRENT_PERSON]
- personId：P20260825001
- 姓名：张三
- 部门：产品部
- 数据版本：7
- 数据更新时间：2026-08-25T20:00:00+08:00

[AUTHORIZED_FACTS]
- 任职年限：5 年
- 当前岗位：产品经理
- 已完成项目数：8

[OUTPUT_CONTRACT]
只基于授权事实回答，区分事实、推断、未知项和建议。
```

上面只是格式示例，不应把真实敏感档案写入 change 或代码仓库。生产中由 DTO 白名单生成，不使用实体的 `toString()`，不把整行数据库记录或任意 JSON 全量塞给模型。

### 第六步：什么时候不该放进系统提示词

```text
短、小、每轮都需要的可信规则和身份摘要
                    -> 系统提示词

大量、经常变化、需要按需查询的档案数据
                    -> Tool 返回值

长文档、附件、制度、历史资料
                    -> RAG 或资源检索

用户本次说的话
                    -> 用户消息
```

动态组合不等于把数据库所有信息都塞进系统提示词。系统提示词越长，成本越高，也越容易让模型忽略重点。

### 第七步：独立 Server 什么时候需要改

#### 推荐路线：不改 Server

```text
[业务前端]
    -> [ruoyi-ai 登录网关]
    -> [带 sid 调 SnailAI OpenAPI]
    -> [Server 原样分发 sid]
    -> [ruoyi-ai PromptFactory 组合]
```

前提是业务聊天必须经过 RuoYi 网关，不能允许客户端绕开网关伪造同一流程。

#### 直连路线：需要扩展 Server 集成

如果用户仍直接使用 SnailAI 自带或嵌入聊天页面：

```text
[用户直接访问 SnailAI Chat]
        |
        v
[SnailAI Server]
        |
        | 当前分发 DTO 没有完整的 RuoYi userId/clientPk
        v
[ruoyi-ai PromptFactory 无法识别可信业务用户]
```

这时需要扩展 Server 到 Agent Client 的分发合同，至少携带可验证的 `openId` 或短期业务上下文凭证；Agent Client 再把它解析为 RuoYi 权限范围。不能在 gRPC 执行线程里直接调用 `LoginHelper`，因为那里没有原来的 RuoYi HTTP 登录请求。

## 推荐的实施顺序

```text
[1. ruoyi-ai 新增受保护的聊天网关]
                 |
                 v
[2. 用 sid + Redis 建立短期上下文]
                 |
                 v
[3. 实现 SystemPromptComposer]
                 |
                 v
[4. 提供自定义 PromptFactory Bean]
                 |
                 v
[5. 加字段白名单、长度预算和敏感信息测试]
                 |
                 v
[6. 再决定是否支持用户直连 SnailAI Chat]
```

至少测试：不存在的 `sid`、过期 `sid`、错误 Agent、错误 conversationId、跨 Client、上下文查询无权限、并发提交、SnailAI 重试、自由文本中的提示词注入内容，以及日志是否泄露档案和 Token。

还要测试一个普通的非个人档案 Agent，确认它不需要业务 `sid`，且提示词与接入前完全一致。

## 术语小词典

- 固定底稿（基础系统提示词）：长期不变的 Agent 角色、规则和输出要求，保存在 SnailAI Server。
- 动态上下文：每次请求都可能不同的当前用户、分析对象、权限范围和业务事实。
- 聊天网关：业务前端进入 AI 聊天前必须经过的 RuoYi 接口，它负责登录和权限校验。
- 关联号码（`sid`）：把发出去的 OpenAPI 请求和返回 Agent Client 的 gRPC 请求对应起来的随机编号。
- 临时上下文仓库（Redis）：按 `sid` 保存几分钟动态数据，过期自动失效。
- 提示词工厂（`PromptFactory`）：把系统提示词、历史消息和用户消息组装成模型最终输入的 Java 扩展点。
- 字段白名单：明确规定哪些业务字段允许交给模型，名单之外一律不发送。
- 流式回答（SSE）：模型一边生成，网页一边收到文字的 HTTP 返回方式。

## 你现在能复述什么

1. 独立的 SnailAI Server 继续保存 Agent 固定指令、Skill 和会话，动态业务提示词由 `ruoyi-ai` 在 Agent Client 执行前组合。
2. 推荐让聊天先经过 `ruoyi-ai`，由登录线程生成 `sid` 并临时保存经过授权的上下文；Server 只需原样分发现有 `sid`。
3. 在 `ruoyi-ai` 中提供自定义 `PromptFactory` Bean，保留 Server 下发的原系统提示词，再追加结构化、裁剪后的动态上下文。
4. 如果用户绕过 RuoYi 网关直接使用 SnailAI Chat，当前分发请求无法可靠识别 RuoYi 用户，这时才需要扩展 Server 分发合同或建立新的可信凭证机制。
