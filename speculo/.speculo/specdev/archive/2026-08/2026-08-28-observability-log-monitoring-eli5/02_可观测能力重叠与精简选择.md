# 可观测能力重叠与精简选择

先说结论：这里确实有重复，但不是七个服务都在做同一件事。

如果当前首要目标只是“集中查看后端日志”，推荐的最小组合只有三个服务：

```text
[Alloy] -> [Loki] -> [Grafana]
  采集       保存       查询展示
```

其余能力建议这样处理：

```text
Monitor Admin
  -> 先改成按需启用，不急着永久删除

Prometheus + node-exporter + cAdvisor
  -> 继续保持 metrics profile 默认不启动

重复日志文件、Docker 标准输出副本、双份 60 天历史
  -> 这才是当前更值得优先精简的真重复
```

本图只分析和给出选择，不实际删除服务、源码、菜单、数据目录或历史数据。

## 先看全图

### 哪些是合作，哪些是重叠

```text
                         [应用产生一次日志事件]
                                   |
                    +--------------+--------------+
                    |                             |
                    v                             v
             [Logback 文件]                [控制台 stdout]
                    |                             |
                    v                             v
                 [Alloy]                  [Docker json-file]
                    |                             |
                    v                             |
                 [Loki]                          |
                    |                             |
                    v                             |
                [Grafana]                        |
                                                  |
                    同一事件保存两份 <-------------+


[后端 Actuator] <------ [Monitor Admin]
      Java 服务状态、线程、日志级别、单实例日志

[主机/容器 exporter] -> [Prometheus] -> [Grafana]
      CPU、内存、磁盘和容器资源趋势
```

上图中：

- Alloy、Loki、Grafana 是一条流水线的三个工位，缺一个就要用别的工具替代，不属于功能重复。
- Monitor Admin 和 Grafana 都有网页，也都能显示“监控信息”，但数据来源与用途不同，只是部分交叉。
- 文件日志和 Docker `json-file` 保存了大量相同事件，这是实际存储重复。

### 推荐的精简后形态

```text
默认启动：日志优先

[后端单一日志文件] -> [Alloy] -> [Loki] -> [Grafana]
       保留较短              集中保留较长


需要 Java 深度诊断时：

[按需启动 Monitor Admin] <-> [后端 Actuator]


需要 Linux 资源趋势时：

[按需启动 metrics profile]
          |
          +--> node-exporter
          +--> cAdvisor
          +--> Prometheus
```

这会把平时常驻的 observability 容器从 4 个降为 3 个；需要服务体检时增加 1 个，需要指标时再增加 3 个。

## 一步一步看

### 第一步：先确定你真正要回答的问题

删减前先把问题分开：

```text
问题 A：刚才哪个接口报错，完整上下文是什么？
  -> Loki + Alloy + Grafana

问题 B：哪个 Java 实例掉线，线程或日志级别怎样？
  -> Monitor Admin + Actuator

问题 C：是不是主机内存不足，哪个容器吃掉 CPU？
  -> Prometheus + exporters + Grafana
```

如果你目前只关心问题 A，那么 B 和 C 都可以不常驻。反过来，如果只想知道服务活没活，完整 Loki 日志平台也可能过重。

### 第二步：不要拆散日志三件套

当前日志链是：

```text
[Alloy]
  只负责读文件和发送
  不负责长期保存，也没有给人查询的完整页面
       |
       v
[Loki]
  只负责保存和查询
  不主动读取宿主机文件
       |
       v
[Grafana]
  只负责帮助人查询和展示
  不保存原始日志
```

所以对当前实现而言：

| 想删除的服务 | 直接删除后的结果 | 能否删 |
| --- | --- | --- |
| Alloy | 没人继续读取 Java 日志文件并发送 | 除非换采集器，否则不能 |
| Loki | 没有集中日志仓库 | 除非换存储，否则不能 |
| Grafana | Loki 仍有日志，但普通用户失去现成查询页面 | 技术上能，实际不推荐 |

这三个服务不是“三套日志系统”，而是一套系统的采集、存储和展示三层。

### 第三步：Monitor Admin 是最适合改成可选的服务

Monitor Admin 与 Grafana/Loki 的交叉点主要是“都能看到一些日志或故障信息”：

```text
Monitor Admin：
  选中一个 Java 实例
    -> 看健康、线程、环境、日志级别、Actuator logfile

Grafana + Loki：
  跨多个实例和服务
    -> 按时间、标签和关键词集中检索历史日志
```

如果日常主要使用 Grafana 查日志，而很少在线调整日志级别、查看线程或浏览 Actuator，那么 Monitor Admin 没必要默认常驻。

但建议先“按需启用”，不要立即永久删除，因为当前它已经接入很多位置：

- `<Path>release-artifacts/docker/docker-compose-observability.yml</Path>` 定义服务、镜像、端口和账号。
- `<Path>release-artifacts/docker/docker-compose-backend.yml</Path>` 给两个 Admin、SnailJob 和 SnailAI 配置注册地址及凭据。
- `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/pom.xml</Path>` 以及三个扩展服务的 POM 引入 Admin Client。
- `<Path>plus-ui-namewta/apps/admin-web/src/views/monitor/external/index.vue</Path>` 提供前端 iframe 入口。
- `<Path>plus-ui-namewta/apps/admin-web/.env.production</Path>` 提供 `/admin/applications` 地址。
- `<Path>release-artifacts/docker/frontend/nginx/lb/nginx-lb-http.conf.template</Path>` 提供 `/admin/` 代理。
- 后端初始化 SQL 还提供 `Admin监控` 菜单和 `monitor:admin:list` 权限。

只删一个 Compose 服务会留下注册失败日志、空白 iframe 和失效菜单，不算完整删除。

### 第四步：metrics 三件套已经默认不用

```text
[普通 observability 启动]
       |
       +--X--> Prometheus
       +--X--> node-exporter
       +--X--> cAdvisor

[带 --profile metrics 启动]
       |
       +-----> 三者才启动
```

这三项已经通过 `profiles: [metrics]` 变成可选能力。如果不需要主机和容器指标，不加 `--profile metrics` 就够了，没有必要仅为了“看起来干净”马上删除配置。

而且当前 metrics 能力还不完整：

- Prometheus 只抓自身、node-exporter 和 cAdvisor。
- 它没有抓取 Java 服务的 `/actuator/prometheus`。
- 仓库里没有预置主机或容器指标 Grafana 仪表盘。
- Grafana 会始终加载 Prometheus 数据源，但 metrics 未启动时该数据源只是不可连接。

因此当前阶段最务实的选择是“保留代码，默认不用”。如果未来确认永远不做指标监控，再整体删除三个服务、Prometheus 配置和 Grafana Prometheus 数据源。

### 第五步：node-exporter 和 cAdvisor 看似相同，观察范围不同

```text
node-exporter：
  [整台 Linux 主机]
    CPU / 内存 / 磁盘 / 文件系统

cAdvisor：
  [主机里的每个 Docker 容器]
    每个容器的 CPU / 内存 / 网络
```

它们都出现 CPU 和内存数字，但回答的问题不同：

```text
只想知道主机还剩多少资源？
  -> 只用 node-exporter

只想比较哪个容器最耗资源？
  -> 只用 cAdvisor

想知道“主机满了”和“哪个容器造成的”？
  -> 两个都用
```

如果只保留其中一个，必须同步删除 Prometheus 中另一个抓取目标，否则 Targets 页面会长期显示失败。

## 真正值得优先精简的重复

### 重复一：SnailJob 和 SnailAI 的同一事件进入多个文件

这两个服务的 Logback root 同时连接：

```text
[一条 INFO 日志]
       |
       +--> console.log
       +--> info.log
       +--> stdout -> Docker json-file

[一条 ERROR 日志]
       |
       +--> console.log
       +--> error.log
       +--> stdout -> Docker json-file
```

而 `<Path>release-artifacts/docker/observability/alloy/config.alloy</Path>` 使用 `**/*.log` 读取 SnailJob 和 SnailAI 目录，所以 `console.log`、`info.log` 和 `error.log` 都会进入 Loki。结果可能是同一事件在 Grafana 中出现两次。

优先级最高、影响最小的精简办法是先选一个集中采集权威：

```text
推荐第一步：
  Alloy 只采集 console.log
  旧 info.log / error.log 暂时仍留在磁盘

确认没有消费者后：
  再把 SnailJob / SnailAI Logback 收敛为单一文件
```

先缩小 Alloy 匹配范围能立即减少 Loki 重复，又不会立刻改变服务自己的本地日志习惯。永久删除 `info/error` appender 则需要验证第三方 Snail 组件没有依赖这些文件。

### 重复二：文件日志与 Docker `json-file`

Java 服务普遍同时启用控制台输出和文件输出：

```text
[同一 Java 日志]
       |
       +--> 文件 -> Alloy -> Loki
       |
       +--> stdout -> Docker json-file
```

Docker 配置为单文件最多 100MB、最多 5 个文件，理论上每个活跃容器可再保留约 500MB 标准输出历史。

三个选择如下：

| 选择 | 好处 | 代价 | 建议 |
| --- | --- | --- | --- |
| 文件和 stdout 都保留 | Loki 故障时还能用 `docker logs` | 双份磁盘和写入 | 当前可保留，但缩小 Docker 上限 |
| 生产只写文件 | 减少 Docker 日志副本 | `docker logs` 基本看不到应用日志 | 稳定运行后可考虑 |
| 只写 stdout，由 Alloy 读 Docker 日志 | 容器日志模型统一 | 要改 Alloy 挂载和安全边界，当前没有实现 | 不建议作为第一次精简 |

当前最保守的做法不是删除控制台 appender，而是把 Docker `max-size`、`max-file` 调小，例如只保留足够应急排查的短窗口。具体值应根据单日日志量决定，不能只凭文件数量猜。

### 重复三：本地 60 天与 Loki 60 天

```text
[应用原始日志文件] -- 本地保留 60 天

[Loki 集中日志]     -- 集中保留 60 天
```

这意味着集中采集成功后，同一批历史大部分时间保存两份。主 Admin 本地日志还有 40GB 总上限。

推荐的职责分配是：

```text
本地文件：短期缓冲，例如 7 到 14 天
  用于 Alloy 中断、Loki 故障和紧急恢复

Loki：长期集中查询，例如 60 天
  用于跨实例搜索和统一保留
```

不要把本地历史直接降为 0。Alloy 的位置记录不是日志内容备份；如果 Loki 长时间不可用、本地日志又提前轮转删除，缺失区间无法恢复。

### 重复四：Monitor Admin 有两个访问入口

```text
入口一：127.0.0.1:49090/admin

入口二：Nginx LB /admin/
```

如果生产运维统一从 Nginx LB 进入，可以删除 Monitor Admin 的宿主机 `49090:9090` 端口映射。容器仍能通过内部网络互相访问，前端 iframe 也仍走 Nginx。

保留直接端口的唯一主要价值是绕过前端和 LB 做本机应急排查。它默认只绑定 `127.0.0.1`，安全暴露面已经较小，所以这是“可以精简”，不是“必须精简”。

类似地，Grafana 通过内部地址访问 Prometheus。如果运维人员永远不直接打开 Prometheus 页面，`49091:9090` 端口映射也可以删除，不影响 Grafana 查询。

### 重复五：Monitor Admin 监控自己

Monitor Admin 同时是 Admin Server 和 Admin Client：

```text
[Monitor Admin Server]
          ^
          | 把自己注册给自己
          |
[Monitor Admin Client]
```

如果不需要在它自己的页面里观察它自己，可以只关闭 Monitor Admin 容器的 `SPRING_BOOT_ADMIN_CLIENT_ENABLED`。服务端收集其他应用的功能仍可保留。

这个精简节省的资源很少，主要价值是减少一个自注册实例和相关请求，不应把它当作首要优化。

## 哪些可以不用，哪些可以删除

### 可以立即不用，不需要改源码

| 能力 | 怎样不用 | 损失 |
| --- | --- | --- |
| Prometheus | 不启用 `metrics` profile | 没有历史指标 |
| node-exporter | 不启用 `metrics` profile | 没有 Linux 主机指标 |
| cAdvisor | 不启用 `metrics` profile | 没有容器资源指标 |
| Prometheus 独立页面 | 不访问 49091 | 无；Grafana 仍可内部查询，前提是 Prometheus 已启动 |

Monitor Admin 当前不在 profile 中，普通 `up observability` 会自动启动它。要让它真正“默认不用”，推荐先给它增加单独的 `service-monitor` profile，而不是让运维人员绕过管理脚本拼接原始 Docker 命令。

### 可以条件删除，但要成套处理

#### 永久删除 metrics 三件套

```text
删除 Compose 三个服务
       |
       +--> 删除 Prometheus 抓取配置
       +--> 删除 Grafana Prometheus 数据源
       +--> 更新 README、测试和管理脚本 profile 说明
       +--> 另行确认并备份后处理历史指标目录
```

这是最容易完整删除的一组，因为它目前已经与默认启动隔离，也没有前后端业务入口。

#### 永久删除 Monitor Admin

```text
删除 Monitor Admin 服务和镜像构建
          |
          +--> 所有后端关闭或移除 Admin Client
          +--> 删除注册 URL、账号和密码环境变量
          +--> 删除前端 Admin 监控菜单、权限和 iframe 目标
          +--> 删除 Nginx monitor_admin upstream 与 /admin/ 路由
          +--> 更新 SQL、测试、README 和端口登记
```

Actuator 的 `/health` 可以继续保留给容器健康检查或其他监控工具，不必因为删除 Monitor Admin 就把整个 Actuator 一起删掉。

#### 永久删除 Loki 日志栈

可以删除 Alloy、Loki、日志 Grafana 面板；如果 Grafana 也不用于指标，Grafana 也可一起删除。但这样只剩本地文件、`docker logs` 和 Monitor Admin 的单实例 logfile，不再具备跨实例集中检索。

对“日志监控”这个目标而言，这不是推荐方向。

## 三种最终方案怎样选

| 方案 | 常驻服务 | 能回答什么 | 不能回答什么 | 适用情况 |
| --- | --- | --- | --- | --- |
| 最小日志方案 | Alloy、Loki、Grafana | 跨服务查日志 | Java 深度状态、资源趋势 | 当前推荐 |
| 最小 Java 体检方案 | Monitor Admin | 实例健康、Actuator、单实例日志 | 集中日志搜索、长期资源趋势 | 机器很小、服务很少 |
| 完整可观测方案 | 全部七个 | 日志、Java 状态、主机与容器指标 | 当前仍缺 Java Prometheus 指标和指标面板 | 有明确运维需求 |

还有一种未来方案：

```text
[Java Micrometer 指标] --\
[主机与容器指标] -------> [Prometheus] -> [Grafana]
[应用日志] --------------> [Loki] ------> [Grafana]

删除 Monitor Admin
```

这样可以把查询统一到 Grafana，但它不是当前配置已经具备的替代关系。必须先加入 Java `/actuator/prometheus` 抓取、仪表盘和告警，并确认不再需要 Monitor Admin 的线程、环境、在线日志级别调整等管理能力，才能删除 Monitor Admin。

## 推荐的精简顺序

```text
第 1 步：什么都不永久删除
  metrics 保持默认关闭
  观察团队是否真的使用 Monitor Admin
        |
        v
第 2 步：消除确定的重复数据
  Alloy 对 SnailJob/SnailAI 只采一个权威日志文件
  缩短 Docker json-file 应急窗口
        |
        v
第 3 步：分配保留职责
  本地文件短保留
  Loki 长保留
        |
        v
第 4 步：把 Monitor Admin 改成可选 profile
  同时处理前端入口在未启动时的可用性
        |
        v
第 5 步：运行一段时间后再永久删除无人使用的能力
```

针对当前“主要为了日志监控”的目标，最终建议是：

```text
保留并默认启动：Alloy + Loki + Grafana

保留但按需启动：Monitor Admin

保留配置但默认不启动：Prometheus + node-exporter + cAdvisor

优先整改：
  SnailJob/SnailAI 多文件重复采集
  文件日志与 Docker json-file 的保存窗口
  本地 60 天与 Loki 60 天的双份长期保留
```

## 术语小词典

- 流水线分工：几个服务前后相接，各做采集、保存或展示中的一步，不代表重复。
- 功能交叉：两个工具能回答一部分相似问题，但各自还有不同能力。
- 真重复：同一事件或数据以近似用途保存多份，例如同一日志同时进入 `console.log` 和 `info.log`。
- 默认不用（profile）：配置仍在，但普通启动不创建容器，需要时可以恢复。
- 永久删除：不仅停容器，还要移除依赖、配置、入口、测试、文档和历史数据处理方案。
- 权威日志文件：集中采集时约定唯一读取的文件，避免同一事件从多个文件重复进入 Loki。
- 短期缓冲：本地保留少量历史，以便集中平台临时故障后补采。
- 集中保留：由 Loki 统一承担较长时间的跨实例历史查询。
- 自注册：Monitor Admin 既是服务端，又用客户端身份把自己登记到自己的服务列表。
- 深度诊断：查看线程、环境、日志级别等 Java 运行时细节，不只是判断端口是否存活。

## 你现在能复述什么

1. Alloy、Loki、Grafana 是同一日志流水线的三层，不是三套重复系统。
2. 只做集中日志时，Monitor Admin 和 metrics 三件套都不必默认常驻；metrics 已经默认关闭，Monitor Admin 适合再加一个独立 profile。
3. 当前最明显的浪费不是服务数量，而是 SnailJob/SnailAI 多文件重复采集、文件与 Docker 标准输出双写、以及本地与 Loki 都保留 60 天。
4. Monitor Admin 可以永久删除，但必须同步处理后端 Admin Client、前端菜单和 iframe、Nginx `/admin/`、SQL 权限、测试与文档，不能只删 Compose 服务。
5. 当前推荐的最小日志方案是 Alloy、Loki、Grafana；先按需停用，再用真实使用情况决定是否永久删除。
