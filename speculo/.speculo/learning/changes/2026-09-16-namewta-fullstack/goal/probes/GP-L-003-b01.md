## Q3 假设与反例

- `objective_id`: OBJ-03
- `bloom_level`: evaluate
- `socratic_move`: assumptions
- `difficulty`: H
- `expected_evidence`: `TestBatchController` 直接持 `TestDemoMapper`；sso/profile/third 的 `usecase/impl`；notify `adapter/worker` 对 Port 而非 UseCase；profile `adapter/api/PersonIdentityLookupServiceImpl` 才是入口适配器

课的反例挡住了四类口头错误：layered 里新建 `service/impl`+Mapper；classic 里再开一条五层日常写法；新模块抄 demo；同一模块按方法挑选模式。假设合格读者读完后仍以下面已存在的源码为样板，课挡得住吗？

1. **classic 已扩大的越层。** `TestBatchController` 注释写「为了便于测试 直接引入mapper」，字段 `TestDemoMapper testDemoMapper`。课把 `TestDemoServiceImpl` 持 Mapper 标成「登记过的 classic，允许」，但权威句是 classic「不得因新增功能继续扩大越层依赖」。读者能否区分「存量允许的 ServiceImpl→Mapper」和「Controller→Mapper 已经是扩大」？
2. **UseCaseImpl ≠ ServiceImpl。** 课的管家样板是具体类 `NotifyNoticeUseCase`。`wta-sso` / `wta-third` / `wta-profile-person` 是 `usecase` 接口 + `usecase/impl`。读者会不会把 `SsoOAuthUseCaseImpl` 看成 classic 的 `ServiceImpl`？
3. **任意 `adapter/` ≠ 入口 API Adapter。** 课反复说 Listener / API Adapter 与 Controller 同属门口、只能依赖 UseCase。脚本只把 `adapter/api` 或 `api/adapter` 当 entry。工作树里真正的入口适配器是 `PersonIdentityLookupServiceImpl`（实现 `wta-api`，只注入 `PersonProfileApiUseCase`）。notify 的 `adapter/worker/NotifyOutboxWorker` 注入的是 Port，不是 UseCase。读者会不会把 Outbox worker 误判成「门口必须只认管家」或「adapter 可以当第三种入口」？
4. **登记 classic ≠ demo 家具。** `wta-ai` 只有 `SnailAiController` + `OpenApiUserClient`，无 ServiceImpl/Mapper。`wta-job` 只有 `snailjob/*` 执行器，无 Controller、无 `src/main/resources`。读者会不会在这两间房里寻找课图上的 Mapper 链，或反过来把它们当成「可以不登记就非五层」的借口？

**问 Lesson：** 读完后仍说不出的，是不是「同一模块一种模式」这句口号，而是**登记列、源码形状、脚本退出码三者不一致时先信哪一份**？

## Q4 视角

- `objective_id`: OBJ-03
- `bloom_level`: analyze
- `socratic_move`: viewpoints
- `difficulty`: H
- `expected_evidence`: 登记表 vs `01-module-map.md` vs 脚本 `forbiddenByLayer`（仍含 `org.dromara.*`）vs ARCH-002A

从三份权威并读，课的 ASCII 分叉图缺了哪些边？

1. **登记表 → 模块地图。** 地图把 `wta-third` 写成独立业务模块（管理 API + `ThirdPartyGateway`），登记表 2026-09-16 未列名；`wta-third/AGENTS.md` 自述 `controller/admin -> usecase/impl -> service -> dao -> mapper`。课只说「未登记默认 layered、回头补表」，没有把「已落地却缺行」标成当前表缺陷。
2. **登记表 → 可验证路径。** 表行是 `wta-modules/wta-profile`；person/enterprise 才是可跑 layered 的模块。对父路径跑脚本必然失败。课未给出正确命令路径。
3. **脚本 → 合同。** `forbiddenByLayer` 仍匹配 `org.dromara.system.api` 等旧前缀；工作树跨模块合同是 `org.namewta.system.api.UserService`。入口若误 import `wta-api`，`.service.` 包规则与 dromara 规则都可能漏检。课写「脚本和人脑都会漏」，但没点出这条具体漏法。
4. **辅助层 → 五层主轴。** 脚本还管 port / adapter / support / domain、`@DSTransactional` 只能在 UseCase、support 不得成 Spring Bean。课把辅助包压缩成「可以存在，但不能绕过 UseCase、不能持有数据库或远程基础设施」。缺一条：`adapter/api` 是入口，其它 `adapter/*` 不是入口，也不得反向依赖 UseCase/Service/DAO。
5. **数据流边。** 课用公告只读列表证明五层 import 方向（有意不教 Outbox）。架构格子 `C:layered-classic` 不要求 Outbox 深走查；但「登记 layered 的模块当前脚本非零」这条边若完全不提，读者会把脚本失败理解成「模块不是 layered」。

**问 Lesson：** 为覆盖 `C:layered-classic`，是否必须补一张「登记名 / Maven 路径 / 当前脚本退出码 / 源码形状」对照，而不是再画一条 CRUD 链？
