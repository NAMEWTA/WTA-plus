## Finding S34-1 — medium — opening the box can preserve an older in-flight snapshot

**Location:** `frontend/apps/admin-web/src/utils/push.ts:132-150` (especially 146-148); unchanged caller `frontend/apps/admin-web/src/layout/components/Navbar.vue:132-134,36-43`; newly added test `frontend/e2e/inbox-without-realtime.spec.ts:75-81` explicitly asserts one request after the box opens.

**Reachable sequence:** Admin login starts the initial `GET /notify/inbox`. That GET has already taken a server snapshot but remains in flight. With `VITE_APP_MESSAGE_ENABLED=false`, a new announcement arrives, then the user opens the message box. Navbar calls `initMessageBox()` with its default `fresh=false`. Because `pendingInbox` has the same token, `initMessageBox` returns the old request and leaves `dirty=false`. When the old response arrives, `setNotices` displays the pre-announcement snapshot. There is no realtime connection, no follow-up GET and no automatic retry; the newly arrived message remains absent until the user closes and opens again or performs another refresh trigger.

**Contract:** Ticket section 6 step 3 requires login completion, opening the box and message events to refresh the shared REST fact while coalescing duplicate requests; AC-034 requires a valid session to remain able to read its own inbox when realtime is off. An explicit box opening after a server-side change is a freshness trigger, not merely another consumer of the login snapshot. The new synthetic assertion that `inboxCalls` remains 1 under a held login request cements this failure case instead of detecting it.

**Fix condition:** Make box opening request freshness even if the login query is pending, e.g. call `initMessageBox(true)` from Navbar so the existing dirty-follow-up mechanism performs one new GET after the held one settles. Add a controlled Promise test where the first result is old, opening occurs after the server fact changes, and the final visible list is new with realtime disabled. Because Navbar is outside the current T-34 writable paths, first declare its exact path in Ticket/Map or implement an equivalent narrowly scoped change in the allowed files that gives open-box an explicit fresh outcome. Keep passive duplicate calls coalesced and do not add polling. If the intended contract instead explicitly permits a stale opening while a login request is pending, amend the Ticket/Spec with that observable limit before treating this as accepted.
