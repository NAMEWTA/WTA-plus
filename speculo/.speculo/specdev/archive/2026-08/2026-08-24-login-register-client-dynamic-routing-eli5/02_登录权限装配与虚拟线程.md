# 登录权限装配与虚拟线程

先给结论：`SysLoginService.java:179-191` 不是在“计算某一次请求是否通过”，而是在用户登录时制作一份完整的**登录权限快照**。

这段代码要回答三个问题：

1. 这个用户在当前 Client 中拥有哪些菜单权限码和角色标识？
2. 这些权限数据怎样从用户、角色、菜单关系中查出来？
3. `ThreadUtils.virtualInvokeAll` 怎样让 4 组互不依赖的数据库查询同时进行，并在全部结束后才返回？

## 先看全图

```text
[用户通过密码、短信、邮箱等方式登录]
                    |
                    v
         [buildLoginUser]
                    |
                    +-- userId：哪个用户
                    |
                    +-- clientId：本次登录属于哪个 Client
                    |
                    v
       [virtualInvokeAll 同时启动 4 个任务]
                    |
          +---------+---------+----------------+--------------+
          |                   |                |              |
          v                   v                v              v
 [查菜单权限码]       [查角色标识]       [查角色对象]      [查岗位对象]
 menuPermission       rolePermission       roles             posts
          |                   |                |
          |                   |                +-> dataScopeRoleMap
          |                   |                    数据权限映射
          +---------+---------+----------------+--------------+
                    |
                    | 等待 4 个任务全部完成
                    v
            [完整 LoginUser]
                    |
                    v
       [存入 Sa-Token 的 Token Session]
                    |
          +---------+-------------------+
          |                             |
          v                             v
 [后端接口权限检查]              [/getInfo 返回前端]
 @SaCheckPermission              permissions + roles
 @SaCheckRole                            |
          |                              v
          v                      [按钮和前端角色判断]
 [允许或拒绝请求]                v-has-permi / v-has-roles
```

必须先分清下面 4 份数据：

```text
menuPermission
  -> 一组操作权限码，例如 system:user:list、system:user:add

rolePermission
  -> 一组角色标识，例如 superadmin、manager、common

roles
  -> 完整角色对象，例如角色 ID、角色名、roleKey、dataScope

posts
  -> 完整岗位对象；它不是菜单权限或角色权限
```

`menuPermission` 虽然名字里有“菜单”，但它不是侧边栏菜单对象，也不是路由树。它保存的是 `sys_menu.perms` 字段中的字符串。

## 一步一步看

### 第一步：先确定用户和本次登录的 Client

代码先从输入对象中取两个主键：

```java
Long userId = user.getUserId();
Long clientId = ObjectUtil.isNull(client) ? null : client.getId();
```

这里的 `clientId` 是 `sys_client.id` 的 Long 主键，不是登录请求头中用于识别 OAuth Client 的字符串 `clientId`。

后面的角色和菜单查询都必须带上这两个条件：

```text
[userId]
   |
   +-> 限定“是谁的角色和权限”

[clientId]
   |
   +-> 限定“本次登录可以看哪个 Client 的角色和菜单”
```

同一个用户即使能从不同 Client 登录，每次生成的权限快照也可能不同。

### 第二步：`virtualInvokeAll` 收到的是 4 个 Runnable

原代码可以先读成下面这个形状：

```java
ThreadUtils.virtualInvokeAll(
    () -> 做任务一,
    () -> 做任务二,
    () -> 做任务三,
    () -> 做任务四
);
```

`() -> { ... }` 是一张“稍后执行的工作单”，专业名字叫 Lambda。因为每张工作单只做事情、不直接向调用者返回值，所以它们会被当成 `Runnable`。

这 4 个任务不是依次查完再查下一个：

```text
顺序写法：
[任务一 80ms] -> [任务二 60ms] -> [任务三 100ms] -> [任务四 40ms]
总时间大约 280ms

并发写法：
时间起点 ------------------------------------------------->
[任务一 80ms  ----------------]
[任务二 60ms  ------------]
[任务三 100ms --------------------]
[任务四 40ms  --------]
总时间接近最慢任务的 100ms，再加少量调度开销
```

数字只是帮助理解的例子，不是这套系统的实测值。

### 第三步：任务一取得菜单权限码 `menuPermission`

第一张工作单是：

```java
loginUser.setMenuPermission(
    permissionService.getMenuPermission(userId, clientId)
);
```

普通用户的主要查询路径是：

```text
[sys_user 当前用户]
          |
          | userId
          v
[sys_user_role 用户与角色关系]
          |
          | roleId
          v
[sys_role 角色]
          |
          | 必须启用，并且 role.client_id = 当前 clientId
          v
[sys_role_menu 角色与菜单关系]
          |
          | menuId
          v
[sys_menu 菜单]
          |
          | menu.client_id = 当前 clientId
          | perms 不能为空、不能是空白字符串
          v
[去重后的权限码 Set<String>]
```

真实查询位于 `<Path>ruoyi-vue-plus-namewta/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/mapper/SysMenuMapper.java</Path>` 的 `selectMenuPermsByUserId`。它用 `distinct` 和 `HashSet` 去重，因此多个角色都拥有 `system:user:list` 时，结果里只保留一份。

除了用户显式分配的角色，系统还会合并当前 Client 的默认角色：

```text
[用户显式角色的菜单权限] ---+
                              +-> [合并并去重] -> menuPermission
[Client 默认角色的菜单权限] -+
```

默认角色不是要求每个用户都在 `sys_user_role` 中保存一条关系，而是由 Client 配置自动附加。读取前会校验：Client 存在且启用、默认角色存在且启用、默认角色确实属于当前 Client。

如果当前用户是超级管理员，`getMenuPermission` 还会先加入通配权限：

```text
普通用户       -> {system:user:list, system:user:add, ...}
超级管理员     -> {*:*:*, 当前 Client 查询到的其他权限码, ...}
```

`*:*:*` 表示所有菜单操作权限。即使是超级管理员，菜单和角色加载仍然携带当前 `clientId`，不会把所有 Client 的菜单合成一份。

### 第四步：任务二取得角色标识 `rolePermission`

第二张工作单是：

```java
loginUser.setRolePermission(
    permissionService.getRolePermission(userId, clientId)
);
```

它的查询过程是：

```text
[userId + 当前 clientId]
          |
          v
[查询用户在当前 Client 的角色对象]
          |
          +-> [合并当前 Client 默认角色]
          |
          v
[读取每个角色的 roleKey]
          |
          +-> roleKey 中有多个值时拆开
          |
          v
[去重后的角色标识 Set<String>]
```

例如两个角色对象是：

```text
角色 A：roleId=10，roleKey="manager"
角色 B：roleId=20，roleKey="auditor,reporter"
```

最后可能得到：

```text
rolePermission = {manager, auditor, reporter}
```

超级管理员会额外加入 `superadmin`。

所以这两个字段不能混用：

```text
@SaCheckPermission("system:user:list")
       |
       +-> 检查 menuPermission

@SaCheckRole("manager")
       |
       +-> 检查 rolePermission
```

一个角色可以带来很多菜单权限；角色名和菜单权限码不是同一种东西。

### 第五步：任务三取得完整角色，并建立数据权限映射

第三张工作单内部有前后依赖，所以它自己仍然按顺序执行：

```java
List<SysRoleVo> roles = roleService.selectRolesByUserId(userId, clientId);
List<RoleDTO> roleDtos = BeanUtil.copyToList(roles, RoleDTO.class);
loginUser.setRoles(roleDtos);
loginUser.setDataScopeRoleMap(
    permissionService.getDataScopeRoleMap(roleDtos)
);
```

流程是：

```text
[查 SysRoleVo 列表]
          |
          v
[复制成跨模块使用的 RoleDTO 列表]
          |
          +-> loginUser.roles
          |
          v
[按 roleId 批量查询每个角色拥有的菜单权限码]
          |
          v
[把 roleId -> 权限码 翻转成 权限码 -> roleId 列表]
          |
          v
 loginUser.dataScopeRoleMap
```

为什么要“翻转”？看一个例子：

```text
查询结果：
角色 10 -> {system:user:list, system:user:query}
角色 20 -> {system:notice:list}

翻转结果：
system:user:list   -> [10]
system:user:query  -> [10]
system:notice:list -> [20]
```

以后访问标有 `@SaCheckPermission("system:user:list")` 的数据接口时，数据权限处理器能知道：这次应让角色 10 参与数据范围计算，而不是把用户所有角色的数据范围不加区分地混在一起。

这也解释了为什么 `roles` 和 `dataScopeRoleMap` 放在同一个 Lambda 中：后者需要前者的 `roleDtos`，它们不能彼此并发。

### 第六步：任务四取得岗位对象

第四张工作单是：

```java
List<SysPostVo> posts = postService.selectPostsByUserId(userId);
loginUser.setPosts(BeanUtil.copyToList(posts, PostDTO.class));
```

查询关系很简单：

```text
[当前 userId]
       |
       v
[sys_user_post 用户岗位关系]
       |
       v
[sys_post 岗位]
       |
       v
[PostDTO 列表] -> loginUser.posts
```

岗位信息和前三组查询互不依赖，所以可以作为第四个并发任务。

### 第七步：线程工具内部到底做了什么

`ThreadUtils.virtualInvokeAll` 的真实实现位于 `<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-core/src/main/java/org/dromara/common/core/utils/ThreadUtils.java</Path>`。可以拆成 5 步：

```text
[创建“每个任务一个虚拟线程”的执行器]
                    |
                    v
[依次 submit 所有 Runnable]
                    |
                    v
[每个任务获得一个 Future 收据]
                    |
                    v
[对每张 Future 收据调用 get，等待任务完成]
                    |
                    v
[关闭执行器，然后返回调用者]
```

近似代码如下：

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Runnable runnable : runnableList) {
        futures.add(executor.submit(runnable));
    }
    for (Future<?> future : futures) {
        future.get();
    }
}
```

一个常见误解是：“第二个 `for` 按顺序 `get`，所以任务仍是串行的。”这不对。所有任务已经在第一个 `for` 中提交并开始运行；第二个 `for` 只是按提交顺序收回完成收据。

```text
submit A -> submit B -> submit C -> submit D
   |           |           |           |
   +-----------+-----------+-----------+
               都可以同时运行

get A -> get B -> get C -> get D
               逐张确认全部完成
```

`Future.get()` 还有两个重要作用：

1. 不让 `buildLoginUser` 提前返回半成品。
2. 保证子线程已经写入的字段在等待结束后能被当前线程看见。

因此第 192 行 `return loginUser` 执行时，正常情况下 4 个任务已经全部完成。

### 第八步：什么是虚拟线程

可以把传统平台线程想成数量有限的正式柜台，把虚拟线程想成很轻的办事号码：

```text
传统平台线程：
[昂贵柜台 1] [昂贵柜台 2] [昂贵柜台 3] ... 数量不宜过多

虚拟线程：
[轻量任务 A] [轻量任务 B] [轻量任务 C] [轻量任务 D] ...
       \          |          |          /
        JVM 把它们安排到底层平台线程执行
```

虚拟线程特别适合“等待数据库、网络或文件返回”的阻塞式任务。一个查询等待数据库时，JVM 可以让底层线程先服务其他虚拟线程。

它不会让一条 SQL 自身变快。这里的收益来自 4 组独立等待发生重叠。

### 第九步：异常或中断时会发生什么

```text
[某个查询正常失败]
        |
        v
[Future.get 抛 ExecutionException]
        |
        v
[取出真正 cause]
        |
        v
[包装为 RuntimeException("线程执行异常：...")]
        |
        v
[buildLoginUser 失败，登录不能拿半成品继续]
```

如果等待线程被中断，工具会重新设置当前线程的中断标记，然后抛出 `RuntimeException("线程执行被中断")`。这保留了“有人要求停止当前工作”的信号。

所有任务在等待前就已提交。当前实现没有在一个任务失败时显式调用 `cancel` 取消其他任务；执行器关闭时会完成资源收尾。因此不要把它理解成带“首个失败立即取消全部兄弟任务”的结构化并发工具。

### 第十步：完整 `LoginUser` 最后去了哪里

以密码登录为例：

```text
[PasswordAuthStrategy]
          |
          v
[buildLoginUser 得到完整 LoginUser]
          |
          v
[LoginHelper.login]
          |
          +-> StpUtil.login 创建 Token
          |
          +-> Token Session.set("loginUser", loginUser)
          |
          v
[后续请求携带 Token]
```

后端 Sa-Token 权限适配器从当前 Token Session 取 `LoginUser`：

```text
SaPermissionImpl.getPermissionList
  -> LoginUser.menuPermission

SaPermissionImpl.getRoleList
  -> LoginUser.rolePermission
```

也就是说，后续权限检查通常使用登录时的会话快照，不会因为每个接口调用而重新执行这一整组角色和菜单查询。

前端调用 `/system/user/getInfo` 时，后端也从同一个 `LoginUser` 取数据：

```text
LoginUser.menuPermission -> response.permissions -> Pinia permissions
LoginUser.rolePermission -> response.roles       -> Pinia roles
```

然后：

```text
[permissions]
     +-> v-has-permi 隐藏没有权限的按钮
     +-> 前端 auth.hasPermi 判断

[roles]
     +-> v-has-roles 判断角色
     +-> 动态路由元数据中的 roles 判断
```

前端隐藏按钮只是用户体验，真正的安全边界仍是后端的 `@SaCheckPermission` 和 `@SaCheckRole`。

### 第十一步：菜单权限码不等于真正的菜单路由

这是最容易被名字误导的地方：

```text
登录时：
[sys_menu.perms 字符串]
       |
       v
[LoginUser.menuPermission]
       |
       v
[接口和按钮权限判断]

进入系统后：
[/system/menu/getRouters]
       |
       +-> 从 Token Session 取 userId + clientPk
       |
       v
[重新查询当前 Client 的菜单树]
       |
       v
[RouterVo 路由列表]
       |
       v
[前端生成侧边栏和动态路由]
```

所以第 180 行拿到的是“菜单上声明的操作权限码”，不是把整个菜单树塞进 `LoginUser`。

### 第十二步：这个线程工具平时怎样使用

没有直接返回值、只需要执行动作时，使用 `virtualInvokeAll`：

```java
ThreadUtils.virtualInvokeAll(
    () -> loadProfile(),
    () -> loadMessages(),
    () -> loadSettings()
);
```

需要直接收集返回值，并且每个任务返回同一种类型时，可以使用同一工具类的 `virtualSubmitAll`：

```java
List<String> results = ThreadUtils.virtualSubmitAll(
    () -> serviceA.loadName(),
    () -> serviceB.loadName()
);
```

结果列表按提交顺序排列：`results.get(0)` 对应第一个 Supplier，`results.get(1)` 对应第二个 Supplier。

适合并发的任务应满足：

```text
[任务 A] ---- 不需要任务 B 的结果 ----+
[任务 B] ---- 不需要任务 C 的结果 ----+-> 可以一起提交
[任务 C] ---- 主要在等待数据库/网络 ---+
```

不适合直接这样并发的情况包括：

```text
[先创建订单] -> [必须拿订单 ID 才能创建明细]
      前后有依赖，不能拆成两个兄弟任务

[任务 A 修改同一个 List] <- 同时 -> [任务 B 修改同一个 List]
      共享可变数据可能发生竞态

[@Transactional 调用线程] -> [新虚拟线程]
      事务和普通 ThreadLocal 上下文不会自动等价地转移

[启动后台任务后立即返回]
      virtualInvokeAll 会等待全部任务，不是“发出去就不管”
```

本段登录代码之所以可用，是因为 4 个兄弟任务主要读取数据库，并分别写 `LoginUser` 的不同字段；第三个任务内部确有依赖，所以把“查角色”和“建立数据权限映射”留在同一个 Lambda 中顺序完成。

### 第十三步：读这段实现时还要知道的精确边界

菜单权限查询和角色对象查询并不是同一条 SQL：

```text
菜单权限查询
  -> 明确过滤正常状态角色
  -> 明确过滤当前 Client 的角色和菜单

角色对象查询
  -> 按 userId 和当前 clientId 查询
  -> 再合并经过校验的 Client 默认角色
```

从当前 Mapper 代码看，角色对象查询本身没有与菜单权限查询相同的 `role.status = 正常` 条件。因此不能仅凭方法名假定这两份结果在所有异常数据状态下必然完全一致；若要评估“停用角色仍有关联”场景，应单独做安全审查和回归测试。

另外，权限是会话快照：数据库里的角色或菜单关系发生变化后，已经登录的 Token 不会因为这段代码自动实时重查。系统需要通过既有的在线会话清理机制使受影响会话重新建立权限快照。

## 术语小词典

- 登录权限快照（`LoginUser`）：登录时把身份、Client、角色、权限和岗位装进一个对象，后续请求从会话中读取。
- 菜单权限码（`menuPermission`）：菜单记录 `perms` 字段中的操作标识，例如 `system:user:list`，不是菜单树本身。
- 角色标识（`rolePermission` / `roleKey`）：代表用户身份类别的字符串，例如 `manager` 或 `superadmin`。
- Client 隔离：同一用户每次只能在当前登录 Client 的边界内加载角色、菜单和路由。
- 默认角色：配置在 Client 上、登录时自动合并给该 Client 用户的角色，不要求显式写入用户角色关系表。
- 数据权限（`dataScope`）：用户已经通过接口权限检查后，还能看哪些部门或哪些行数据的范围规则。
- 数据权限角色映射（`dataScopeRoleMap`）：记录“某个接口权限码由哪些角色提供”，帮助数据权限只使用相关角色计算范围。
- 工作单（Lambda）：用 `() -> { ... }` 表示的一段稍后执行的代码。
- 可运行任务（`Runnable`）：只执行动作、不直接返回计算结果的任务接口。
- 供给任务（`Supplier<T>`）：执行后返回一个 `T` 类型结果的任务接口。
- 虚拟线程（virtual thread）：由 JVM 调度的轻量线程，适合大量等待数据库或网络的阻塞任务。
- 执行器（`ExecutorService`）：接收、安排并关闭一组线程任务的管理器。
- 完成收据（`Future`）：代表一个任务将来会完成；调用 `get()` 会等待并取得完成或失败结果。
- 并发（concurrency）：多个任务的执行时间互相重叠，不等于一条 SQL 自己变快。
- 会话（Token Session）：Sa-Token 根据 Token 保存当前登录上下文的地方。
- 通配权限（`*:*:*`）：后端和前端约定的“拥有所有菜单操作权限”标识。

## 你现在能复述什么

1. 这 13 行是在登录时并发装配一份 `LoginUser` 权限快照，不是在返回菜单树，也不是在执行某一个接口的最终判断。
2. 菜单权限沿着“用户 -> 用户角色 -> 角色菜单 -> 菜单 `perms`”取得，并由当前 `clientId` 收敛；角色权限则从当前 Client 的角色 `roleKey` 得到，两者都会合并 Client 默认角色，超级管理员还会加入通配标识。
3. `virtualInvokeAll` 先把所有 `Runnable` 提交到虚拟线程执行器，再逐个 `Future.get()` 等待；所以任务同时运行，但方法只有在全部成功后才返回。
4. 完整 `LoginUser` 被放进 Sa-Token 的 Token Session；后端权限检查和前端 `/getInfo` 都读取这份快照。
5. 真正的侧边栏菜单由 `/system/menu/getRouters` 使用会话里的 `userId + clientPk` 另行查询，不能把它与 `menuPermission` 权限码集合混为一谈。
