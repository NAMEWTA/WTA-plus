# 可观测日志监控全链路

这份图解回答三个问题：

1. 这套可观测系统是什么，为什么需要它？
2. `docker-compose-observability.yml` 启动的每个服务分别做什么？
3. 日志、服务状态和机器指标怎样从后端流到监控页面，前端又怎样进入这些页面？

先记住一个最重要的结论：这里不是一条万能监控链，而是三条相互独立的链。

```text
日志内容链：应用日志文件 -> Alloy -> Loki -> Grafana

服务状态链：后端的 Admin Client -> Monitor Admin -> 后端的 Actuator

机器指标链：node-exporter / cAdvisor -> Prometheus -> Grafana
```

当前实现层面的事实来自 Compose、Alloy、Loki、Grafana、Prometheus、后端配置和前端源码。本次没有实际启动容器，因此这里解释的是“配置已经定义的连接”，不是一次运行中的健康证明。

## 先看全图

### 一张图看懂全部关系

```text
                              同一个 Docker 私有网络
                    ruoyi-namewta-network（服务名就是地址）

 [后端一号] --写文件--\
 [后端二号] --写文件---+--> [宿主机 runtime/logs] --只读挂载--> [Alloy]
 [监控中心] --写文件---+                                    |
 [任务服务] --写文件---+                                    | 推送日志
 [智能服务] --写文件--/                                     v
                                                          [Loki]
                                                             |
                                                             | 查询日志
                                                             v
 [浏览器] <---------- 43000 端口 ------------------------- [Grafana]
                                                             ^
                                                             | 查询指标
                                                             |
 [Linux 主机] --> [node-exporter] --\                      [Prometheus]
 [Docker 容器] -> [cAdvisor] -------+------------------------/

 [后端一号 / 后端二号 / 任务服务 / 智能服务]
          | 注册自己，并开放带账号密码的 Actuator
          v
 [Monitor Admin] <------ /admin/ ------ [Nginx 统一入口]
                                              ^
                                              |
                                      iframe 嵌入管理前端
                                              |
                                         [浏览器]
```

图中有两个容易混淆的名字：

- Grafana 是“统一看日志和指标的仪表盘”。
- Monitor Admin 是“查看 Java 服务是否健康、有哪些实例和 Actuator 信息的服务监控台”。

Monitor Admin 不替代 Grafana，Grafana 也不替代 Monitor Admin。

### Compose 默认启动什么

```text
[启动 observability]
          |
          +--> ruoyi-monitor-admin
          +--> loki
          +--> alloy
          +--> grafana
          |
          +-- 不启动 --> prometheus
          +-- 不启动 --> node-exporter
          +-- 不启动 --> cadvisor

[启动 observability --profile metrics]
          |
          +--> 上面全部七个服务
```

`prometheus`、`node-exporter` 和 `cadvisor` 标有 `metrics` 启动档位（profile），所以普通启动只带日志和 Java 服务监控；显式启用 `metrics` 才增加 Linux 主机与容器指标。

## 一步一步看

### 第一步：后端先把日志写成文件

主后端的 Logback 会把 `INFO` 及以上日志写入 `sys-console.log`：

```text
[Java 代码产生一条日志]
           |
           v
[Logback 判断级别和格式]
           |
           v
[/ruoyi/server/logs/sys-console.log]
           |
           | Docker 目录映射
           v
[宿主机 runtime/logs/server1/sys-console.log]
或
[宿主机 runtime/logs/server2/sys-console.log]
```

相关配置：

- `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/src/main/resources/logback-plus.xml</Path>` 使用环境变量 `LOG_PATH`，当前只写 `sys-console.log`，按天压缩，最多保留 60 天且历史总量上限为 40GB。
- `<Path>release-artifacts/docker/docker-compose-backend.yml</Path>` 把两个 Admin 实例的 `LOG_PATH` 都设为 `/ruoyi/server/logs`，再分别映射到宿主机的 `logs/server1` 和 `logs/server2`，所以两台实例不会写进同一个文件。
- Monitor Admin、SnailJob 和 SnailAI 也在各自容器工作目录的 `logs` 下写文件，并映射到同一宿主机日志根的 `monitor`、`snailjob` 和 `snailai` 子目录。

这里采用的是“文件接入”，后端没有调用 Loki SDK，也不会直接向 Grafana 发日志。

### 第二步：Alloy 像持续看守文件的收件员

Compose 把宿主机的整个日志根以只读方式交给 Alloy：

```text
[宿主机 NAMEWTA_DATA_ROOT/logs]
               |
               | 只读挂载
               v
[/var/log/ruoyi]
               |
               v
[Alloy 按目录找 *.log]
               |
               +--> server1  标记 service=ruoyi-admin, instance=server1
               +--> server2  标记 service=ruoyi-admin, instance=server2
               +--> monitor  标记 service=ruoyi-monitor-admin
               +--> snailjob 标记 service=ruoyi-snailjob-server
               +--> snailai  标记 service=ruoyi-snailai-server
```

`<Path>release-artifacts/docker/observability/alloy/config.alloy</Path>` 做三件事：

1. 只匹配明确列出的五类 Java 服务日志目录。
2. 给每条日志附上 `job=ruoyi`、`service` 和 `instance` 标签，方便以后筛选。
3. 把新内容推送到 `http://loki:3100/loki/api/v1/push`。

Alloy 的位置记录保存在宿主机 `observability/alloy` 目录。它重启后可以接着上次位置继续读，避免每次从文件第一行重新发送。

### 第三步：Loki 保存并索引日志

```text
[Alloy 推送：日志正文 + 标签]
                 |
                 v
[Loki 接收端口 3100]
                 |
                 +--> 索引：根据时间和标签找日志
                 |
                 +--> 数据块：保存日志正文
                 |
                 v
[宿主机 observability/loki]
```

`<Path>release-artifacts/docker/observability/loki/loki.yml</Path>` 定义的是单机 Loki：

- 使用本地文件系统，不依赖对象存储。
- 复制份数为 1，适合单机部署，不是高可用集群。
- 日志保留期为 60 天，由 compactor 执行清理。
- `auth_enabled: false`，Loki 自身不校验账号；当前 Compose 没有把 3100 端口发布到宿主机，只允许同一 Docker 网络里的服务访问，这是它目前的重要保护边界。

Loki 的 60 天是“集中日志库的保留期”；Logback 自己的 60 天是“原始文件的保留期”。两边各自清理，互不代替。

### 第四步：Grafana 查询 Loki 并画成日志面板

```text
[浏览器]
    |
    | http://127.0.0.1:43000
    v
[Grafana 登录]
    |
    | Grafana 服务端代替浏览器查询
    v
[Loki 数据源 http://loki:3100]
    |
    v
[返回日志 -> Grafana 显示]
```

Grafana 启动时会自动装入两类配置：

- `<Path>release-artifacts/docker/observability/grafana/provisioning/datasources/loki.yml</Path>`：建立默认 Loki 数据源。
- `<Path>release-artifacts/docker/observability/grafana/provisioning/datasources/prometheus.yml</Path>`：建立 Prometheus 数据源。
- `<Path>release-artifacts/docker/observability/grafana/provisioning/dashboards/namewta.yml</Path>`：从固定目录加载 NAMEWTA 仪表盘。
- `<Path>release-artifacts/docker/observability/grafana/dashboards/namewta-logs.json</Path>`：提供 `NAMEWTA Logs` 日志仪表盘。

当前日志面板的查询是：

```text
{job="ruoyi"}
```

它表示“显示 Alloy 标记为 `job=ruoyi` 的全部日志”。面板默认看最近 1 小时，每 30 秒刷新，并允许展开日志详情。若要只看一号后端，可以在 Grafana Explore 中进一步按 `service` 和 `instance` 标签筛选。

Grafana 数据目录映射到宿主机 `observability/grafana`，账号、用户偏好等运行数据不会随着容器重建而消失。仪表盘 JSON 和数据源配置则以只读文件装入，不能在页面中永久改写这些受管定义。

### 第五步：Monitor Admin 走另一条服务健康链

Monitor Admin 不读取 Loki。它使用 Spring Boot Admin 协议和 Spring Boot Actuator：

```text
[后端服务启动]
       |
       | Admin Client 带账号密码注册
       v
[Monitor Admin 的 /admin]
       |
       | 根据注册地址反向请求
       v
[后端服务的 /actuator/**]
       |
       +--> health：是否健康
       +--> logfile：应用日志文件
       +--> env、beans、loggers 等已暴露端点
       |
       v
[Monitor Admin 页面汇总实例状态]
```

主后端的接入点包括：

- `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/pom.xml</Path>` 引入 `spring-boot-admin-starter-client`。
- `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/src/main/resources/application-prod.yml</Path>` 原本默认关闭客户端，Compose 用 `SPRING_BOOT_ADMIN_CLIENT_ENABLED=true` 打开它，并把注册地址改成 Docker 网络内的 `http://ruoyi-monitor-admin:9090/admin`。
- `<Path>ruoyi-vue-plus-namewta/ruoyi-admin/src/main/resources/application.yml</Path>` 暴露 Actuator 端点，并把 `logfile` 指向 `./logs/sys-console.log`。
- `<Path>ruoyi-vue-plus-namewta/ruoyi-common/ruoyi-common-security/src/main/java/org/dromara/common/security/config/SecurityConfig.java</Path>` 给 `/actuator/**` 加 Basic Auth，Monitor Admin 使用注册元数据中的账号密码读取它。

SnailJob 和 SnailAI 的生产配置本来就启用 Admin Client；Compose 再把它们的注册地址和账号密码改成容器网络中的 Monitor Admin。Monitor Admin 自己也作为客户端注册给自己，所以页面中也能看到监控中心实例。

`<Path>ruoyi-vue-plus-namewta/ruoyi-extend/ruoyi-monitor-admin/src/main/resources/application.yml</Path>` 把所有页面放在 `/admin` 下，Monitor Admin 自己使用登录表单和 HTTP Basic 保护，账号密码来自 `.env` 中的 `MONITOR_USERNAME` 与 `MONITOR_PASSWORD`。

### 第六步：可选指标链只监控主机和容器

启用 `metrics` profile 后才有这条链：

```text
[Linux 主机 CPU、内存、磁盘]
              |
              v
       [node-exporter:9100] --\
                                 \
                                  >--每 15 秒抓取--> [Prometheus]
                                 /
[Docker 容器 CPU、内存、网络]   /
              |                 /
              v                /
          [cAdvisor:8080] -----/
                                  |
                                  v
                         [保存 30 天指标]
                                  |
                                  v
                              [Grafana]
```

三个服务的关系是：

- node-exporter 读取 Linux 主机视角的数据，例如 CPU、内存和文件系统。
- cAdvisor 读取 Docker 容器视角的数据，例如每个容器的 CPU、内存和网络使用量。
- Prometheus 每 15 秒主动访问自身、node-exporter 和 cAdvisor 的指标地址，并把时间序列保存到宿主机 `observability/prometheus`，保留 30 天。

当前 Prometheus 配置没有抓取 `ruoyi-server1`、`ruoyi-server2` 或其他 Java 服务的 `/actuator/prometheus`，也没有装入现成的指标仪表盘。因此现在的可选指标链是“主机 + 容器基础指标接线”，不是“Java 业务指标已经完整可视化”。

## 七个服务分别做什么

| 服务 | 日常类比 | 真正职责 | 默认启动 | 宿主机入口 |
| --- | --- | --- | --- | --- |
| `ruoyi-monitor-admin` | Java 服务体检中心 | 接收 Admin Client 注册，再读取各服务 Actuator | 是 | `127.0.0.1:49090/admin` |
| `loki` | 带标签的日志仓库 | 接收、索引、保留和查询日志 | 是 | 无，只在 Docker 网络开放 3100 |
| `alloy` | 日志收件员 | 跟踪指定文件，附标签并推送到 Loki | 是 | 无 |
| `grafana` | 查询与展示大厅 | 查询 Loki/Prometheus，显示日志或指标 | 是 | `127.0.0.1:43000` |
| `prometheus` | 定时抄表员兼指标仓库 | 每 15 秒抓取 exporter 并保存 30 天 | 仅 `metrics` | `127.0.0.1:49091` |
| `node-exporter` | 主机仪表传感器 | 暴露 Linux 主机 CPU、内存、磁盘等指标 | 仅 `metrics` | 无宿主机映射，网络内 9100 |
| `cadvisor` | 容器仪表传感器 | 暴露 Docker 容器资源指标 | 仅 `metrics` | 无宿主机映射，网络内 8080 |

此外，Compose 顶部的 `json-file` 不是第八个服务，而是 Docker 自带的容器标准输出保存方式：

```text
[容器 stdout / stderr]
          |
          v
[Docker json-file]
  单文件最多 100MB
  最多保留 5 个文件
```

这只限制 Docker 自己的标准输出日志占盘。当前 Alloy 没有读取 Docker `json-file`，所以它和 Grafana 日志链是并行的两份日志出口，不是自动相连的上下游。

## 后端和前端怎样接入

### 后端接入有两种方式

```text
方式一：接入集中日志

[后端 Logback] -> [目录映射] -> [Alloy 读文件]

方式二：接入服务监控

[Admin Client 注册] -> [Monitor Admin]
[Monitor Admin 查询] -> [后端 Actuator]
```

第一种是“旁路采集”：后端只管写本地文件，并不知道 Alloy、Loki 或 Grafana 的存在。好处是日志平台临时停止时，后端业务仍可继续写文件；Alloy 恢复后从位置记录继续读取。

第二种是“应用主动注册 + 监控端反向查询”：后端必须启用 Admin Client、暴露 Actuator，并让 Monitor Admin 有正确账号密码和可达地址。

### 管理前端只嵌入 Monitor Admin

```text
[用户点击 Admin 监控菜单]
              |
              | 先检查 monitor:admin:list 权限
              v
[管理前端 external 页面]
              |
              | iframe 地址 /admin/applications
              v
[Nginx LB 的 /admin/ 路由]
              |
              v
[ruoyi-monitor-admin:9090/admin/]
```

真实接入位置：

- `<Path>plus-ui-namewta/apps/admin-web/src/views/monitor/external/index.vue</Path>` 读取 `VITE_APP_MONITOR_ADMIN`，检查 `monitor:admin:list` 后放入 iframe。
- `<Path>plus-ui-namewta/apps/admin-web/.env.production</Path>` 把生产地址设为 `/admin/applications`；开发环境则默认直接访问 `http://localhost:9090/admin/applications`。
- `<Path>release-artifacts/docker/frontend/nginx/lb/nginx-lb-http.conf.template</Path>` 把统一入口的 `/admin/` 转发给 `ruoyi-monitor-admin:9090/admin/`，并明确拒绝外部访问 `/actuator/**`。

菜单权限只决定“管理前端是否给用户打开入口”；Monitor Admin 自己仍会要求登录。这是两层不同的访问控制。

### Grafana 当前没有嵌入管理前端

```text
[管理前端菜单] -X-> [Grafana]

[浏览器] -> [127.0.0.1:43000] -> [Grafana 登录]
```

当前前端没有 Grafana 环境变量、页面或菜单，Nginx LB 也没有 `/grafana/` 代理路由。因此查看集中日志需要直接访问 Grafana 的宿主机端口，使用 `.env` 中单独配置的 `GRAFANA_ADMIN_USER` 和 `GRAFANA_ADMIN_PASSWORD`。

Grafana 的浏览器不会直接连接 Loki。浏览器只连接 Grafana，Grafana 服务端再通过 Docker 内部地址 `http://loki:3100` 查询，所以 Loki 不需要公开宿主机端口。

## 当前没有接入什么

“启动了可观测服务”不等于“所有东西都已经被采集”。当前边界如下：

```text
已进入 Loki：
  server1 / server2 / monitor / snailjob / snailai 的匹配日志文件

未进入 Loki：
  Nginx access/error 日志
  浏览器 console 日志
  Docker json-file 日志
  MySQL / Redis / MinIO / Elasticsearch 日志
  不在 Alloy 五组路径中的其他文件

已进入 Prometheus：
  Prometheus 自身、Linux 主机、Docker 容器指标

未进入 Prometheus：
  Java Actuator Prometheus 指标
  MySQL / Redis / Nginx 的专用 exporter 指标
```

特别注意前端：浏览器里的 `console.log` 不会自动传回服务器；Nginx 日志写在 `<Path>release-artifacts/docker/frontend/nginx/log/</Path>`，而 Alloy 只挂载 `${NAMEWTA_DATA_ROOT}/logs`。因此当前 Grafana 的 `NAMEWTA Logs` 面板主要是 Java 后端服务日志，不是前后端全链路日志。

还有四个运行边界：

1. `depends_on: [loki]` 只保证 Docker 先启动 Loki 容器，不保证 Loki 已经通过健康检查；配置中没有 observability 健康检查。
2. 四类 Compose 依赖已经存在的 external network，管理脚本会幂等创建；直接运行单个 Compose 前必须自己确保网络存在。
3. `node-exporter` 和 cAdvisor 挂载 Linux 主机的根目录、`/sys`、Docker 目录与 `/dev/kmsg`，主要面向 Linux Docker 主机，不应把 macOS Docker Desktop 体验当成同样的宿主机视角。
4. Loki、Grafana 和 Prometheus 都有持久数据目录。删除卷或宿主机目录会丢历史，不能把重建容器等同于无损重启。

## 启动后怎样访问和排查

### 启动顺序

管理脚本定义的完整启动顺序是：

```text
[基础设施]
 MySQL / Redis / MinIO
       |
       v
[可观测服务]
 Monitor Admin / Loki / Alloy / Grafana
       |
       v
[后端服务]
 Admin 双实例 / SnailJob / SnailAI
       |
       v
[前端服务]
 Nginx LB / Admin Web
```

这样后端启动并注册时，Monitor Admin 已经先开始启动；后端写出第一批日志时，Alloy 和 Loki 也已开始启动。

常用命令来自 `<Path>release-artifacts/scripts/docker-manage.sh</Path>`：

```bash
# 检查 Compose 展开结果
bash release-artifacts/scripts/docker-manage.sh config observability

# 启动默认日志与服务监控
bash release-artifacts/scripts/docker-manage.sh up observability

# 加上 Linux 主机和容器指标
bash release-artifacts/scripts/docker-manage.sh up observability --profile metrics
```

### 默认访问地址

```text
Grafana：
  http://127.0.0.1:43000

Monitor Admin 直接端口：
  http://127.0.0.1:49090/admin/applications

Monitor Admin 经完整前端统一入口：
  http://<LB 地址>/admin/applications

Prometheus，仅 metrics profile：
  http://127.0.0.1:49091
```

默认只绑定 `127.0.0.1`。设置 `NAMEWTA_BIND_HOST` 才会改变监听范围；扩大到内网或公网前，必须重新评估 Grafana、Monitor Admin 和 Prometheus 的认证与网络边界。

### 日志面板为空时按箭头倒着查

```text
[Grafana 没有日志]
        |
        v
1. Loki 数据源能否连接？
        |
        v
2. Loki 中是否存在 job="ruoyi"？
        |
        v
3. Alloy 是否能连接 http://loki:3100？
        |
        v
4. Alloy 的 /var/log/ruoyi 下是否看得到 *.log？
        |
        v
5. 宿主机 runtime/logs 下是否已有文件和新内容？
        |
        v
6. 后端容器是否把正确目录映射出来？
```

如果 Monitor Admin 看不到实例，则查另一条链：Admin Client 是否启用、注册地址是否为 `ruoyi-monitor-admin:9090/admin`、账号密码是否一致、Monitor Admin 能否访问客户端容器 IP 的 `/actuator/health`。不要用 Loki 是否有日志来判断 Admin Client 是否注册成功。

## 术语小词典

- 统一观察系统（可观测性，observability）：把日志、健康状态和资源数字集中起来，帮助回答“哪里出问题、何时开始、影响谁”。
- 应用日记（日志，log）：程序运行时写下的事件文字，例如请求、异常和启动信息。
- 文件收件员（Grafana Alloy）：持续读取指定文件的新内容，附上标签后发送到日志仓库。
- 日志仓库（Loki）：按时间和标签保存、检索日志的服务。
- 看板大厅（Grafana）：连接数据源并展示日志或指标的网页，不负责直接产生这些数据。
- 服务体检台（Spring Boot Admin / Monitor Admin）：登记 Java 服务并读取它们的 Actuator 信息。
- Java 服务体检口（Actuator）：后端提供的健康、日志、环境、线程等管理端点；本项目用 Basic Auth 保护。
- 定时抄表系统（Prometheus）：定期抓取数字指标并按时间保存。
- 主机传感器（node-exporter）：把 Linux 主机的 CPU、内存和磁盘状态变成 Prometheus 可抓取的数字。
- 容器传感器（cAdvisor）：把每个 Docker 容器的资源使用情况变成指标。
- 数据源（datasource）：Grafana 查询数据的后端地址；当前有 Loki 和 Prometheus 两个。
- 标签（label）：贴在日志上的可检索信息，例如 `service=ruoyi-admin` 和 `instance=server1`。
- 目录映射（bind mount）：让容器内路径和宿主机目录指向同一批文件。
- 私有服务网络（Docker bridge network）：容器用服务名互相访问的网络，例如 `loki:3100`，不等于公网地址。
- 启动档位（profile）：只有显式选择时才启动的一组 Compose 服务；这里的 `metrics` 包含 Prometheus 和两个 exporter。
- 保留期（retention）：历史数据最多保留多久；当前 Loki 日志 60 天、Prometheus 指标 30 天。

## 你现在能复述什么

1. 日志链不需要后端直接认识 Loki：后端写文件，Docker 把文件放到共享宿主机目录，Alloy 读取并推给 Loki，Grafana 再查询 Loki。
2. Monitor Admin 是独立的 Java 服务监控链：后端主动注册，Monitor Admin 使用账号密码反向读取 Actuator；管理前端通过权限检查、iframe 和 Nginx `/admin/` 路由打开它。
3. Prometheus、node-exporter 和 cAdvisor 只有启用 `metrics` profile 才启动；当前抓的是 Linux 主机和 Docker 容器指标，还没有抓 Java Actuator 指标。
4. Grafana 当前通过 `43000` 独立访问，没有嵌入管理前端；Loki、Alloy 和 exporters 没有对宿主机公开页面。
5. 当前集中日志只覆盖 Alloy 明确列出的五类 Java 服务文件，不覆盖 Nginx、浏览器、Docker `json-file` 或基础设施日志。

```text
想查某次后端报错？
  -> Grafana -> Loki 日志

想看某个 Java 实例是否健康？
  -> 管理前端 -> Monitor Admin -> Actuator

想看主机或容器是否吃满资源？
  -> 启用 metrics -> Grafana / Prometheus
```
