- difficulty: high

课的隐含假设若反转，合格读者会把哪扇门或哪道闸认错？

1. **「三扇门共用 `cacheCaptchaCode`」。** 覆盖该方法的测试证明 SMS/MAIL 失败不缓存。图形路径根本不进这个钩子。读者按暂停项 1 打开文件，会看到两套 Redis 写入，却以为改测试钩子等于改了 `/auth/code`。
2. **「口表里的密码策略 = `PasswordPolicyService`」。** 删键发生在密码**登录策略**。读者可能口述成「策略服务删验证码」或「登录会跑 `validateOrThrow` 所以旧弱密码进不去」——后者已被反例 3 钉死，前者仍被对照表喂回去。
3. **「邮箱拆 impl 是为了 enable 闸」。** 注释原句还在。工作树没有这只闸。读者会把图形开关抄到 `/resource/email/code`，或以为关 `captcha.enable` 就停掉短信/邮箱发码。
4. **「管理端新增用户走 `generateDefaultPassword`」。** `add` 对请求体 `validateOrThrow`。无 userId 的 `getInfo` 才把 generate 填进 Vo 当候选。把 B 格扩成 generate，会把 L-015 的候选/导入链算进 OBJ-12。
5. **「文件开头的 `initPassword=123456` 仍是现行菜谱」。** 同文件后段把旧键随机化退役，另插 `sys.user.passwordPolicy`。只读到 344 行会以为弱默认仍在。
6. **「domain-admin 不 GET 短信码，等于这两扇门不存在」。** 身份服务 `login` 还把 `grantType` 写死为 `password`。门在 `CaptchaController` 上仍然匿名可打；缺的是本厅堂的调用，不是后端入口。

问：读完后仍说不出的，是不是「三条 path 的名字」，而是 **图形答案柜到底谁写入、口表「密码策略」到底是哪个类、generate 算不算本格副作用**？
