## Checked source contracts

- **Version-specific durable fence.** `NotifyNoticeUseCase.java:25-31` wraps publication and retraction in `@DSTransactional`. `NotifyNoticeService.java:121-147` takes the Notice row lock, reads the latest snapshot, then locks the exact `(appId, idempotencyKey)` Intent. `NotifyNoticeVersionFence.java:29-47,59-98` binds the marker to app/scene/template/bizId/idempotency version and changes only that version to `retracted=true`; malformed or audit-only old metadata is `UNVERIFIED` for dispatch/retry. The metadata update (`NotifyNotificationDao.java:99-116`) writes only metadata, so an external result transaction cannot have its aggregate status overwritten by retract. `NotificationApplicationRuntimeService.java:179-195` rejects manual retry of RETRACTED/UNVERIFIED versions.
- **Worker and external outcome.** `DispatchNotificationService.java:69-124` calls `deadlineGate` before routing and again immediately before the external client; `NotifyDispatchResultService.java:28-44,70-146` uses Intent→Outbox→Delivery locks and an active lease. The fence closes IN_APP without a relation and closes external work only when the lease was claimed from READY, the persisted `DEADLINE_UNSENT_READY` marker and both attempt counts are zero, and no provider/accept/delivered fact exists (`:149-170`). Other external work becomes UNKNOWN/WAITING_RECEIPT rather than a false unsent cancellation. An external call already past its gate writes its actual result through `complete` (`:313-367`), which does not overwrite it with a late retract decision. This implements a grant-of-execution boundary; a retract after the second gate does not promise to recall the call.
- **Publication/link atomicity.** `NotifyNoticeService.java:108-118` requires exactly one lifecycle update. `NotifyNoticePublisherService.java:45-90` inserts one snapshot, checks a positive receipt against the exact locked Intent and marker, then, only for IN_APP, updates `Intent.pathSnapshot`, `Intent.templateParamsJson.path`, and the same version's `Snapshot.pathSnapshot` to the own-inbox message ID; each update requires one row (`NotifyNotificationDao.java:118-126`, `NotifyPersistenceDao.java:48-56`). External-only publication retains `/notify/inbox`. A late update failure propagates to the use-case transaction, so no partial published lifecycle/Intent/snapshot is accepted. `InAppNotificationService.java:117-122` classifies the deep link as a notice.
- **Narrow missing-Intent seed case.** `NotifyNoticeService.java:150-170` allows only the two fixed six-SQL IDs, V1 with snapshot ID equal to notice ID, one snapshot, matching frozen source fields, ALL/IN_APP/empty recipient filters, and no same-business Notice Intent. Any other missing Intent fails before lifecycle change. Repeated retract is revalidated; it is not a generic missing-task success branch.
