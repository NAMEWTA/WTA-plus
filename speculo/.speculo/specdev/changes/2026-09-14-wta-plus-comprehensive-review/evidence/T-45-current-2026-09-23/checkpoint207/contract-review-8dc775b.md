## Blocking finding

**High — an old diagnostic can populate a new session for the same user.** `frontend/packages/web-domains/system/src/oss-config/OssConfigPage.vue:328–359` fences a result using only the user ID, list permission and a page-local version. The host implementation at `frontend/apps/admin-web/src/router/adminManifestRegistry.ts:195–198` exposes only Pinia `userId`. On a same-user re-login, `frontend/apps/admin-web/src/store/modules/user.ts:35–42` increments `sessionGeneration`, sets `identityLoaded=false`, and changes the token while the previous `userId` and permissions remain until `getInfo`; the page may also be retained by Admin's `KeepAlive`. If an earlier POST resolves in that interval, `current()` still returns true and writes its facts/error/loading state into the new session. After `getInfo` returns the same ID, the page watch need not see any identity change. This violates Ticket 45's “old response does not overwrite a new session” requirement. Add a read-only host session epoch/active value to `SystemWebRuntime`, capture it for each request, include it in `current()` and the close watcher, and test a generation/token change with an unchanged user ID and a late old success/error/finally. The backend permission check remains authoritative. Lead and writer were notified immediately.
